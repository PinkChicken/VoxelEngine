### 2026-07-20 (STILL OPEN, THIRD REJECTED ATTEMPT): the "own upward-facing lane pinned" buoyancy bug — a temporal (occupancy-history) lever also fails, same as the two prior geometric attempts

**Context:** picking up the open item from 2026-07-19's mirror correction — `test_oil_waterfall.py`'s thin-pool discriminator fails `all_sorted` when `light_punches_heavy=True` because the mirror's extra pool churn triggers a pre-existing bug (`_is_at_rest`'s own comment, 2026-07-16): a free-surface liquid cell's upward-facing flux lane is permanently re-saturated by `phi_flood`'s seed rule (`P=fill` at any free surface, air above reads `P=0`) regardless of whether the cell is truly still moving, so it can never pass the flux-magnitude rest check buoyancy needs to sink it. Two same-tick geometric exemption attempts (2026-07-16) were already rejected: unconditional (`climb_events=3`) and narrowed to require a lighter-liquid-below condition (`climb_events=17`, counterintuitively worse — a chaotic nonlinear system where narrowing the trigger doesn't narrow the blast radius).

**Diagnosed the specific stuck case first, empirically, before attempting a fix:** a long-run repro (thin-pool waterfall, mirror on, extended from the test's 1500 ticks to 6000) showed the sortedness-violation count oscillating in a band around ~20 indefinitely — 21 at t=1500, 24 at t=2000, 19/18/20/24 at t=3000..6000 — ruling out "just needs more settle time" as the explanation. `_is_at_rest`/flux diagnostics on the stuck cell showed `unchanged_for=0` (content changes every tick from neighbour churn) even while the OWN upward lane stayed pinned (`fy≈-765`, magnitude far over `rest_flux_threshold`) — confirming `stuck_rest_ticks` (the 2026-07-16 fix for a *different* instance of this bug class, a byte-identical frozen film) structurally cannot engage here, because this residue's fill genuinely fluctuates even though it never leaves its voxel.

**Third attempt (rejected):** a NEW temporal signal, distinct from both prior same-tick geometric attempts and from `stuck_rest_ticks` — continuous MATERIAL occupancy of the exact voxel (fill allowed to vary, only the material identity need survive), tracked as a parallel history pass (`surface_stuck_ticks`, alongside `_update_fill_history`). Rationale: a falling/splashing stream cell gets consumed and replaced by different mass within a few ticks (never accumulates N ticks of continuous occupancy at one position); a genuinely stuck residue sits in the same voxel indefinitely regardless of how its fill wobbles tick to tick.

- **First cut (occupancy alone, threshold 12):** fixed the target case cleanly — thin-pool-mirror violations 21→0, held for the full 6000-tick long-run — but cost `climb_events=1` (`worst_climb=2`, first at tick ~82) on the MAIN waterfall (mirror off, the un-related base regime). Raising the threshold to 30 changed nothing: same single climb, same tick, proving it wasn't a timing-sensitivity problem but a structural one — SOME genuinely-settled-looking cell in the main pool's busier neighborhood satisfies 30-tick occupancy while still being part of a real, uncorrected dynamic.
- **Second cut (occupancy + isolation gate, no same-material HORIZ4 neighbour, mirroring the punch's bulk-oil gate):** fixed the main waterfall back to `climb_events=0`, but then FAILED to re-fix the original target case (`all_sorted=False` again, plus a new `water` conservation LEAK not present in either prior variant) — the actual stray thin-pool residue has same-material horizontal neighbours often enough that the isolation requirement excludes it from the exemption too.

Both variants fully reverted (constructor param, parallel history dicts, `_is_at_rest` exemption branch, `step()`'s dispatch gate — see git-free diff via the file's blame if ever tracked; this file is bench-local and untracked). Confirmed clean via `test_momentum_demand.py`: `climb_events=0`, `OVERALL: PASS`, byte-for-byte the same baseline as before this session touched the file.

**Rule to remember:** three independent attempts across two sessions, using three different kinds of signal (two same-tick geometric, one temporal/occupancy-based), have now each perturbed this exact face enough to reopen a climb somewhere else in the chaotic system — even the narrowest, most carefully-scoped one. See the 2026-07-21 investigation below for WHY, and which of the "next directions" turned out to be dead.

### 2026-07-21 (INVESTIGATION — root of the difficulty pinned down; two more levers ruled out, including one this file previously recommended)

After the third rejected attempt, dug into *why* every lever reopens a climb instead of trying a fourth blind. Three empirical findings, each from a targeted diagnostic (all scratch, removed after):

1. **The thin-pool residue is NOT a frozen block — it's a churning quasi-steady-state.** Tracking the actual residue cells over the full 1500-tick run: the pour ends at t=138, but ~20-26 columns always have water sitting on oil at any instant, while individual residue cells slowly drain (a sampled cell went fill 189→155→146→105→83 across t=200..1499, air above / oil below throughout). Mass leaves via slow base-Transport bleed (the only cross-material removal available, since buoyancy is locked out); new water is re-presented above oil elsewhere as the under-mixed pool sloshes. So it is a dynamic equilibrium, not a stuck voxel — which is why `unchanged_for` stays ~0 (fill always wobbling) and `stuck_rest_ticks` can never engage.

2. **The residue's chunks are PERPETUALLY active — the neighbourhood never idles.** `active_chunks` held at 4 (non-zero) at every checkpoint t=200..1499; the residue's own slow churn keeps marking its chunks dirty forever. **This RULES OUT the "activity/scheduler-gated exemption" direction** (the lever that worked for the 2026-07-17 orphan-demand strand) that the entry above suggested as promising — it can never fire here because the sim never reaches the idle state the gate waits for. (Note: this corrects the prior entry; that direction is dead, not untried.)

3. **A fourth lever — substrate quiescence — also fails, exactly like the first three.** Hypothesis (the most promising remaining local signal): the stuck residue sits on SETTLED oil (thin pool, post-pour), while the climb-causing splash sits on CHURNING oil (deep pool, during-pour), so exempt the water's pinned upward lane only when the oil cell directly below has quiet raw flux. Tested via a non-invasive subclass override (source untouched). Result: MAIN waterfall still `climb_events=1` (`worst_climb=2`, tick 88), and the thin pool sorted but stranded 8 demands (`pending=8`). Same failure shape as every prior attempt.

**The actual root of the difficulty (the real deliverable of this investigation):** there is **no local observable that separates the two configurations.** The stuck residue (must-fix) and the transient active-pour splash (must-not-touch) are identical in every locally-measurable quantity — geometry (denser liquid, air above, lighter liquid below), fill dynamics (fluctuating, non-monotone), material occupancy, chunk-active status, and even substrate flux at the moment sampled. They differ ONLY in non-local/temporal context: whether an inflow source is still feeding the connected body. A deep, actively-churning pool *transiently visits* the exact local state the exemption targets — the churn explores the whole configuration space, including momentarily-settled-looking cells — so ANY exemption keyed on local state will, at some tick, fire on a splash cell and let oil climb into it. Four levers (two same-tick geometric, one occupancy-temporal, one substrate-quiescence) have now each produced precisely `climb_events=1-3` for this reason. This is not a tuning problem; it is a structural indistinguishability.

**Where that leaves it — the genuinely-different strategies (none attempted, in rough order of promise):**
- **(A) A non-local "no active inflow" signal.** Gate the exemption on a GLOBAL quiescence measure — e.g. total active-flux magnitude across the body below a threshold, or "no source cell has emitted in the last K ticks" — rather than any per-cell state. This is the only signal that actually tracks the real difference (pour ongoing vs done). Plausible because the deep-pool climbs all happen *during* the pour (high global flux) while the thin-pool residue persists *after* it (low global flux). Risk: the residue's own churn keeps *some* flux alive, so the global threshold must be chosen to sit between "pouring" and "just sloshing" — measure both regimes before picking it.
- **(B) Attack the root in `phi_flood`, not the rest gate.** The upward lane is pinned because phi's seed rule (`P=fill` at any free surface) conflates an air-exposed true surface with an interior point — the *same* conflation behind the OPEN "flat-lake ripple" bug (see this file's phi_flood entries). A correct seed rule would stop pinning the lane in the first place, dissolving this bug and the ripple together. High-value but high-risk: that seed rule has its own history of failed fixes (breaking the U-tube mechanism), so it is a research task, not a patch.
- **(C) Accept it as a tracked limitation.** Treat the thin-pool-with-mirror residue as a known cosmetic artifact: keep the mirror opt-in (already the case) and, for any scene that legitimately needs the mirror, document a `require_sorted=False` / widened-tolerance exception with this entry as justification (the established `oil_tol`/`water_tol` precedent). Cheapest; correct if the mirror stays a bench-only experiment.

### 2026-07-19 (SHIPPED, bench-only, opt-in): light-punches-heavy — the MIRRORED punch, oil punching down into water — plus a real-attribution water-tolerance fix

**What:** the punch mechanic (`_pass_momentum_punch`) previously only fired denser-into-lighter (water punches oil). Added the mirror: a LIGHTER liquid arriving with real downward flux now also punches straight down through BULK DENSER liquid (`light_punches_heavy`, **default False — see correction entry above**). Both directions share the same trigger/bulk-safety machinery; only the RESOLUTION differs, tagged per-demand as `sink: bool`:
- `sink=False` (unchanged) — displaced material is lighter, rises to its local surface, spreads laterally, climbs its own column up when buried. Exactly the validated pre-2026-07-19 behaviour.
- `sink=True` (new) — displaced material is denser, sinks to its local BOTTOM instead (mirror image along Y: `_is_dischargeable_liquid_down`, `_down_column_surface`, spill direction flipped). It can never end up above its own origin, so it is climb-safe by the same construction argument that made the original direction climb-safe — verified directly (see below), not just argued.

Also ported (was previously dead/no-op in the live resolver despite existing as a constructor param): `max_climb_above_origin`/`cap_y`, now actually filters candidates in both directions.

**Validation (three-way):**
1. `test_momentum_demand.py` (the existing climb=0 bar, run at the DEFAULT `light_punches_heavy=False`, i.e. mirror-off — the original regime's own baseline) — `climb_events=0` on both the main and thin-pool waterfalls, matching historical results exactly.
2. New `test_oil_into_water.py` (the mirror's own acceptance test — oil dropped onto a deep water pool with real momentum): `water_climb_events=0`, real penetration (`min_oil_y` well below the pool's original surface — proves an actual punch happened, not just floating), both materials conserved. Control (`light_punches_heavy=False`) correctly shows no penetration.
3. `test_orphan_rescue.py` — unaffected by the new trigger (its own stale assertion needed a separate fix, see below).

**A real regression found and root-caused, not just patched over:** `MOM_DEMAND_thin` failed on the first post-mirror run — water leaked 8.3% of emitted, over the fixed 5% tolerance (previous baseline: 3.4%, comfortably inside). Rather than assume a bug in the new resolution code, it was measured directly: summing `fluid_engine.FluidSim.last_conservation_delta` (the base engine's own self-reported per-tick Transport rounding) across the entire 700-tick thin-pool run accounted for **exactly** 1925 of the 1925 total observed units lost — zero unexplained. This is the SAME phenomenon this file's "RESOLVED (2026-07-13)" entry diagnosed for oil ("pushes make previously-still material move, and moving material pays the already-documented Transport rounding tax") — now also true of water, because the mirror is the first mechanism that ever agitates water this way; water was previously exempt from this tax simply because nothing ever pushed it. Fix: `run_waterfall` gained a `water_tol` parameter (default 0.05, unchanged for every other caller); the thin-pool call passes `water_tol=0.10`, matching how `oil_tol` was already widened for the same reason.

**Rule to remember:** when a mechanism starts agitating a material that was previously calm, its existing tight conservation tolerance may simply no longer apply — measure the base engine's own self-reported delta before assuming the NEW code has a leak. An exact accounting match (0 unexplained) is much stronger evidence than a clean code trace, and is cheap to get (the engine already computes and exposes this number every tick).

### 2026-07-19 (STRUCTURAL FIX): the bench now MODELS the GPU resolver pipeline instead of paraphrasing it — closing the class of bug that made four separate GPU defects invisible to a green suite

**Motivation (user's call, before building the mirrored punch):** every bench→engine divergence this week was caught only by in-editor testing, never by the suite. Adding a new mechanism (oil-punches-into-water) on top of the old bench would just manufacture defect #5. So the partnership was fixed first.

**The structural root cause** (audit item 5, the one that could never be tested): the bench resolved each queued demand **sequentially and independently**, each seeing the previous one's writes. The GPU runs **one invocation per queue entry against a snapshot**, merges them all into a shared `demand_accum`, and applies in a **second pass**. Those are different algorithms, so a green bench proved nothing about the merge path — precisely where the >255 merged-excess truncation and the excess-requeue churn lived.

**What changed:** `momentum_demand.py`'s `_drain_demands` is now a 1:1 model of `momentum_resolve.comp`:
- **pass 0 (walk)** — one pass per queue entry, all reading the same pre-pass world state, none seeing another's deposits; each finds a seed and *accumulates* into shared `demand_accum` via `_gpu_accumulate` (which reserves the `touched_cells` slot **before** adding, mirroring the 2026-07-16 reserve-before-mutate fix).
- **pass 1 (apply)** — one pass per touched-cell *entry* (duplicates allowed, exactly like the GPU); takes the total with read-and-zero semantics (models `atomicExchange`), deposits `min(total, headroom)`, requeues the excess **from that cell**.
- **carry** — the requeue buffer becomes the next substep's queue.
- **capacities modelled, not just documented**: `MAX_PUNCH_DEMAND_ENTRIES = 262144` bounds both `touched_cells` and `demand_requeue`, so capacity-exhaustion bugs are now reproducible in-bench rather than GPU-only.
- **`WALK_CAP` aligned 512 → 64**, the engine's shipped `punch_walk_cap` default. The bench was searching 8× wider than the engine actually does, so "the walk finds X" could be true in-bench and false on GPU.

**Divergences this closes** (from the audit entry below): #3 requeue-from-seed, #4 candidate scope / visited handling, #5 demand merging, plus the walk-budget half of #2. **Still open:** #1 (`max_climb_above_origin`/`cap_y` has no GLSL equivalent — inert while disabled, but it is the anti-climb safety valve; port it or delete the bench knob before anyone relies on it).

**Rule to remember:** a reference implementation earns its authority only by being a *transcription* of the thing it validates, not a re-derivation of the same design. Where the GPU must genuinely differ (parallel merging, fixed-size buffers, bounded local arrays), model those constraints in the reference too — otherwise the reference is silently testing an easier problem, and every "bench green / editor broken" round trip costs a full debugging session.

### 2026-07-19 (AUDIT): `momentum_resolve.comp` vs `momentum_demand.py::_resolve_demand` — systematic diff after four "the port silently weakened the bench behaviour" bugs

**Why:** four separate bugs this week all had the same shape — the GPU port quietly did something weaker than the bench, so the bench stayed green while the shader misbehaved in-editor (8-bit amount truncation; capacity-gated bookkeeping ×2; "distribute across candidates" collapsed to "dump at one cell"). Rather than wait for symptom #5, both implementations were read side by side. Findings, highest risk first:

1. **`max_climb_above_origin` / `cap_y` has NO GLSL equivalent.** The bench filters every candidate by `cap_y = origin.y + max_climb_above_origin` (and applies it to the one-step fallback rise); the shader has no such clamp. **Currently inert** — the shipped config is `max_climb_above_origin = -1` (disabled) — but this is precisely the anti-climb safety valve, so if anyone ever enables it in the bench to fix a climb regression, the GPU will silently ignore it and the bench result won't transfer. Either port it or delete the bench knob.
2. **Walk budget differs 8×:** bench `WALK_CAP = 512`, shader `params.walk_cap` default **64** (`WALK_CAP_MAX = 128`). The shader therefore reaches far fewer candidates than the validated bench for the same scene. Known/documented, and much less critical now that the deposit spreads instead of depositing one cell per pass — but any bench claim of the form "the walk finds X" is not automatically true on GPU.
3. **Requeue origin differs.** Bench requeues the remainder from **`origin`**; the shader (post-2026-07-18) requeues from the **seed** (a surface cell). The shader's choice is deliberate and better — it continues the spread from the surface instead of restarting at a buried origin — but the two are now behaviourally different and the bench is the weaker one. Align by teaching the bench the same rule.
4. **Candidate scope / visited handling.** Bench collects candidates during the *origin* BFS (plus the surf BFS when buried), sorts them all together by min-Y, and shares one `visited` set across both walks. The shader picks a single min-Y `best_cell` and then runs a **second** BFS from it with `visited` **reset to empty**. Similar in effect, not identical: the shader can re-walk cells the first pass already covered, and its deposit neighbourhood is centred on the best cell rather than the global candidate set.
5. **GPU-only demand merging has no bench analogue (architectural).** `accumulate_at` sums multiple demands into `demand_accum[cell]`, and the apply pass deposits `min(total, headroom)` then requeues the excess *from that cell*. The bench resolves each demand independently and sequentially, so amounts never merge. This asymmetry is the direct cause of two shipped bugs (the >255 merged excess that the 8-bit decode truncated, and the excess-requeue churn) and it means **no bench test can ever exercise the merge path**. Any future change to accumulate/apply must be reasoned about directly, not validated by proxy.

**Equivalent-and-fine (checked, no action):** the dischargeable test and its `rest_tol` (`max(1, settle_threshold-1)`) match; the bubble landing is absent from the shader but `bubble_mode="off"` is the shipped bench config; `fallback_air_rise=False` is hardcoded in the shader to match; the down-probe's trigger (`tail == 1` vs `not frontier`) is the same condition; the amount decode is now full-width on both sides.

**Rule to remember:** a CPU reference implementation only validates a GPU port to the extent the port is a faithful transcription. Where the GPU *must* differ (parallel merging, fixed-size buffers, bounded local arrays), that difference is un-testable by the reference and needs its own reasoning and its own in-engine instrumentation — which is what the F6 `[PunchQueue]` dump now provides.

### 2026-07-18 (GPU-only throughput bug — the remaining "never settles"): the resolver dumped a whole demand at ONE cell, and min-Y deliberately picks the cell with the LEAST headroom

**Context:** after the rounding revert, in-editor conservation improved a lot (world 1,367,089 + queue 148,788 = 1,515,877 of 1,539,435 → **1.5% loss, down from 4.7%**), but the queue still stalled at ~583 voxels, oil `max_y` sat at 12 (BELOW the starting 13), and chunks stayed active. The stranded origin `(-1,11,-20)` was only ONE cell below the surface — so the ordinary BFS *did* find a landing (`best_valid=true`) and the up-column rescue never even ran. The bug was in the normal path.

**Root cause (two compounding halves):**
1. `accumulate_at(best_pos, mat, amt)` dumped the **entire** demand (148,788) at a **single** cell. The apply pass clamps to that cell's real headroom and requeues the rest — so only one cell's worth moves per pass no matter how much is queued.
2. min-Y deliberately selects the **lowest** landing. For a settled surface that is a *partial-fill oil cell* (`land = pos` when `fill < 255`), and churn leaves those at **fill 253–254** → headroom **1–2**. The high-capacity option (the air cell above a *full* surface cell, headroom 255) is one y higher, so min-Y systematically rejects it.

Combined: ~2 fill moved per pass, the chunk re-dirtied every tick, and 148,788 fill needed ~74,000 passes. That is the in-editor "oil keeps twitching, never settles, queue stuck".

**Why the bench never showed it:** the bench's deposit loop iterates *all* candidates and `_write_at` places `min(amt, headroom)`, carrying the remainder to the **next** candidate — i.e. it always spread across many cells with exact headroom. The GPU port collapsed that to a single `accumulate_at`. Another instance of the recurring family: *the GLSL port silently weakened a behaviour the bench relies on, so the bench validated something the shader wasn't doing.*

**Fix:** one **unified deposit spread** used by BOTH paths (normal min-Y result and up-column rescue). The walk now records `best_cell` (the walkable OIL cell) alongside `best_pos`; that cell — or the up-probe's surface cell when the walk found nothing — seeds a bounded lateral BFS that deposits **headroom-exact** amounts (`min(left, FILL_CAP - fill)`, or a full 255 into an air landing) at each surface cell until the demand is spent, requeuing any remainder **from the seed** (a surface cell) rather than a buried origin. Shipped in `shaders/momentum_resolve.comp` only — the bench already behaved this way.

**Rule to remember:** when porting a CPU resolver that distributes a quantity across many targets, check that the GPU version still *distributes*. Collapsing "fill candidates until exhausted" into "dump it all at the best one and let the requeue sort it out" looks equivalent on paper but silently becomes O(1 cell/tick) throughput — and pairs catastrophically with any selection rule (like min-Y) that prefers low-capacity targets.

### 2026-07-18 (OPEN, attribution measured): the plunge LOOKS wrong — displaced oil arrives as a mound long after the water lands, and chunks never go idle. Two separate causes isolated.

**Context:** with conservation fixed (queue drains, oil `max_y` rises 13→14, `|flux|=0`), the in-editor plunge still looks wrong: oil appears at the top well after the water has settled, "twitches" for ~30 s, and chunks stay active far longer than they should. User's framing: *we solved the disappearing oil; now we need to fix WHEN and WHERE it goes back.* Correct behaviour would be the level rising **as** the water sinks (same tick, or 1-3 after).

**Attribution (bench plunge, 13×13×14 oil pool, 5×5×4 water block; oil `max_y` and active-chunk count sampled per tick):**

| config | t10 | t40 | t90 | t130 | active chunks |
|---|---|---|---|---|---|
| punch ON (default) | **19** | 18 | 16 | 15 | 12 → 8, **never 0** |
| punch OFF (`punch_threshold=1e9`) | 15 | 15 | 15 | 15 | 8–12, **never 0** |
| punch + buoyancy OFF | 14 | 14 | 14 | 14 | 4 → **0 by t90** |

Correct final level is 15 (water volume ÷ footprint). Two independent findings:

1. **The punch creates the mound.** With it on the level overshoots to 19 (+4) and takes ~130 ticks to decay back; with it off the level lands on 15 almost immediately and stays. So the visible artifact is the punch's *redistribution*, not base splash physics.
2. **Buoyancy is what prevents idle.** Active chunks never reach 0 with buoyancy on (punch on *or* off), but drop to 0 by t90 with it off. This is a distinct bug from the mound and is likely a large share of the "30 s of twitching / chunks active forever".

**Why the mound happens (design tradeoff, not an oversight):** each punch hop removes an oil cell, advances water into it, and vacates the water's old cell to AIR. Physically that oil should fill *the void the water just left* — a one-cell local exchange (the user's own description). But the resolver deliberately routes it to a distant min-Y surface instead, because depositing into the vacated cell inside the water column is the documented **chimney seed** (more falling water re-punches it and ratchets it upward — this is exactly why `force_exchange` was rejected and `fallback_air_rise=False`). Chimney-safe routing is what buys the mound.

**Options (not yet chosen):** (a) local exchange into the vacated cell **gated on no descending stream above** (`_stream_descending()` already exists for this test) — most physical, needs careful waterfall validation; (b) tame the punch (`punch_threshold` ↑ / `max_reach` ↓) so it displaces less — cheap and keeps all guarantees, weakens momentum grading; (c) fix buoyancy's never-idle behaviour first — it is unambiguously a bug rather than a tradeoff, and is independent of the mound.

**Also fixed here:** F6 and M (AutoF6) had drifted — M was missing the `[PunchQueue]` line, i.e. the one per-tick signal needed to watch mass being queued/drained during a plunge. Both now call a single `world.gd::_dump_fluid_debug()`.

**TRIED and REVERTED (no-op):** routing displaced oil by seeding the resolver's BFS at the origin's local surface (`_up_column_surface`) *before* the normal walk. Bit-identical results — the seed is not the policy; the deposit loop sorts candidates by min-Y, so the lowest cell wins regardless of where the walk started. Changing where displaced mass lands requires changing the **selection (the sort)**, not the seed. Signpost comment left in `_resolve_demand` so this isn't retried.

### 2026-07-18 (the up-column probe, take 2 — the idle gate + single-cell drain were wrong; UN-GATED + LATERAL-SPREAD is the fix): the in-editor strand still didn't drain and the sim "never settled"

**Context:** the first up-column probe (idle-rescue-gated, single-cell deposit) was bench-green but FAILED in-editor: KEY_L still showed `[PunchQueue] count=1, queued_fill≈264k` and the active-chunk tint flashed forever ("never settles"). Two independent flaws:

1. **Idle-gating defeated in-editor.** The probe only ran when `params.rescue==1`, set only by `_rescue_punch_backlog()` when the active set is empty. But a large pool with mass in flight rarely reaches that clean-idle state (the punch churn keeps chunks active), so the probe almost never fired and the strand never drained. Worse, the `has_work()`-counts-the-backlog change kept the sim awake while the queue was non-empty, and the idle-rescue re-activated a chunk on each tiny deposit — a perpetual wake/settle/wake oscillation, which is exactly the "flashing, never settles" the user saw. (Ruled out the per-face rounding regression as the cause: a bench pool settles cleanly to `|flux|≈8, active=0` even under new rounding.)
2. **Single-cell drain far too slow.** Even when it fired, the GLSL walk deposits into ONE cell per demand per pass (255/tick). A ~1000-voxel strand would take ~1000 ticks (~17 s) — visually "never settling" even while technically draining.

**Fix (bench-validated):** make the up-column probe **UN-GATED** and **LATERAL-SPREAD**.
- **Un-gated:** it fires only when the min-Y BFS found NO dischargeable surface — i.e. a *deeply buried* origin, which only occurs in a large/deep pool. A waterfall pool is shallow, so displaced oil is always within `walk_cap` of its surface and the probe never fires there — proven un-gated: `run_waterfall` on OLD rounding gives `climb_events=0, worst_climb=0`, bit-identical to green. So it needs no idle gate (the down-probe for AIR-orphaned origins still does — that one drops mid-air debris that can chimney onto a live stream; the up-probe deposits at the local oil surface of the same body). Un-gating lets it drain during *normal active resolve*, which is essential since the pool may never reach full idle.
- **Lateral-spread:** climb the origin's column to the local surface, then run a bounded BFS *across* the surface depositing ~one cell's worth at each surface landing (air above full oil, or a partial-fill surface cell) until the demand is spent — raising the pool level a layer per pass instead of stacking one column (which overflows the container) or dripping 255/tick. Bench: the buried strand drains `7641/7650` in **46 ticks with the idle-rescue entirely OFF** (vs. permanently stranded without the probe).

Shipped: bench `momentum_demand.py::_resolve_demand` (up-probe gate changed from `self._probe_now and not candidates` to just `not candidates`; two-pass `_bfs` already spreads laterally) and GLSL `momentum_resolve.comp` walk pass (up-probe moved AFTER the `best_valid` return, un-gated, with a fresh lateral BFS from the surface accumulating at every surface landing until `amt` is spent, requeuing any remainder from the surface). In-editor verification pending: KEY_L → expect `[PunchQueue] count=0` and the tint to settle within a second or two of the plunge finishing.

**Rule to remember:** "gate the rescue on the scheduler being idle" is attractive but fragile — an idle state that a large, busy scene never reaches means the rescue never runs. Prefer a *trigger condition that is itself safe* (here: "the BFS found no surface" only happens for deep burial, which the chimney-prone shallow scenes never produce) over gating on a global quiescence that may not occur. And a background drain must be fast enough to finish inside the work's natural active window, or the keep-awake machinery turns into a visible never-settles oscillation.

**THIRD correction (2026-07-18) — the climb's "surface" test was wrong: partial fill ≠ surface.** The un-gated lateral-spread probe *still* made no progress in-editor (`[Rescue] fired but made NO progress`, queue holding ~280k across 3 entries). Cause: the column climb stopped at the first cell with `fill < FILL_CAP`, treating any partial-fill cell as "the local surface". But the stranded origins read `mat=7 fill=254` — partial from ordinary churn while **still buried under packed oil**. So the climb terminated at the origin itself, the lateral spread then ran from a buried cell where nothing is dischargeable, and the demand requeued forever. **Fix:** a cell is the local surface ONLY if the cell directly above it is AIR; a partial-fill cell with same-material above is still buried, so keep climbing. (Also: seed the lateral BFS with the surface *oil* cell, not the air above it — the BFS walks same-material cells and computes the landing itself.) **Why the bench missed it:** bench pools are pristine 255-fill, so injected origins were always full and the premature `fill < 255` branch never fired; in-editor, churn leaves cells at 254 constantly. Regression added: a buried-origin test whose origin cell is explicitly set to fill 254.

**Better acceptance signal than "does the queue drain" (user's observation):** after a body of liquid is added to a pool, **the pool's `max_y` must RISE, not fall.** The in-editor dumps showed oil `max_y` going 13 → 11 — the level *dropped* while 1100 voxels sat in the queue. That single number catches the whole class of "displaced mass never made it back into the world" bugs, and it is visible in the ordinary F6 dump without any queue instrumentation. Prefer it as the primary in-editor check for displacement correctness.

### 2026-07-17 (FIXED — the root of the non-deterministic "walking origin" and unreliable DebugSnapshot): a mid-step flux-chunk-list realloc silently invalidated the cached uniform set, skipping whole dispatches

**Context:** the in-editor submerged-sphere debugging kept producing non-reproducible results — the stranded punch demand's origin "walked around" between otherwise-identical runs, and DebugSnapshot save/restore didn't replay deterministically. A stray engine error surfaced the cause: `Storage buffer supplied (binding: 5) is invalid. Parameter "buffer" is null.` at `fluid_simulation.gd` step()'s PhiFloodStep dispatch, followed by `uniform_set_create returned an invalid set; skipping dispatch`.

**Root cause:** `step()` builds the flux uniform set once up front (`flux_uniforms := _build_flux_uniforms()`), then calls `_upload_flux_chunk_list()` several times (for the phi list, then the flux list). `_upload_flux_chunk_list()` FREES and RECREATES `_flux_chunk_list_buf` (a NEW RID) whenever the list exceeds the current capacity (initial 256). `compute_helper.run()` builds its `uniform_set` from the RIDs in the uniforms array at dispatch time — so a realloc between building `flux_uniforms` and a later `run()` leaves binding 5 pointing at a FREED RID. `uniform_set_create` then returns invalid and the ENTIRE dispatch is silently skipped. Whichever pass came after the realloc (Phi, Accelerate, Transport, fill-history, buoyancy, or the punch pass) just didn't run that tick — so the sim's trajectory depended on chunk counts and capacity-growth timing, i.e. was non-deterministic, and any partially-skipped Transport/resolve left demands in inconsistent states. It only bit once scenes got large enough to exceed 256 chunks in the dispatch list (the 17×17×20 submerged-sphere pool allocates ~300 pages), which is exactly when this debugging started.

**Fix:** pre-grow the chunk-list buffer to the largest list this step (`max(flux_count, phi_count)`; phi_list ⊇ flux_list) BEFORE building the uniform set, via a new `_ensure_flux_chunk_list_capacity()` split out of `_upload_flux_chunk_list()`. With capacity guaranteed sufficient up front, no realloc happens mid-step, so the cached RIDs stay valid for every dispatch. (Pre-existing latent bug, not introduced by the momentum/buoyancy work — but it invalidated all the in-editor measurements taken while it was active, including the `punch_walk_cap` 64/256/512 comparison below, which must be re-run.)

**Rule to remember:** any GPU buffer referenced by a uniform set that is (re)built once per frame must not be freed/reallocated between that build and the last dispatch using it. Either size it up front for the whole frame, or rebuild the uniform array after every possible realloc. A "skipping dispatch" warning is not benign — it silently drops physics and manifests as non-determinism, not a hard failure.

### 2026-07-18 (RESOLVED — REVERTED): the "Round PER-FACE" Transport change was the root cause of the never-settling fluid AND the mass loss. Four measured regressions, zero measured benefit.

**Decisive measurement** (bench plunge: 13×13×14 oil pool + 5×5×4 water block, 400 ticks — the key ingredient is a **water/oil interface**, which buoyancy creates once it sorts the water to the bottom):

| | active chunks | conservation delta / tick | total mass |
|---|---|---|---|
| NEW per-face rounding | **8 — never idles** | **≈ −150 every tick, forever** | **−6.56%** |
| OLD sum-then-round | **0 — fully settles** | **0** | **−0.35%** |

Plus the previously-logged `climb_events` 0 → 4 on the waterfall bar. So the change:
1. broke the waterfall acceptance bar,
2. made mass loss **19× worse** — the exact metric it was introduced to improve,
3. made a cross-material interface churn **forever** (conservation delta never reaches 0),
4. kept chunks permanently active — the user's in-editor report of fluid "twitching for ~30 s" with chunks active long after the water landed.

**Mechanism:** rounding each face independently manufactures a ±1 quantum on every face whose true transfer is fractional. A cell with several small simultaneous flows (exactly a settled liquid–liquid interface) then jitters forever instead of netting to zero — so it never goes quiet and bleeds fill every tick. Summing the six faces first lets those fractional flows cancel, and the cell settles. The per-face symmetry argument (`round(−X) == −round(X)` per face) is true in isolation but is not what the engine's conservation actually rests on.

**Reverted** in both `shaders/fluid_flux.comp` (Transport) and `tools/fluid_prototypes/python/fluid_engine.py::_pass_transport`.

**Investigation trap worth remembering:** an earlier check "does a pool settle under new rounding?" said YES and wrongly exonerated the change — because it used a **pure single-material pool with no interface**. The bug only appears where two liquids meet. When testing a fluid-settling hypothesis, the scene MUST contain the material interface the real case has, or a passing result means nothing.

### 2026-07-17 (THE ACTUAL DOMINANT LEAK — third instance in the same pipeline): requeued demand amounts were packed full-width but decoded through an 8-bit mask

**Context:** in-editor re-test of the submerged-sphere rig (KEY_L) on the build with both 2026-07-16 reserve-before-mutate fixes in: **loss unchanged** — total fill 1,539,435 → 1,183,644 settled (~23.1%), the *bit-for-bit identical* end total as the pre-fix run. Water conserved (+0.12%) and fully sorted to the pool floor; the loss is all oil (1,473,900 → 1,118,028, −24.1%), concentrated in the plunge phase. Identical deterministic totals across builds meant the two capacity-path fixes never actually engaged in this scene — the dominant leak was somewhere that fires unconditionally, in proportion to churn.

**Root cause (found by direct audit of `momentum_resolve.comp` for representation mismatches):** the apply pass MERGES every demand landing on the same cell into one accumulated total (`demand_accum`), deposits `min(total, headroom)`, and requeues the overflow packed full-width: `mat | (excess << 8)`. In a fully-packed pool, many displaced-oil demands route to the same few lowest surface cells (min-Y selection), so `excess` routinely exceeds 255. But the walk pass decoded every queue entry with `amt = (packed >> 8u) & 0xFFu` — truncating each requeued excess to its low 8 bits on the very next substep (700 → 188: 512 fill destroyed, per entry, per substep, for as long as the plunge churns). Fully deterministic, churn-proportional, invisible at bench scale: **the bench cannot express this bug at all** — it never merges demands into a single total, so no bench amount ever exceeds 255 and no 8-bit assumption is ever violated there. A second, smaller drop found in the same audit: `accumulate_at()`'s `flat_idx < 0` requeue path wrote `int(mat)` with no amount packed at all — the entry re-read as `amt=0` next substep and was discarded by the walk's early-out (a "requeue" that silently dropped the whole demand).

**Fix:** decode the amount full-width (`amt = uint(packed) >> 8u` — fresh punch entries still carry ≤255, requeued merged excesses now round-trip exactly), and pack the amount into the `flat_idx < 0` requeue path. Both in `shaders/momentum_resolve.comp` only; no GDScript or bench change needed (the bench's tuples are unbounded ints, already the semantics the decode now matches).

**Diagnostic added alongside (F6):** `FluidSimulation.debug_dump_punch_queue()` — prints the punch demand queue's standing count and total queued fill per material. F6's fluid stats only count WORLD fill; mass sitting in unresolved/requeued demands is invisible to them (the bench's conservation checks add `pending_demands` for exactly this reason). After a settle, a large standing `queued_fill` = stranded backlog (walk starvation — raise `WALK_CAP` per the file-header note), while a nonzero *permanent* loss with an empty queue = a real destruction path still live.

**Rule to remember (extends the pipeline's two 2026-07-16 rules):** when a GPU port packs a quantity into bitfields, audit every *decode* site against every *encode* site's actual range — especially where the pipeline can MERGE values before re-encoding (sums outgrow the field a single producer respects). "Encode full-width, decode masked" is silent, deterministic destruction that no small-scale test catches, because small scenes never produce merged values past the mask.

### 2026-07-16 (PARTIAL FIX — see the follow-up entry immediately below for the actual second leak): punch's demand-queue entry was capacity-gated but the changelog mutation that erases the oil was not

**Context:** the mass-loss investigation below (designated_liquid revert) isolated the leak conclusively via direct A/B: same scene, same snapshot — buoyancy-only lost ~1.0% (normal churn tax), punch-only lost ~20.2%. The leak is specifically in the momentum punch, not ownership arbitration, not buoyancy, not base Transport.

**Root cause, found by direct code reading (`fluid_flux.comp` pass 9, `MomentumPunch`):** each punch hop writes TWO things — a `changelog` entry (the only thing that actually mutates `voxels_a`: water advances into the oil cell, the oil cell's old contents are overwritten) and a `punch_demand_queue` entry (the only record of what that displaced oil was and where `momentum_resolve.comp` should route it). The changelog write was unconditional (gated only by `MAX_CHANGELOG=524288`, a capacity so large relative to actual usage it never binds). The demand-queue write was gated by `MAX_PUNCH_DEMAND_ENTRIES=65536`. Once the queue count reached capacity, new entries were silently dropped — but the changelog mutation had **already happened**, so the displaced oil's fill was erased from the world with no record anywhere to restore it. A second factor compounds this: `punch_demand_queue.count` is never reset between ticks (`_resolve_punch_demands`'s own comment confirms this — leftover requeued entries seed the count, and each tick's fresh punch activity `atomicAdd`s more on top), and `momentum_resolve.comp`'s `WALK_CAP=64` is far smaller than the Python bench's own `WALK_CAP=512` (a difference flagged as a likely gap when this was first ported, never actually stress-tested until now) — meaning on a large, sustained scene, resolution can chronically lag generation, letting the backlog grow past 65536 over time even if no single tick's fresh demand volume is that large.

**Fix:** reserve the demand-queue slot *before* writing the changelog, and skip the entire mutation for that hop if the queue is full — `break` out of the punch loop for that cell rather than truncating the record of an already-applied mutation. If the queue's full, that water cell simply doesn't punch again until next tick; nothing is created or destroyed either way, regardless of what's driving the backlog. Shipped in `shaders/fluid_flux.comp` only — the Python bench's `pending_demands` is a plain unbounded list, structurally incapable of this exact bug, which is precisely why the bench validated cleanly while the GLSL port had a real, serious leak (`tools/fluid_prototypes/python/momentum_demand.py` gets an explanatory comment only, no functional change).

**Why the bench never caught this:** every bench acceptance scene (waterfall, thin-pool, sealed column, submerged body) tops out at a few hundred to low-thousand liquid voxels. The leak only manifests once genuine per-tick punch demand volume, compounded by resolution lag, exceeds the GLSL port's fixed 65536-entry buffer — a scale no bench scenario, and apparently no earlier in-editor test either, ever exercised. The bug was invisible until a deliberately large (6000+ liquid voxel) submerged-body test rig was built specifically to chase a *different* bug (the stuck-water investigation).

**Still open, lower priority:** the underlying resolution-rate gap (`WALK_CAP=64` vs. bench's `512`) that lets the backlog grow in the first place. The conservation fix above makes this safe (no more mass loss) but doesn't address it directly — under sustained heavy load, punches may now simply stop firing (deferred, not lost) once the queue saturates, which could read as "punch feels sluggish/unresponsive" in a very large or very active scene. Worth revisiting if that's observed; not urgent since correctness no longer depends on it.

**Rule to remember:** when a GPU port bounds an unbounded bench/CPU data structure with a fixed-size buffer, always check whether *every* write path that depends on "did this reservation succeed" is actually gated consistently — a mutation that happens unconditionally while its own bookkeeping record is conditional is a silent, scale-dependent leak that no small-scale test will ever surface.

### 2026-07-16 (RESOLVED, immediately after the entry above): the SAME bug class, a second time — `accumulate_at()`'s `touched_cells` registration

**Context:** re-tested in-editor after the punch-pass fix above (queue slot reserved before the changelog write). The loss was still there, essentially unchanged (~18.4% this run vs. ~18.3%/20.2% before) — the punch-pass fix was necessary but not sufficient; there was a second leak in the same pipeline.

**Root cause:** `momentum_resolve.comp::accumulate_at()` (called from the walk pass once a landing candidate is found) added the demanded amount to `demand_accum.data[flat_idx]` **unconditionally**, then only registered that cell in `touched_cells` if there was room (`if (slot < MAX_PUNCH_DEMAND_ENTRIES)`, deduplicated via a `prev==0` race so each distinct cell registers once). The apply pass (pass 1) is dispatched entirely over `touched_cells.count` — it never scans `demand_accum` directly. So if `touched_cells` filled up, the registration silently failed while the amount had *already* been added to `demand_accum` — that accumulated demand became permanently unreachable, sitting in a buffer nothing would ever read again. Exact same bug class as the punch-pass leak (a mutation/side-effect committed unconditionally while its own bookkeeping record was conditional), just one step further down the same pipeline, in a buffer my first fix never touched.

**Fix:** reserve the `touched_cells` slot *before* adding to `demand_accum`; if the reservation fails, requeue the demand (via `demand_requeue`, the existing carry-forward path) instead of losing it. Dropped the `prev==0` dedup in the process — every `accumulate_at()` call now reserves its own slot, so a given cell can get multiple `touched_cells` entries if several demands land there. This is safe, not a new bug: the apply pass's `atomicExchange(...,0u)` read-and-reset means the first entry for a cell reads the true accumulated total and zeroes it; any duplicate entries for the same cell then read `0` and no-op immediately (`if (total == 0u) return;`). Trades a little redundant GPU work for a hard guarantee that a successfully-reserved accumulation is never silently orphaned.

**Also raised `MAX_PUNCH_DEMAND_ENTRIES` 65536 → 262144** across all three buffers (`fluid_flux.comp`, `momentum_resolve.comp`, `fluid_simulation.gd`) as pragmatic headroom on top of both correctness fixes — confirmed in-editor that a single large (6000+ liquid voxel), heavily-punching scene can generate/backlog demand volume well past the original capacity. This is not a substitute for the reserve-before-mutate fixes (a bigger fixed capacity just moves the ceiling, it doesn't remove it), but reduces how often either safety valve actually needs to engage in practice.

**Status:** shipped, awaiting in-editor re-confirmation (this was the second of two leaks found in the same debugging session; the user's re-test after the first fix alone is what surfaced this one).

**Rule to remember (reinforcing the one above):** finding one instance of "unconditional mutation + conditional bookkeeping" in a pipeline is a strong signal to audit every OTHER buffer in the same pipeline for the identical pattern, not just the one that happened to be found first — this bug class tends to repeat within a single demand-queue/multi-buffer resolver, since it's usually a copy-pasted structural pattern (accumulate → conditionally record → apply-reads-only-the-record), not a one-off typo.

### 2026-07-16 (RESOLVED, later the same day, SEE REVERT ABOVE): the real root cause of the whole-submerged-body stall — `designated_liquid()`'s tie-break can permanently starve a minority liquid, not just intermittently

**Context:** in-editor investigation of the submerged-water-stall bug (previous 2026-07-16 entry), using the new `KEY_X`/`KEY_C`/`KEY_L` debug tools. Systematic F7 sampling found a water voxel resting directly on an air cell that *also* touched 2-3 oil neighbours. Critically, watching the water's own face (the §3.2 pin, already understood) is a DIFFERENT lane from the one that actually governs whether the water can transport into the air below it — that's the **air cell's own face**. Watching that directly showed `flux=(0,0,0)` — completely flat — for hundreds of consecutive ticks, while unrelated nearby faces on the same air cell showed real nonzero values in the same tick. Not slow, not intermittently blocked: permanently zero.

**Root cause:** `designated_liquid()` (both `fluid_engine.py` and `fluid_flux.comp`) picks which single liquid an air cell's flux is computed against this tick by scanning its 6 neighbours in a fixed axis order and returning the first liquid match — every other liquid's face into that air cell gets hard-zeroed (`flux_buf.data[lane] = 0`), by design, to keep Transport's single unlabeled delta from silently crediting the wrong material. A prior fix (2026-07-10) alternates between exactly 2 scan orderings (forward / reverse) by frame parity, specifically to stop a single fixed order from starving a minority liquid forever. That fix is insufficient: if a competing liquid occupies a neighbour slot that's checked *before* the minority liquid's slot in **both** orderings (provable directly from the two fixed orderings — e.g. oil at `-X` beats water at `+Y` in forward order since `-X` is checked first, and oil at `-Y` beats water at `+Y` in reverse order since `-Y` is checked first — a single liquid occupying both `-X` and `-Y`, or equivalent combinations, wins every tick regardless of frame parity), the minority liquid can be excluded **permanently**, not just blocked every other tick. With 2-3 oil neighbours on a real contested air pocket, this is easy to hit by chance.

**Fix:** rotate the scan **start position** by `frame % 6` instead of just flipping forward/reverse (2 states). This guarantees every occupied neighbour direction is checked first — and therefore wins — at least once every 6 ticks, regardless of how many other directions are also occupied by a competing liquid. A hard fairness bound, not a probabilistic improvement, and still fully deterministic/snapshot-only (pure function of `gpos`/`frame`, no new persistent state, same design constraint the function already had). A losing material is now blocked at most 5 consecutive ticks, never permanently. Shipped in both `tools/fluid_prototypes/python/fluid_engine.py::_designated_liquid` (bench-validated first) and `shaders/fluid_flux.comp::designated_liquid()`.

**Validation:** full `test_momentum_demand.py` suite PASS (`climb_events=0`, thin-pool, sealed column, momentum grading all intact), `test_stuck_film.py` PASS (control still reproduces, fix still sorts), and the baseline `run_tests.py` regression suite unchanged (flat lake settles, falling block conserves; the U-tube "FAIL" is the documented-expected behaviour for the raw `FluidSim` base class without the phi correction, unrelated to this change). A targeted synthetic bench repro of the exact starvation geometry was attempted and abandoned as unreliable: placing a single solid oil voxel next to an air cell causes it to immediately expand into that air via completely ordinary same-material lateral spread (any liquid adjacent to empty air has *some* driving force into it), collapsing the "persisting contested air cell" setup within the first tick regardless of the ownership fix — a real persisting contested air pocket apparently requires the surrounding liquids to already have low net driving force from every direction simultaneously (as in the actual in-editor case, where one contested neighbour had fill=98, not 255), which isn't easy to construct by hand. The fix's correctness rests on the direct code-level proof (any occupied slot gets a guaranteed win within 6 ticks) rather than an isolated repro; the full regression suite is the safety net.

**Rule to remember:** when a same-tick "who owns this contested resource" tie-break only alternates between a *small, fixed number* of orderings (here: 2), always check whether a candidate can occupy enough of the higher-priority slots to win in *every* available ordering, not just one — a fix that reduces starvation from "always" to "most of the time" can still leave a permanent-starvation case if the number of alternated states is smaller than the number of contestants it needs to be fair against.

### 2026-07-16: buoyancy's rest gate could permanently lock out its own use case (water stuck on a thin oil surface, GLSL `buoy_at_rest()` + bench `momentum_demand.py::_is_at_rest`)

**Context:** in-editor report — a small water sphere dropped onto a settled water/oil pool left a residual patch of water sitting visibly on top of the oil indefinitely (FluidWatch: `fy` pinned at the Y-axis clamp ceiling, `FILL_CAP*gravity_bias`, for 100+ ticks straight, fill never changing). Not a waterfall/continuous-pour scene — a one-shot drop into an otherwise-quiet pool, so there was no ongoing churn to blame; the water should reach true rest and sort.

**Root cause:** `buoy_at_rest()`/`_is_at_rest()` requires every face's flux magnitude to be under `buoy_rest_flux`. But Accelerate recomputes a liquid's downward face fresh every tick from the hydrostatic head difference — for a liquid resting directly on a lighter, different liquid, Transport can never actually move any mass across that interface (cross-material fill transfer only happens via buoyancy/punch, never ordinary same-material Transport), so that face's flux has no mechanism to ever decay. It sits pinned at the axis cap forever, permanently failing the rest check for the very cell buoyancy's swap exists to fix — buoyancy locked out of its own use case by construction, not by some external disturbance.

**First fix attempt (2026-07-15) and REJECTED:** widening the momentum punch's bulk check (which requires same-material liquid beneath the target) to also accept solid ground beneath a thin puddle. Bench-caught before shipping: once punch fires across an entire single-layer pool, the last displaced oil cell can end up with zero same-material neighbours left anywhere nearby, and the demand resolver's walk-then-one-step-rise fallback has no candidate to land on — the demand requeues forever (`pending=1`, never resolves). Reverted; the original bulk check is correct as-is (buoyancy already sorts a flat single-layer interface fine on its own — confirmed via `run_waterfall(..., pool_depth=1)`, `pending=0`).

**Actual fix:** a density-aware exemption in the rest gate itself, not the punch. For the Y-axis face specifically, if the OTHER side of that face is a different liquid whose density puts it on the correct side of a legitimate buoyancy swap (denser resting on lighter, checked symmetrically from both cells' own perspective — the "own" face toward above, and the "behind" face toward below), that face's flux magnitude no longer blocks rest. This can never mask a real falling stream: a stream's faces always border same-material liquid or air, never a lighter different liquid it's structurally blocked from entering, so the exemption is inert for every case rest-gating was originally built to protect. Ported identically to both `tools/fluid_prototypes/python/momentum_demand.py::_is_at_rest` and `shaders/fluid_flux.comp::buoy_at_rest()` (no new bindings/params needed — reuses `material_density`/`material_sim`, already bound).

**Validation caveat (be honest about this next time it comes up):** the full waterfall/thin-pool-waterfall/sealed-column bench suite passes unchanged with the fix in place (zero regressions). But an isolated 1-voxel-column repro of the exact "water resting on non-bulk oil" configuration — both at full fill and at the dust-level fill (1-4) actually seen in the FluidWatch trace — resolved via buoyancy within ~10 ticks **with or without this fix**; I could not force a genuine permanent lock in bench isolation. The real 100+-tick freeze most likely requires the busier, multi-cell neighborhood of an actual pool (ongoing disturbance on the cell's other faces, or nearby phi-flood coupling) to manifest — something a quiet single-column test can't reproduce. Ship the fix on its logical merits (it removes a real, provably-permanent structural flaw and cannot regress anything already covered), but treat the in-editor retest as the actual confirmation, not the bench run.

**Rule to remember:** a rest/idle gate built on raw flux magnitude assumes flux always decays given enough time. That assumption silently breaks for any face where transport is structurally impossible (not just slow) — check for "can this face's flux physically ever reach zero" before trusting a magnitude threshold as a rest signal.

### 2026-07-16 (same day, follow-up): the SAME bug's real root cause found — a liquid's own upward-facing face, not the cross-material interface — but every same-tick fix attempt reopens the chimney; left OPEN (RESOLVED later the same day via fill-history, see the next entry below)

**Context:** further in-editor testing (5×3×5 oil-filled hole, water dropped in) surfaced a cleaner trace of the still-stuck-water symptom: `fx=0, fy=-408 (pinned), fz=0` for a water film sitting on oil with genuine AIR directly above it (not another liquid). Since `fx`/`fz` are exactly 0, only the Y axis blocks rest — and since the neighbour above is air, not oil, this is the cell's **own** upward-facing lane, not the below-interface the same-day fix above targets. Different face, different mechanism.

**Root cause, confirmed by direct code reading (`phi_flood.py`'s `_compute_phi`):** a free-surface cell (fill<255, or the cell above isn't the same liquid) is a **seed**, `P(pos) = fill(pos)` exactly — identical to plain `head()`. The neighbour above, being air, isn't in the pressure field at all and reads `P=0`. So `dh = fill(pos) - 0`, and since `accel = (dh - FILL_CAP) * g_dt * gravity_bias`, any non-full liquid cell with air above it computes a maximally negative own-Y accel, **completely independent of what's below it** — this is a much more general condition than the earlier below-interface fix covers, and it applies to almost every partially-filled liquid surface in the game.

**Two fix attempts, both REJECTED by the bench's own climb=0 invariant:**
1. **Unconditional exemption** ("own lane negative + air above ⇒ always exempt from rest," reasoning that Transport's `s_out`/`s_in` makes the actual transferred amount 0 anyway since air can't donate fill, so the reading is inert noise). Bench-caught before shipping: `run_waterfall` showed `climb_events=3, worst_climb=3` — a genuinely still-moving stream droplet can also momentarily read air above it mid-splash, and the blanket exemption let buoyancy fire on it, reopening the chimney.
2. **Narrowed exemption** (same condition, but additionally requiring the cell also be resting on a lighter, different liquid below — tying it to the literal reported case). Counter-intuitively **made it worse**: `climb_events=17`. This is a chaotic nonlinear system; blocking one specific swap redirects momentum into triggering a *different*, worse swap elsewhere. Narrowing the logical scope of a same-tick geometric condition does not reliably narrow its dynamical blast radius.

**Both attempts fully reverted** (`momentum_demand.py::_is_at_rest`, `fluid_flux.comp::buoy_at_rest()`) back to the same-day density-only fix above (denser-above / lighter-below exemptions only) — full suite re-confirmed clean (`climb_events=0`) after reverting.

**Status: OPEN, unresolved.** The root cause is understood and documented, but no same-tick, purely-geometric exemption has been found that fixes it without risking the chimney elsewhere — two independent attempts both failed the bench's own acceptance bar, which is treated as a hard invariant, not a tunable tradeoff. A future attempt should likely try a fundamentally different lever instead of another same-tick condition on `is_at_rest`: e.g., tracking per-voxel fill-history state (has this cell's fill actually changed in N ticks, not just "is its computed flux magnitude currently large") as the rest signal for this specific face, since the geometric same-tick approach has now failed twice in different scopes.

**Rule to remember:** in this fluid system, "narrower condition" does not imply "smaller/safer regression" — the flux/phi-flood coupling is chaotic enough that a more restrictive same-tick rest-gate exemption can produce a *worse* climb regression than a looser one. Always re-run the full `climb_events=0` bench check after ANY change to a rest/trigger gate, never assume a narrowing is strictly safer without measuring it.

### RESOLVED (2026-07-16, third same-day entry): the stuck-film rest lock fixed with per-voxel fill history (`stuck_rest_ticks`) — and the reason no bench ever reproduced it was the idle-guard's page eviction silently self-healing it

**The fix (the "different lever" the entry above called for):** a per-voxel fill-history counter as an additional path to "at rest," instead of a third same-tick geometric exemption. Each tick, after Transport/punch and before buoyancy, a history pass compares every dispatched voxel's `(material | fill)` u16 against a stored snapshot: identical ⇒ increment a per-voxel unchanged-counter, different ⇒ reset it and re-snapshot. `_is_at_rest`/`buoy_at_rest()` then treats any cell whose counter has reached `stuck_rest_ticks` (default 12, `-1` disables) as at rest regardless of flux magnitude. The signal is exactly the thing Accelerate's permanently re-saturating free-surface lane can't fake: a genuinely moving/splashing cell's content changes within a few ticks; a structurally stuck film's bytes are identical forever. The theoretical worst case — a saturated steady-stream conduit whose fill sits pinned at 255 while mass flows through — can't ratchet a chimney, because each buoyancy swap rewrites both cells (resetting both counters) and zeroes their fluxes, rate-limiting even that shape to one swap per N ticks; the waterfall suite confirms `climb_events=0`.

**Shipped:** bench `momentum_demand.py` (`stuck_rest_ticks` param, `_update_fill_history`, `_is_at_rest` early-out) and GLSL (`fluid_flux.comp`: new binding 22 `FillHistory` — one uint per full flat voxel index, low 16 bits last-seen u16 / high 16 saturating counter; new pass 10 `FillHistoryUpdate`, dispatched after Transport's `apply_changelog()` and before the buoyancy block; `buoy_at_rest()` early-out; new `SimParams.stuck_rest_ticks` at offset 80 / params buffer 80→84 bytes; `fluid_simulation.gd`: `_fill_history_buf` + `_ensure_fill_history_capacity()` on the density-touch sizing pattern, `stuck_rest_ticks` export).

**Why no bench repro ever worked — two engine-fidelity discoveries (`test_stuck_film.py`, which now reproduces the lock for the first time):**
1. **The idle guard was silently self-healing the bug in every bench scene.** With the bench's small (8³) test chunks, a stuck film's chunk has nothing else moving in it, so after 4 non-dirty ticks the idle guard evicts its flux page — and `_is_at_rest`'s `page<0 ⇒ at rest` convention then lets buoyancy sort the film on the very next tick (traced directly: `buoyed=25` the tick after eviction). In-editor, `chunk_size=32` means the film shares its chunk with the rest of the still-churning scene, the page stays live, and the pinned lane blocks rest indefinitely. The repro therefore must hold the film's chunks in the active set every tick (what "embedded in a larger, actively-disturbed body" — the handoff's suspicion — actually cashes out to). Corollary divergence, worth knowing when reading bench results: the bench's `_pass_buoyancy` scans ALL loaded chunks every tick, while GLSL pass 8 only dispatches over `flux_list` (active + face neighbours) — so in the real engine a stuck film in a fully-asleep chunk gets no buoyancy pass at all until something re-disturbs it. The fill-history counter survives the nap (it just freezes), so with the fix the film sorts on the first re-disturbance.
2. **The full trap needs five ingredients**, and missing any one of them lets some mechanism self-heal it (each was verified by an actual failed repro attempt): (a) partial fill — a full cell reads `dh − FILL_CAP = 0`, no pin; (b) air above — the §3.2 pin itself; (c) **non-bulk** oil below (a single oil layer already resting on water — the normal mostly-sorted end state): over *bulk* oil the pinned lane feeds `_downward_flux` too, so the punch fires on the film and sorts it anyway; (d) no lateral escape — a film smaller than its surface drains sideways through ordinary Transport into adjacent air-over-oil cells (real fill gradient) and buoyancy sorts the relocated pieces; it must uniformly cover a walled-in cross-section; (e) chunks held awake (point 1).

**Validation:** `test_momentum_demand.py` full suite PASS with the fix on by default (waterfall `climb_events=0, worst_climb=0, all_sorted, final_residue=0, pending=0`; thin-pool PASS; sealed column exact; momentum grading intact). New `test_stuck_film.py` PASS: FILM control (fix off) stays locked all 700 ticks with byte-exact conservation — the first bench reproduction of the in-editor symptom — and the fix sorts it (~N+1 ticks); DROP scene clean under both configs. In-editor verification of the GLSL port still pending (same status as every port until played).

**Rules to remember:**
- **When a bug reproduces in-editor but not in bench, suspect the *scheduler*, not just the scene** — chunk size changes which cells share an idle/active fate, and an idle-eviction path (`page<0 ⇒ at rest`) can be an accidental self-heal that only exists at bench scale.
- **A repro of a "stuck state" must arrange every escape mechanism to be blocked, and each blocked mechanism should be verified by an attempt where it wasn't** — the three failed scene attempts (bulk oil ⇒ punch sorts it; partial coverage ⇒ Transport drains it laterally; sleepy chunks ⇒ eviction sorts it) each looked like "the bug doesn't transfer to bench" until traced.

### RESOLVED (2026-07-13): the momentum-displacement "conservation leak" was misattributed — the swap pass moves exactly 0 mass; the loss is base-engine Transport rounding on material the pushes set in motion

**Context:** `tools/fluid_prototypes/MOMENTUM_FLUX_HANDOFF.md` handed off a residual ~1–5% conservation discrepancy that appeared only when `MomentumDisplaceFluidSim` (the density-agnostic cross-liquid momentum mechanism, Python bench only) performed real pushes. Three prior fix rounds (same-tick `touched` claim set, post-Transport reordering, touched-cell flux zeroing) each reduced it without closing it, which was read as a genuine representational gap: `flux_buf` stores momentum per grid position, so a discrete swap leaves the mover's momentum history behind and hands it the previous occupant's.

**Root cause of the misattribution:** nobody had measured WHERE the mass went. Instrumenting every tick (total water+oil fill snapshotted before/after the base Accelerate/Transport step and before/after the momentum pass) on both the control scene and the waterfall scene showed: the momentum pass's cumulative mass delta is exactly **+0** in every `swap_flux_mode` (whole-voxel swaps can't lose fill), and 100% of the loss occurs inside base Accelerate/Transport — matching the engine's own cumulative `last_conservation_delta` to the unit (control: −2368/−2448/−1052 for zero/carry/inert, all exact equalities; waterfall: −3401/−3303/−1115, same). Inert oil at rest loses 0.00%, always. The causal chain: **pushes make previously-still material move, and moving material pays the already-documented Transport rounding tax** (the same churn noise CONTROL runs show at −3.6%…−5.16%). The apparent conservation-vs-responsiveness tradeoff across the three zeroing rounds was an artifact — the zeroing changed how much material moved, not how much any swap leaked.

**Rules to remember:**
- **Flux surgery cannot affect conservation.** Flux never carries mass; only Transport moves fill, and (post-reorder) it runs before the momentum pass. Any flux manipulation after a swap is a *dynamics* decision, never a conservation fix.
- **Attribute a mass discrepancy to a pass before chasing it in that pass** — a before/after fill snapshot around each pipeline stage is cheap in the bench and would have saved three fix rounds.
- **Exact conservation is the wrong bar for a mechanism whose purpose is to agitate material**; the right bar is the churn-scaled tolerance the CONTROL run establishes (`test_momentum_displace.py`'s waterfall check now passes `oil_tol=0.025, require_sorted=False` with the justification inline; density-mechanism tests keep the strict 1%/sorted defaults).

**Resolution shipped with the finding:** the handoff's "carry the flux with the parcel" candidate was implemented and measured (`swap_flux_mode` on `MomentumDisplaceFluidSim`: zero/carry/carry_own/none). "carry" — snapshot each moved parcel's own 3 lanes, zero touched cells' lanes, translate the snapshot to the destination, superposing overlaps with `+=` — is now the **default**: 1875 pushes vs zeroing's 507 on the control scene at equal-or-better conservation, no double-counting blow-up (next tick's Accelerate re-clamps, `damp` decays, face-validity zeroing kills carried lanes facing solids/cross-material), `climb_events=0` still holds on the waterfall, boxed-pocket denial still exactly conserves. All three scenario tests + control comparison PASS; `test_oil_waterfall.py`'s density suite unchanged. **This unblocks the buoyancy half** (lighter-rises-at-rest), which was gated on the momentum mechanism being trustworthy.

### 2026-07-14: `buoyancy.py` scoped into the Python bench — 3 real bugs found and fixed, 1 open architectural finding (momentum+buoyancy feedback loop, not converging — RESOLVED later the same day, see the next entry below)

**Context:** `BuoyantMomentumFluidSim(MomentumDisplaceFluidSim)` — the rest-gated, density-dependent "lighter liquid rises through a denser one" half, reusing momentum's own `_try_piston_displace` chain-relocation mechanism. `test_buoyancy.py` (5 checks) was written to validate it before any GLSL port.

**Bug 1 — rest-gate starvation catch-22 (`buoyancy.py::_is_at_rest`).** The gate treated "no flux page for this cell" as "can't confirm rest, assume moving" (`return False`). But a chunk only *has* no page once the base engine's own idle-eviction has kicked in (nothing moved there recently) — so a genuinely calm, long-settled cell would get evicted, and once evicted could never pass the gate again: calm enough to be evicted ⇒ evicted ⇒ can't be checked ⇒ can never buoy ⇒ stays wrong forever. Same starvation bug *class* as the density-stacking mechanism's own chunk-starvation bug (see below). Fixed by inverting the assumption: no page means the engine itself has nothing to compute there, i.e. flux is definitionally zero (matches `compute_s_out`/`compute_s_in`'s own `page<0 => 0.0` convention) — `return True`. Confirmed against a plain inverted water-over-oil column: `buoyed` was 0 for the entire run before the fix, sorts correctly after.

**Bug 2 — piston escape direction had the wrong sign for buoyancy's own call (`buoyancy.py`'s call to `_try_piston_displace`).** `_try_piston_displace`'s "escape away from the pusher" heuristic (`-direction * axis_dir`) is correct for momentum's own collision case (splash back toward where the impactor came from). Buoyancy called it with `direction=+1` (matching how `npos` was computed — straight/diagonal up from the mover), which made the escape heuristic compute *downward* — back toward the rising bubble itself, exactly where there's no room, since that's where the mover is coming from. Every straight vertical chain got denied. Fixed by passing `direction=-1` instead, flipping the heuristic to escape upward — confirmed directly against the same column (denied → succeeds, water shifts up 3 to a free cell).

**Bug 3 — piston escape_dirs ordering wastes the push_cap budget in wide, shallow layers.** `escape_dirs` tries all 4 lateral directions before "away from the pusher." Reasonable for momentum's punctual-collision case (sideways is usually the fastest real exit), but wrong for buoyancy's much wider/flatter rising-through-a-layer case: a chain walking through a wide, shallow water sheet kept finding an unvisited lateral neighbour first and burned the whole `push_cap=12` budget wandering sideways, even when open air sat 1-2 hops directly above. Fixed by adding a `prefer_away: bool = False` parameter to `_try_piston_displace` (default False preserves momentum's own already-validated lateral-first behaviour exactly); `buoyancy.py`'s call passes `prefer_away=True` to put the vertical escape first.

**Two test-scene-construction bugs, not mechanism bugs**, also found and fixed along the way (worth noting so they aren't rediscovered as "real" bugs later):
- `build_boxed_denser_scene`'s `sealed_shell` half-extent left `cavity_depth+2` cells of open headroom above the water stack instead of 0 — water had somewhere to legitimately rise into, so the scene wasn't "boxed in" at all (measured `buoyed=1`, a real rise, not a denial).
- The same scene's X/Z half was `cavity_half+1` (=2), giving a 3-wide interior with only the center column explicitly filled — 8 open lateral columns of air the piston could freely walk into sideways. Fixed by hardcoding a true 1-wide shaft (X/Z half=1, matching `column_scene`'s own proven approach in `test_density_demand.py`).

**Open, unresolved finding — momentum and buoyancy do not reach equilibrium on the full waterfall scene.** With all 3 bugs above fixed, `run_full_waterfall`'s 5th check still fails: run to 3000 ticks (well past the 1200-tick original budget), `pushed_total`/`buoyed_total` never plateau — `buoyed_total`'s *growth rate accelerates* in the back half of the run (26→13→7→17→16→37→10→22→35→49→44→47→60 events per 200-tick window) and `active_chunks` never drops below 6. Oil drains continuously and does not stabilize: 123930→122975→120912→118980→116880→114495→112371→110503→108760→106976→105317→104348→103572→102871→102024→101385 (−18.2% by t=3000, still declining at t=3000, no sign of leveling off).

**Hypothesis tried (2026-07-14) and FALSIFIED: buoyancy-swap discontinuity re-triggering momentum's force threshold next tick.** Reasoning: a buoyancy swap is a discrete material-identity change, and `head()` reading different materials at the swap boundary could perturb the very next tick's Accelerate enough to cross `force_threshold`, reading as a genuine collision and cascading (same *class* of discontinuity-perturbs-next-tick effect already documented for the density-stacking trigger's own rest gate, see "ADDED (2026-07-12): density_rest_flux" below). Tested directly: added `trigger_grace` (a base-class hook on `MomentumDisplaceFluidSim`, empty/no-op unless populated — confirmed `test_momentum_displace.py` unaffected) and had `BuoyantMomentumFluidSim.step()` shield cells buoyancy touched last tick from momentum's trigger for one tick. Result on the same 3000-tick run: **worse, not better** — `pushed_total` roughly TRIPLED (20328 vs 6546 without the shield) for essentially the same final oil count (102746 vs 101385) and still no convergence. So either this specific mechanism isn't the (or the whole) cause, or shielding the trigger cell just redirects the disturbance to a neighbor rather than damping it. Reverted (`buoyancy.py`'s `step()` no longer populates `trigger_grace`; the hook itself stays on the base class, harmless, in case a future attempt wants it for something else).

**Not yet root-caused. Candidates not yet tried:** running buoyancy less than once per tick (only after N ticks of continuous rest, not just the instantaneous flux check); tightening `force_threshold` specifically so small discontinuity bursts can't cross it while real collisions still can; instrumenting exactly which pass (momentum vs. buoyancy vs. base Transport) is losing the mass, the same before/after-each-stage snapshot technique that resolved the momentum-alone "leak" above — attribution has NOT yet been done for the combined system, so it's still unknown whether this is Transport rounding tax on the now-much-higher churn (consistent with the existing finding: "any pass that makes still material move pays Transport's rounding tax") or a genuinely new loss; or accepting a churn-scaled (not exact) conservation tolerance the way `MomentumDisplaceFluidSim`'s own waterfall test does and re-scoping "success" as convergence-toward-sorted rather than full sort within a fixed tick budget. **Do not port to GLSL/GDScript until this is resolved** — the Python bench discipline (`CLAUDE.md`) exists precisely to catch this before it becomes an in-editor lag/correctness hunt.

### ✅ RESOLVED (2026-07-14, later the same day): the non-convergence was submerged air holes punched by BOTH mechanisms' resolutions — buoyancy's piston replaced with a direct two-cell exchange; momentum gains an opt-in `hole_safe` gate. Combined system now fully converges.

**Root cause, proven in three steps:**

1. **Attribution first (the untried candidate above):** instrumented the combined 1200-tick waterfall — momentum and buoyancy passes both move exactly **0 mass**; 100% of the oil drain (−11549) is base Transport rounding on churn. So the question was never "what leaks," it was "why does churn never stop."
2. **Buoyancy's piston resolution punches a submerged air hole on every rise** (87 of 93 buoy events measured): it relocates the denser blocker to *free space* and vacates the riser's cell to AIR — under liquid. The base engine collapses the hole; the collapse undoes the rise. Measured on the plain inverted column: a persistent air bubble oscillating forever (`[7,7,0,7,3,3]` snapshots), final column IDENTICAL to the initial inverted state after 200 ticks and 20 "successful" buoys — **zero net sorting progress, ever**. This was masked by `run_inverted_column`'s `sorted_ok` check being written BACKWARDS (`max(oil_ys) < min(water_ys)` demands oil *below* water — the starting configuration), so the oscillation "PASSED". Displacement-to-free-space semantics are right for a collision (the stream refills the vacated cell) and wrong for buoyancy at rest (nothing refills it).
3. **Momentum's vacate-to-air seeds a self-sustaining loop once a stratified interface exists.** A push whose vacated cell ends up under a *different* liquid punches the same hole class; the collapse free-fall regenerates near-cap flux — post-pour churn forces measured at **p50=566 of the 765 cap, HIGHER than pour-phase impact forces (p50=398)** — which re-crosses `force_threshold` and re-triggers pushes, which unsort what buoyancy sorted (16,971 post-pour trigger attempts vs 9,272 during the pour, 92% of them downward water→oil at the y=7-9 interface). This also explains why the trigger-grace shield (falsified above) made things worse: the disturbance was never at the swapped cells — it was the hole collapse *below* them.

**Falsified with data (don't retry): `force_threshold` tuning.** Since loop-churn forces exceed real impact forces, no threshold separates them. Also falsified: a general "mass in transit" gate at the trigger (churn IS real mass motion — fill-delta forensics showed only 1% of attempts happen between full cells).

**Fixes (both bench-validated, `fluid_engine.py` untouched):**
- **`buoyancy.py`: resolution is now a direct two-cell exchange** — lighter rises into the denser cell, denser sinks into the exact cell the lighter vacated. Geometry untouched, conservation exact by construction, no denial outcome exists (a sealed water-packed cavity now correctly lets the oil droplet rise to the ceiling — `test_buoyancy.py`'s boxed-denser check updated to expect this, and the inverted `sorted_ok` fixed). Buoyancy ALONE now solves the full waterfall: sorted by ~t=200, oil **±0.0%**, asleep (`active_chunks=0`) for the rest of a 3000-tick run.
- **`momentum_displace.py`: opt-in `hole_safe` gate** (default **False** — plain momentum behaviour bit-identical, both momentum suites re-run PASS; `BuoyantMomentumFluidSim` defaults it **True**): (a) block any push whose mover has a *different* material directly above (vacating would seal a submerged hole; own material above refills it by falling, air above is open surface); (b) a *downward* cross-liquid push with air above additionally requires arrival evidence — mover fill changed ≥ `min_transit` (default 128) across the just-completed base step, read from a pre-step fill snapshot in the bench (a GLSL port reads the engine's existing changelog buffer instead). Real impactors arrive with ~100-255/tick; resting surface films pressing down hydrostatically measured 0-20 — that press is buoyancy's job, not a collision.

**Result on the 3000-tick combined waterfall:** all 81 columns sorted and inversions=0 by ~t=1000, `active_chunks=0` from t=1000 to t=3000 (completely asleep), oil frozen at exactly −2.9% (all paid during the active phase, zero drift after). `test_buoyancy.py` 5/5 PASS; `test_momentum_displace.py` + `test_momentum_control.py` PASS unchanged.

**Rules to remember:**
- **A discrete pass must never vacate a cell to AIR beneath liquid.** Collision semantics (mover leaves a gap the stream refills) and rest semantics (nothing refills the gap) need different resolutions; the submerged-hole collapse is a churn generator the flux engine will happily run forever.
- **When two passes fight, check what each one's *writes* look like to the other's *trigger*** — both triggers here were fine; each resolution's side effect (holes) was the other trigger's food.
- **A test that passes while the mechanism visibly oscillates is a wrong test** — print the actual final state (the inverted-column check was backwards and validated the failure for two days).

### FIXED (2026-07-12): eliminated the remaining 2 CPU<-GPU stalls in `_resolve_density_demands()` entirely — still laggy after the first stall-reduction pass, and a fair architectural question ("why is this running on the CPU?") pointed at the real remaining issue

**Symptom:** "still lagging" reported after the previous entry's fix (5 stalls → 2). The user also asked directly why density-demand resolution touches the CPU at all, given the engine's GPU-resident design.

**Answer to the question, and the bug it exposed:** the actual COMPUTE (BFS walk, accumulate, apply) always ran entirely on the GPU in `density_resolve.comp` — that was never the issue. What was CPU-side were two remaining `download_range()` calls (from the previous fix) that existed to shuttle GPU results through the CPU for reasons that, on inspection, didn't require the CPU at all:
- **Touched-cell data** was downloaded only to decode chunk positions for `FluidSimulation`'s own dirty-chunk tracking (`density_touched_chunks`). But `fluid_flux.comp`'s other passes (Trigger, Transport) already produce this exact information via `mark_dirty()` into a shared bitmask buffer that `step()` already downloads once per substep regardless, for its own unrelated purposes. The touched-cell readback was duplicating information the engine already had.
- **Requeue data** was downloaded to the CPU and immediately re-uploaded verbatim into `_density_demand_queue_buf`, with no CPU-side logic ever inspecting or transforming it in between — a pure GPU-buffer-to-GPU-buffer copy wearing an unnecessary CPU round-trip.

**Fix:**
1. `density_resolve.comp`'s `pass_apply` now calls `mark_dirty()` (new `DirtyChunks` binding, mirrors `fluid_flux.comp`'s own function exactly — same formula, same shared buffer) instead of relying on the CPU to decode `touched_cells` for this purpose. `FluidSimulation.step()`'s existing single dirty-bitmask download (already happening after Transport, for the base flux system's own needs) now picks this up for free. The whole `density_touched_chunks` Dictionary/parameter/union-into-`changed` mechanism is deleted — dead code, not just redundant.
2. Added `ComputeHelper.buffer_copy()`, a thin wrapper around `RenderingDevice.buffer_copy()` — a genuine GPU-side buffer-to-buffer copy with zero CPU involvement. The requeue-carry-forward step (previously download-then-reupload) is now two `buffer_copy()` calls (count, then entries) directly from the requeue buffer into the demand queue buffer.

**Result:** `_resolve_density_demands()` now makes ZERO `download_range()` calls — down from 5 in the original version, 2 after the previous fix, 0 now. The only remaining sync points are ordering fences (`submit()`+`sync()` between dependent dispatches, and `apply_changelog()`'s own internal changelog-count check) that transfer no bulk data back to the CPU and are an existing, engine-wide cost every mutation pathway already pays — not specific to this mechanism.

**Not yet re-verified in-editor.**

**Rule to remember:** "does this need to touch the CPU at all" is a better question than "how do I make this CPU round-trip cheaper" — the previous fix (combining reads, avoiding dispatch-sizing reads) was real progress, but it was still optimizing a round-trip that turned out to be entirely unnecessary once examined structurally. A GPU-to-GPU copy or a piece of information another pass already produces are both signs the CPU was never actually needed in the loop.

### FIXED (2026-07-12): `_resolve_density_demands()` made 5 synchronous CPU<-GPU stalls per substep — the real lag source, not shader compute cost

**Symptom:** "still really laggy" reported after the falling-mass/N-material fixes below (which improved correctness but didn't address performance — `WALK_CAP` had already been dialed back once for suspected shader-cost reasons, with limited effect).

**Root cause:** `_resolve_density_demands()` called `_compute.download_range()` — a SYNCHRONOUS, blocking `RenderingDevice.buffer_get_data()` (`compute_helper.gd`) — five separate times per invocation: queue count (to size pass 0's dispatch), touched-cell count (to size pass 1's dispatch), touched-cell data, requeue count, and requeue data. Each is a full CPU<-GPU pipeline stall, not just a bandwidth cost — and this function runs every substep `use_density_stacking` is on, so any tick with active sorting (a splash settling over many frames) paid all 5 stalls repeatedly, stacked on top of the pipeline's other existing sync points (ClaimZero, Trigger, two `apply_changelog()` calls, pass 0, pass 1). This is very likely the dominant real cost — GPU-side compute time for a bounded, small-workgroup dispatch is typically far cheaper than even one CPU-GPU synchronous round-trip.

**Fix, two parts:**
1. **Eliminated the two dispatch-sizing reads (queue count, touched count) entirely.** Both `density_resolve.comp` passes already self-gate on the real count internally (`if (idx >= count) return;`), so dispatching a FIXED, worst-case-sized grid (`MAX_DENSITY_DEMAND_ENTRIES / 64` = 1024 workgroups, always) is correct regardless of the actual count — excess invocations do one comparison and return immediately, a small constant NON-STALLING GPU cost, versus a variable-latency CPU-GPU round-trip removed entirely.
2. **Combined the two still-necessary reads (touched-cell data, requeue data) from "read count, then conditionally read data" into ONE call each**, reading the buffer's full allocated capacity every time and parsing the real count out of the same downloaded blob. Down from 5 stalls to 2, regardless of whether the queue was empty or full that substep.

**Not yet re-verified in-editor.**

**Rule to remember:** when a GPU-dispatching function feels slow, check the CPU-GPU **synchronization pattern** (how many blocking readbacks per call) before tuning shader-internal constants (search caps, workgroup sizes) — a large compute dispatch with mostly-idle invocations is typically cheap; a handful of `buffer_get_data()` calls in a hot per-substep path is not, and no amount of shader-side optimization fixes a stall-bound function. Indirect GPU-computed dispatch sizing (avoiding the CPU readback for dispatch counts altogether) isn't used anywhere in this codebase yet — worth it if a lower stall count is still needed later.

### FIXED (2026-07-12): fill==255-OR-unchanged trigger gate had a falling-solid-mass loophole; trigger was also hardcoded to WATER/OIL instead of reading density — both found after retesting the WALK_CAP fix above

**Symptom (second in-editor test, after the WALK_CAP fix above):** oil still appeared on/around a dropped sphere as it fell through an oil pool, and still climbed from the pool's center — plus major lag on impact.

**Root cause 1 (the climb/appear-on-sphere symptom):** the trigger's "full-or-settled" gate (`my_fill == FILL_CAP OR unchanged since last substep`) was designed against the WATERFALL bench scene, where a thin STREAM's cells are genuinely partial-fill while falling and only reach fill=255 once they pool and settle — so "full" was a reasonable proxy for "at rest" there. A solid falling mass (a dropped sphere) breaks that proxy completely: every voxel in a solid block of water is fill=255 for its ENTIRE fall, landing included, so the "full always eligible" half of the gate let it trigger claims against oil immediately on contact, mid-fall, with real downward momentum still in play — structurally the same "displaced material appears where it shouldn't because the trigger fired on something still in motion" failure class as the waterfall bug, just exposed by a different scene shape. The user correctly diagnosed this and proposed the fix: check the water voxel's actual FLUX (a direct measure of current motion), not fill or fill-history.

**Fix 1 — replaced the fill-based gate with a flux-based one, and deleted the `density_changed` buffer entirely.** `fluid_flux.comp` pass 7 now reads the SAME `flux_buf` Accelerate/Transport already populate this substep: any non-negligible flux (`eff_flux() != 0`) on any of the cell's 3 owned faces OR the 3 incoming neighbour-owned faces means real motion right now, regardless of fill. This is strictly more correct than the fill-based gate (catches both a partial-fill stream in transit AND a full-fill solid mass still falling) and needed NO cross-tick history at all — the whole `density_changed` scratch buffer (self-clearing "changed last substep" flag, binding 16) was deleted as dead weight, a net simplification, not just a fix. Binding 16 is now retired/unused rather than renumbered (downstream bindings 17-20 kept their numbers to minimize touch points).

**Root cause 2 (scope, flagged directly by the user, not a bug report):** the trigger hardcoded `MAT_WATER`/`MAT_OIL` — the system should reason about relative DENSITY, not fixed material identities, both because that's the physically correct model and because it's the only way a third liquid could ever participate without editing the trigger again.

**Fix 2 — generalized to N materials via a new `MaterialDensity` buffer**, mirroring the existing per-material `MaterialFlow`/viscosity buffer exactly: `MaterialDef.density` (new export, default `0.0` = "not density-sorted" — the safe default is EXCLUSION, unlike flow's "default 1.0 so nothing freezes," since an unconfigured material should never accidentally participate just by being `SIM_LIQUID`), populated by `WorldOrchestrator._build_material_cache()` into a 256-float GPU buffer (binding 21), water=1.0 (baseline) and oil=0.85 (floats above it) set in `material_db.gd`. The trigger now compares `material_density.data[mat_id]` against every liquid candidate's own density and only proceeds when the candidate is BOTH a different registered liquid AND has a strictly smaller positive density — no material ids appear anywhere in the trigger logic anymore.

**Root cause 3 (the lag):** `density_resolve.comp`'s `WALK_CAP` had been raised to 256 (see the entry above) to give the min-Y walk enough lateral reach across a wide pool. Its "already visited" check is an O(n²) linear scan over the `visited` array, so cost grows QUADRATICALLY with `WALK_CAP` — and with the (now-fixed) trigger gate previously firing on every fill=255 voxel of a falling sphere every substep, a splash scene could generate a very large number of simultaneous demands, each paying that quadratic cost. **Fix 3 — `WALK_CAP` dialed back 256 → 128**, a deliberate compromise: fix 1 above should sharply cut how many demands get generated during a fall in the first place (no claims at all until the mass actually settles), so the walk's per-demand cost matters less even at a somewhat smaller budget. If lag persists after re-testing, the O(n²) seen-check itself (not `WALK_CAP`'s value) is flagged as the next thing to address.

**Not yet re-verified in-editor** — all three fixes are diagnosis + fix, not confirmed resolution; this entry records what was found and changed, not a retest result.

**Rule to remember:** a trigger gate's proxy (fill==255 as a stand-in for "at rest") is only as good as the scene it was validated against — a bench scene built around one failure mode (a thin stream) can leave a completely different, plausible real-world case (a solid falling mass) untested and broken. When a "settled vs. moving" distinction is the actual thing that matters, use the simulation's own direct motion signal (flux) if one already exists, rather than reconstructing "did this change" from fill history — it's both more correct and cheaper (no extra buffer, no cross-tick bookkeeping).

### FIXED (2026-07-12): density_resolve.comp's WALK_CAP=64 was too small — oil still climbed the waterfall, forming a thin chimney from the center of the pool outward

**Symptom (first in-editor test of the step-3 port):** oil still climbed the waterfall — a thin, tall, single-voxel-wide spike of oil rose from the center of a pool a sphere had been dropped into, with low, scattered fill values along its length (fill=4 near the tip). A second scene (sphere splash onto an oil pool) showed oil settling into a rough disconnected blob near the impact point instead of a clean flat layer, with concentric flux ripples around it.

**Root cause:** `density_resolve.comp`'s bounded BFS walk (min-Y candidate search) used `WALK_CAP=64`, copied directly from `demand_resolve.comp` (GranularSimulation's phi_demand resolver) without re-deriving it for this mechanism's different connectivity requirement. `demand_resolve.comp`'s 64 was tuned for a SPARSE case — a single sand grain displacing a small amount of water, where a nearby free surface is almost always within a handful of hops. Density-stacking's actual scenario is a DENSE, wide oil pool with water sinking through its middle: as water claims oil cells top-down, the real remaining free surface retreats toward the pool's edges, and the lateral distance from a buried, near-center origin to that surface routinely exceeds 64 hops in a real-sized pool. When the walk exhausted its budget without finding real capacity, every demand fell through to the one-step-only fallback (deposit one cell above origin — see that fallback's own comment for why it's deliberately short-range) — and since origin is exactly the cell the sinking water just claimed, that fallback fires at a NEW, ever-deeper position every tick as the water column advances, stacking one more oil cell onto the same spot each time. The visual result — a thin, tall column of small partial deposits rising from wherever the water intrusion happened to be deepest (typically the center, since that's where a dropped sphere or falling stream penetrates furthest) — is structurally the same "displaced material teleports/piles at the disturbance point" failure class documented for the two OLDER, already-abandoned resolution mechanisms (`docs/BUG_LOG.md`'s "oil climbs the sinking water mass" and "oil 'teleports' to the surface" entries), just re-introduced through a different specific bug (an undersized search budget) rather than the resolution algorithm's shape.

**Fix, three parts, in `density_resolve.comp`:**
1. **`WALK_CAP` raised 64 → 256.** The real requirement is lateral reach across a pool, not a small local neighborhood — 256 gives meaningfully more headroom without the memory cost of matching the Python bench's `WALK_CAP=512` (a CPU dict-based visited set, cheap to size generously; a GLSL local array of 512 `ivec3` is not).
2. **The separate `cand_pos[WALK_CAP]` candidate array was removed.** `pass_walk` only ever needed the MINIMUM-Y candidate, not the full set, so tracking a single running best (`best_pos`/`has_best`) inline during the same walk needs no array at all — freeing a whole `WALK_CAP`-sized array's worth of per-invocation memory to spend on the bigger `visited`/`frontier` budget in (1) instead of paying for three separate arrays.
3. **`NEIGH6`'s expansion order changed to +Y-first** (was the plain axis order `demand_resolve.comp` uses). Documented honestly as a modest, UNPROVEN heuristic (preferring upward expansion when multiple same-material directions are available), not the primary fix — a same-material BFS can only ever expand through oil-connected cells regardless of order, so this can't shrink the real lateral distance a buried-in-the-middle origin needs to travel; (1) is what actually addresses the measured failure.

**Not yet re-verified in-editor** — this fix has not been re-tested after being written; the original symptom report is what identified the bug, this entry documents the diagnosis and fix, not a confirmed resolution.

**Rule to remember:** don't reuse a tuned constant (search radius, cap, budget) across two mechanisms just because they share a code shape (BFS walk + accumulate) — `demand_resolve.comp` and `density_resolve.comp` solve structurally different connectivity problems (sparse point-source vs. dense-pool lateral traversal) even though the walk/accumulate/apply scaffolding is identical; the NUMBER has to be re-derived for the new problem, not copied from the old one's precedent.

### SOLVED IN BENCH (2026-07-11): oil-water interaction — "oil travels up the waterfall" root-caused; a min-Y demand resolver with bubble landings + full-or-settled trigger passes a new waterfall scene that every prior mechanism fails

**Symptom (in-editor, reported 2026-07-11):** the latest attempt, a lighter-initiated local rule ("if oil, and water above, move up"), makes oil travel UP a falling waterfall of water, engulfing the stream, instead of being pushed aside and floating on top.

**Why no prior bench scene caught this:** every existing density scene (INVERTED, POOL_INVERTED, falling-mass, test-tube) tests water *settled* above oil. None models water *in transit*. A new scene, `tools/fluid_prototypes/python/test_oil_waterfall.py`, pours a continuous 1x1 water stream from 10 cells above a 9x9x6 oil pool in a walled basin, and gates on: (1) no column ever holds >255 fill of oil above the legitimate current level (level = initial surface + average rise from water actually in the world), (2) final state fully density-sorted per column, (3) conservation (oil ≤1% drift, water ≤5% — a no-mechanism CONTROL run already loses ~3.6% of emitted water to base-engine transport rounding at waterfall flux magnitudes, so tighter water bounds would gate on the wrong thing), (4) demand queue fully drained. The scene **reproduces the reported failure**, which is what makes its verdicts transferable.

**Measured verdicts (700 ticks, 120 voxels of water):**
- `NAIVE_OIL_UP` (the reported rule): fails catastrophically — the rule can't distinguish settled water (buoyancy applies) from water in transit (momentum should dominate); after each swap the stream re-presents "water above oil" one cell higher, so the rule is a CONVEYOR. Oil reaches source height (worst_climb=7) by tick ~15 and stays.
- `DensitySwapFluidSim` (the reverted 2026-07-10 direct-swap+cooldown design): fails the same way, slightly worse — a swap puts oil INTO the stream cell the water just vacated, and the stream replenishes water above it every tick. (This design remains the best on the *sealed* falling-mass scene; its flaw is specifically transit.)
- `DensityDemandFluidSim` (demand+BFS, nearest-surface deposit): fails two DIFFERENT ways, both traced cell-by-cell: (a) burst demands stack deposits at the nearest dischargeable surface — exactly the stream's impact point — each newly-topped cell becoming the next demand's discharge site, building an oil tower up the stream (this is the "BFS deposits at nearest free surface reads as engulfment" flaw flagged in ARCHITECTURE.md's phi_demand entry, now confirmed and characterized); (b) the MAX_TUNNEL_HEIGHT=64 fallback tunnels displaced oil straight up THROUGH the falling water column and lands it in the first air gap INSIDE the stream (measured: a ring of oil at y=10 on tick 13).

**The passing design — `DensityLowestSurfaceFluidSim` (`density_demand.py`), four load-bearing pieces, each one's absence measured as a failure:**
1. **Min-Y deposit selection.** The BFS walk (bounded, WALK_CAP=512) collects ALL dischargeable candidates and deposits into the LOWEST landing site first (ties by discovery order) instead of the first found. A real displaced liquid keeps its surface level; a tower cell is by definition higher than the surface elsewhere, so min-Y starves tower growth structurally. (Alone: cut climb events ~25%, insufficient.)
2. **Bubble landings.** A full oil cell sealed under WATER is not dischargeable in place, but physically its displaced volume can rise through the water sheet and collect on top. The walk offers "first air straight up through water from a sealed full oil cell" (bounded by MAX_TUNNEL_HEIGHT) as a candidate; min-Y then naturally prefers the sheet top over any chimney. Without this, a pour that seals the whole oil surface leaves the BFS exactly one dischargeable cell in the component — its own previous deposit — and min-Y dutifully builds a 255-fill chimney up the basin wall, 1 cell/tick, y=9→17 (traced).
3. **One-step fallback rise (not 64, not 0).** When the walk finds zero capacity: deposit into the cell directly above origin if it's air, else requeue for next tick. 64-step tunneling = oil in the stream (see above). Pure requeue = every sealed scene deadlocks: an exactly-full basin has no dischargeable cell anywhere, so the entire displaced volume accumulates in the queue forever while water keeps claiming (INVERTED/POOL_INVERTED ended with oil 765→0 in-world). One step up from origin is the just-vacated claimant cell in the sealed case — exact swap semantics — and can never leap past a water sheet.
4. **Full-or-settled trigger gate.** Water claims oil below only if the water cell's fill == 255 OR its voxel didn't change last tick. Full alone froze the ENDGAME: the pour leaves alternating partial water/oil layers ("lasagna"), every interface is a hard-zeroed different-liquid face, no partial cell may ever claim — 2/3 of the emitted water levitated permanently. No gate at all re-enables the conveyor through the one-step fallback (fresh falling water re-claims a risen oil cell every tick). Together: full water sorts at full speed even while churning; partial water sorts once it stops moving, which consolidates the lasagna (displaced oil deposits into its own partial layer's neighbours, opening holes the water falls through). **GPU port cost: needs a per-voxel "fill changed last tick" flag** — same one-uint-per-slot, self-clearing lifecycle as the reverted DensityCooldown buffer (old binding 17).

**Result:** waterfall `climb_events=0, all_sorted=True, final_residue=0, pending=0`, conservation within tolerance; the 5-scene suite (INVERTED/STABLE/POOL_INVERTED/DIAGONAL_LEDGE/SPLASH_POCKET) passes with EXACT conservation; sealed falling-mass ends sorted with the queue drained (it routes oil through the basin's real free-surface air row — the shipped `test_density_demand_mass.py` metric zero-tolerances that row based on an "exactly full" premise its own geometry doesn't satisfy; that metric is only valid for in-place swap semantics). Residual benign artifacts, both characterized and tracked-not-gated by the test: sub-voxel splash slosh (≤82 fill per column, 1-3 ticks, impact zone) and ≤8-fill MIN_FLOW corner trickle (+1 fill/tick, base-engine phi over-pressure boundary behavior, same family as the known flat-lake ripple; also present in mechanism-free churn).

**Before porting to GLSL, in order:**
1. Resolve the still-open 2026-07-10 mystery ("three bench-validated fixes, three 'no difference' in-editor reports") — e.g. a debug tint on any voxel the trigger touches — BEFORE trusting this bench verdict to transfer.
2. Re-apply the three reverted independent base-engine fixes the bench's engine already contains and this mechanism depends on: `designated_liquid()` air-cell ownership + frame-parity scan order (`fluid_flux.comp`), `_ensure_demand_accum_capacity()` × chunk_size³ (both simulations), and eligibility-based (not success-based) `mark_dirty` for conditional passes.
3. Port `DensityLowestSurfaceFluidSim` exactly — all four pieces; each was individually measured as load-bearing.

**Rule to remember:** "water above oil" is not one situation but two — settled (buoyancy applies) and in transit (momentum dominates) — and any purely geometric local trigger conflates them; the discriminator that works is *state history* (full-or-settled), not geometry, fill alone, or flux magnitude (settled surface faces legitimately carry large persistent flux). And: a bench scene only validates a mechanism against a reported failure if the scene first REPRODUCES that failure with the mechanism that caused the report.

### FIXED (2026-07-10): oil visibly "climbs"/engulfs a large water mass as it sinks through oil — demand-queue resolution replaced with a direct swap

**Symptom (in-editor, sphere-of-water-onto-oil-pool):** as a large, cohesive water mass sinks through oil, oil visibly wraps around and climbs the sides of the sinking mass before the whole thing eventually settles correctly — described as looking "like a venom symbiote." Final state is correct; the multi-tick transition is not.

**Root cause (confirmed via `tools/fluid_prototypes/python/test_density_demand_mass.py`, a purpose-built large-falling-mass scene):** the demand-queue+BFS resolution mechanism (borrowed wholesale from `phi_demand`'s sand-into-water displacement) is structurally wrong for a liquid-liquid density inversion. Sand entering water ADDS net volume to the liquid body, so the displaced water genuinely must surface somewhere — BFS-to-dischargeable-surface is correct there. A density inversion is VOLUME-NEUTRAL: in a sealed, exactly-full basin, every "dischargeable" cell IS the free surface, above the displaced cell by definition, so the BFS resolution (success or fallback alike) always deposits the displaced lighter material above its own origin. Measured directly: an instrumented falling-mass run showed 56 demands resolved via the BFS *success* path depositing 18870 fill of oil above the pool's original surface after ONE tick. Two attempts at patching the demand-queue's origin/fallback convention (using the lighter material's true prior position as origin; tunneling straight up when blocked) each fixed one symptom and surfaced another (a permanently-stuck demand backlog; an ambiguous climb-metric regression) without addressing the actual structural cause.

**Fix — replace the resolution, not just the origin.** `density_demand.py`'s `DensitySwapFluidSim` (subclass of the demand-queue version, keeping only its 5-candidate downward trigger — the real fix for the original local single-hop swap's zero lateral reach) resolves each misplaced pair with a direct in-place swap of the two cells' contents: no queue, no search, no fallback, no in-flight volume. The displaced lighter material's correct destination is already known deterministically — the claimant's own just-vacated cell — so the hard invariant ("displaced material never rises except by being pushed up by the denser liquid seeping under it") holds BY CONSTRUCTION: the lighter material ends exactly one Y-level above (or diagonal-up from) its prior position, in the cell the denser material just left.

**Verified:** `test_density_demand.py`'s full 5-scene suite (INVERTED, STABLE, POOL_INVERTED, DIAGONAL_LEDGE, SPLASH_POCKET) passes against the swap version unchanged. `test_density_demand_mass.py`'s falling-mass repro — the exact scene that exposed the artifact — now reports `climb_events=0 worst_climb=0 all_sorted=True water 31875->31875 oil 215985->215985`: zero liquid above the sealed basin's original surface at any tick, and exact fill conservation (not just within tolerance).

**Ported to GLSL:** `shaders/fluid_flux.comp`'s `params.pass == 5` now performs the swap directly via a 2-entry changelog write (claimed cell becomes the claimant's content, claimant's old cell receives the displaced voxel), guarded by `atomicCompSwap` self-claim + target-claim against `DensityClaim` (binding 16) so each cell participates in at most one swap per substep — closes both the original cross-claim race AND a new chain-guard case the swap introduces (a middle-density cell being simultaneously claimant and target). Binding 15 (the old `DemandQueue`) is retired; `simulations/fluid_simulation.gd`'s entire demand-resolve buffer set/pipeline/dispatch for density-stacking (`_demand_resolve_pipeline`, `_demand_queue_buf`, `_demand_accum_buf`, `_touched_cells_buf`, `_demand_requeue_buf`, `_resolve_fluid_demands()`, etc.) has been removed as dead code — `GranularSimulation`'s own separate instance for `phi_demand` sand-water displacement is untouched and still uses the queue+BFS resolver, which remains correct for that use case. Not yet re-verified in-editor.

**Rule to remember:** a resolution strategy borrowed from a shared mechanism (BFS-to-free-surface) can be correct for one physical relationship (mass-adding displacement) and structurally wrong for another (volume-neutral exchange) even when the *trigger* that finds the pair is legitimately reusable — don't assume borrowing the trigger means the resolution transfers too; check whether the two use cases are conserving the same quantity.

### FIXED (2026-07-10): the swap redesign above didn't fix the reported symptom — root cause was the TRIGGER's candidate shape, not the resolution

**Symptom:** in-editor re-test of the swap redesign (previous entry) showed no visible difference at all — oil still visibly engulfs the sinking water mass. Isolating the variable (toggling `use_density_stacking` off) proved the swap trigger IS the source (with it off, water and oil don't interact at all — see below), so the fix above, while a real and correct improvement, wasn't addressing the actual mechanism producing the visual.

**Second root cause, found via an actual cross-section trace (not just aggregate numbers) of `DensitySwapFluidSim` sinking a solid embedded water cube through oil:** the mass doesn't climb, it **fragments**. `DOWNWARD_CANDIDATES`' 4 diagonal-down offsets exist to reach an isolated droplet with nothing directly below it (`DIAGONAL_LEDGE`/`SPLASH_POCKET`'s single-voxel droplets, which have no same-material neighbour in any direction). But nothing distinguished that case from a cell on the FLANK of a large cohesive mass — which also has nothing directly below it (more of its own material is there instead), yet DOES have same-material company on 3 of its 4 horizontal sides. Firing diagonal candidates for flank cells too let the ENTIRE outer shell of a solid block swap independently and simultaneously each tick, not just its bottom face — punching scattered single-cell channels through the sides in an uncoordinated order. Viewed from outside (raymarched, opaque materials), disconnected tendrils of oil threading through the water body read exactly as "oil engulfing the water" / "venom symbiote," while conservation and the climb-check both stayed clean throughout (neither test catches a lateral shape defect).

**Fix — gate diagonal reach on horizontal isolation.** `density_demand.py`'s `_find_misplaced_pairs()` now only tries the 4 diagonal-down candidates for a cell that has ZERO same-material neighbour among the 4 horizontal offsets (`HORIZ4`) — true for a lone droplet, false for essentially every surface cell of a mass wider than 1 voxel. Straight-down stays unconditional either way, so a bulk mass still advances — strictly from its bottom face, one layer at a time, instead of eroding from every exposed side simultaneously. Ported identically to `shaders/fluid_flux.comp`'s pass-5 trigger (same `HORIZ4` isolation check before the diagonal-candidate loop).

**Verified:** all of `test_density_demand.py` (5 scenes), `test_density_demand_mass.py` (climb-check + exact conservation) still pass unchanged. New `test_density_demand_coherence.py` added specifically to catch this class of bug (neither existing test inspects lateral shape during the transition, only final state / height) — checks that every horizontal layer of a sinking mass's footprint stays a single CONNECTED region (4-connectivity flood fill in the X-Z plane) at every tick, not fragmented into disconnected islands. Failed before the fix (fragmentation visible within the first few ticks in a manual cross-section trace), passes after (`worst_fragmentation_runs=1` throughout a submerged-block repro).

**Follow-up found, NOT fixed at the time (separate, lower-priority, tracked here):** the same trace surfaced a distinct artifact — a falling mass's LOWEST layer always has fresh oil to swap into and re-fires every tick, while each layer above it can only fire once its own immediate neighbour below has vacated (a one-tick propagation delay per layer). The leading layer races ahead, opening vertical gaps between horizontal bands of the original mass as it falls, before recompacting once it reaches the pool floor. This is vertical banding/stretching, not lateral wrapping — a different-looking, different-mechanism issue from what was reported and fixed here. `test_density_demand_coherence.py` deliberately checks LATERAL (per-layer) coherence only, not vertical (per-column) coherence, and documents this gap explicitly rather than asserting against it. **Superseded by the next entry** — this follow-up turned out to be the DOMINANT visible artifact in the real in-editor scene, not a minor secondary one.

**Rule to remember:** a trigger's candidate set tuned for one geometry (isolated droplets) can silently misbehave for a structurally different geometry (a bulk cohesive mass) even when both are handled by the "same" 5-candidate check — the failure mode isn't in what the candidates individually do, it's in WHICH cells qualify to use the wider (diagonal) reach at all. A per-cell local check (isolation) can distinguish the two geometries cheaply, without any connected-component analysis.

### FIXED (2026-07-10): the lateral-fingering fix above didn't fix the reported symptom either — the "separate, lower-priority" vertical-racing follow-up flagged in that entry was the actual dominant artifact

**Symptom:** in-editor re-test of the lateral-isolation fix showed no visible difference — oil still "teleports" to the surface while the water sphere is still falling (described as arriving at the top WHILE the mass is still moving, not after). A separate regression in sand-water displacement was also reported at the same time (`granular_simulation.gd`'s `phi_demand`, tracked separately — not touched by this entry).

**Ruled out first:** toggling `use_density_stacking` off confirmed the swap trigger is still the source (with it off, water and oil don't interact at all — different-material liquid-liquid flux is hard-zeroed in the base engine, `fluid_engine.py`'s `_pass_accelerate` / `fluid_flux.comp`'s Accelerate pass, mat_id != nm forces flux to 0). No shader-caching bug either: `compute_helper.gd`'s `compile_shader()` keys its pipeline cache by a hash of the GLSL source text on a fresh per-`_ready()` `ComputeHelper` instance, so every edit is guaranteed to force recompilation on the next run.

**Root cause: this IS the vertical-banding follow-up from the previous entry, just far more visible in a real scene than judged at the time.** A swap trades contents: for every water cell that hops down into oil, the oil hops up into the water's old position, in the exact same spot. The previous entry's "leading layer races ahead of the layers behind it" dynamic, viewed from the oil's side rather than the water's, means a single-file column of oil directly above the fastest-advancing part of the falling mass gets pushed upward every single tick, uncontested, reaching the real free surface in roughly (depth below surface) ticks — while the bulk of the water mass is still working through its own layer-by-layer bottleneck below. That reads exactly as "oil teleports to the top while the water is still falling."

**Fix — a one-tick cooldown on the trigger, not another candidate-shape change.** `density_demand.py`'s `DensitySwapFluidSim` gained `_is_cooling_down()`: a cell that swaps this tick is barred from swapping again next tick (checked at the top of `_find_misplaced_pairs()`'s per-cell scan; the check itself clears the flag, so no separate "zero the buffer" pass is needed). Only the denser (triggering) material needs this — the lighter material never initiates a candidate search, so it can't race ahead on its own. This forces the leading edge down to the exact same rate as every layer behind it: both still advance, just offset by a constant one-tick phase instead of an ever-widening gap.

**Verified:** the existing 5-scene suite, the falling-mass climb-check, and the lateral-coherence test all still pass unchanged. A direct vertical-gap probe (ad hoc, mirrors `test_density_demand_coherence.py`'s connected-region logic but per-column) showed the worst vertical run-count growing unboundedly without the cooldown (reached 5 within a few ticks and kept climbing) versus **bounded at 3 regardless of pool depth or tick count** with it (traced out to 400 ticks on a much deeper pool) — a constant offset, not a growing one.

**Ported to GLSL:** new `DensityCooldown` scratch buffer (binding 17, one uint per voxel slot, sized like `DensityClaim`). Critically UNLIKE `DensityClaim`, this is never zeroed by a separate dispatch pass — it must persist across substep boundaries by design (a cell's cooldown has to survive from the substep it swapped in to the very next one). It self-clears inline: pass 5 checks `density_cooldown.data[my_flat]` first; if set, clears it and returns without searching for a candidate. On a successful swap, `density_cooldown.data[n_flat] = 1u` marks the denser material's NEW position for the next substep. Not yet re-verified in-editor.

**Rule to remember:** when a bounded-vs-growing metric (worst vertical run-count capped at a small constant vs. climbing without limit) is the actual signal, "does it look different" is not a reliable substitute for measuring the metric directly — the lateral fix above was real and necessary, but insufficient alone, and its own entry had already found and documented the actual dominant cause as a "separate, lower-priority follow-up" before realizing (only after a fresh in-editor test) that it wasn't lower-priority at all.

### FIXED (2026-07-10): `_ensure_demand_accum_capacity()` sized its scratch buffer to the chunk-slot count, not the voxel count — silently dropped every demand-resolver deposit in both `FluidSimulation` and `GranularSimulation`

**Symptom:** in-editor testing of density-ordered liquid stacking showed the test-tube scene losing ~65-70% of its total liquid fill within the first tick, then stabilizing. Direct GPU-side probing (reading `demand_accum.data[]` and the resolver's own `changelog.count` right before/after each dispatch) showed `touched_count > 0` (cells were genuinely being accumulated into) but `changelog.count` staying exactly 0 after the apply pass — meaning every one of `demand_resolve.comp`'s `pass_apply` invocations was hitting its `amount == 0u` early return, despite `pass_walk` having just accumulated real fill into that exact slot.

**Root cause:** `WorldOrchestrator.get_voxel_buf_capacity()` returns the number of **chunk slots** the voxel buffer is sized for (`_voxel_buf_capacity`), not the total voxel count — the real voxel buffer is `capacity * chunk_size³ * 4` bytes (see `_init_grid`/`_add_chunk_to_grid`). `_ensure_demand_accum_capacity()` (in both `FluidSimulation` and `GranularSimulation` — the latter is where the pattern originated, and `FluidSimulation`'s was copied from it verbatim for the density-demand port) sized its accumulator buffer directly to this **slot** count instead of multiplying by `chunk_size³`, undersizing it by a factor of `chunk_size³` (32768 at the default chunk_size=32). Since `demand_accum` is indexed by the **full flat voxel index** (`slot * vpc + local`, same as `voxels_a` itself), any accumulate() write beyond the first ~512 voxels (out of a real capacity of hundreds of thousands to millions) landed out of bounds and was silently discarded by the GPU — a plausible driver behavior for storage-buffer OOB writes, not a crash. The confirming direct probe: `demand_accum.data[probe_flat]` read back as `0` immediately before the apply pass, with `probe_flat` (174908) far exceeding the buffer's actual capacity (512).

**Fix:** multiply by `chunk_size³` in both `_ensure_demand_accum_capacity()` (`FluidSimulation`, `GranularSimulation`) and `FluidSimulation`'s analogous `_ensure_density_claim_capacity()` (the CAS-claim scratch buffer added for the density-demand trigger, same indexing scheme, same latent bug).

**Impact on already-shipped `phi_demand`:** `GranularSimulation`'s sand-water displacement mechanism has this exact same bug, unfixed until now, in already-tested code. The earlier "it works, and looks great!" in-editor confirmation predates this fix and this discovery — it was a qualitative visual check, not a mass-conservation measurement, so it would not have caught silent fill loss of this kind. Needs re-verification now that the fix is in.

**Rule to remember:** any buffer indexed by the **full flat voxel index** (not by chunk slot, not paged like `flux_buf`/`phi_buf`) must be sized to `get_voxel_buf_capacity() * chunk_size³`, never to `get_voxel_buf_capacity()` directly — the latter is a chunk-slot count, and using it raw undersizes by a factor of `chunk_size³`. GPU storage-buffer out-of-bounds writes on this hardware/driver combination fail silently (no crash, no validation error visible in the console) — a wrong-but-plausible-looking number (`0`) is the only symptom, which is why a direct value probe (not just count/flag checks) was needed to actually find this.

### FIXED (2026-07-10): `designated_liquid()`'s fixed scan order could permanently freeze one liquid's settling near the other (found via in-editor testing: sphere-of-water-onto-oil-pancake)

**Symptom:** dropping a large water sphere onto a flat oil pancake left the pancake's own Y-axis settling frozen wherever splashed water droplets scattered across its surface — reported alongside the scattered-stray-voxels symptom the air-cell-ownership fix (previous entry) was meant to solve.

**Root cause:** `designated_liquid()` (added by the previous fix) picks which single liquid "owns" a contested air cell via a scan over the 6 neighbours in a FIXED order (+X,-X,+Y,-Y,+Z,-Z, first match wins). That function's own doc comment originally assumed a losing material only loses "a one-tick cosmetic ambiguity" — true for a single momentary contest, but WRONG for a persistent spatial arrangement: if water happens to sit in whichever direction gets checked first relative to a given air cell, and neither material is moving away (e.g. a droplet just resting on an oil surface), water wins ownership of that air cell **every tick, indefinitely**. With droplets scattered across a whole surface after a large splash, this can systematically lock oil out of most of its own exposed boundary — reading exactly as "oil stopped moving," not a rare edge case.

**Fix:** alternate the scan direction by frame parity (`(params.frame & 1)` selects forward vs. reverse order) in both the shader (`fluid_flux.comp`'s `designated_liquid()`) and the Python bench (`fluid_engine.py`'s `_designated_liquid`, keyed on `self._frame % 2`). A losing material is now blocked at most every OTHER tick instead of permanently, so both liquids keep making real progress over time. Full regression suite re-ran clean afterward (density-stack suite, `run_tests.py phi`, `test_phi_demand.py`, `test_staircase_recovery.py` — all identical results to before this fix, confirming it doesn't change behavior when there's no real contention).

**Rule to remember:** any "pick one deterministic winner" tie-break for a GPU pass must be checked against a PERSISTENT spatial arrangement, not just a single-tick snapshot — a fixed, position-only tie-break that seems like "rare, cosmetic ambiguity" in isolation can become a systematic, permanent lockout the moment the contending elements aren't moving relative to each other. Prefer a tie-break that varies over time (frame parity, a per-tick hash, etc.) whenever the two contenders could plausibly sit still next to each other for a while.

### FIXED (2026-07-10): density-stacking Buoyancy pass could leave stray voxels stuck forever (chunk starvation, found via in-editor testing, not the Python bench)

**Symptom (reported after first in-editor test of the K-scene test-tube rig):** scattered individual water voxels resting on top of oil that never sink through, and oil voxels sitting above water that never finish resolving — random, persistent, not resolving no matter how long the sim runs.

**Root cause:** the Buoyancy pass (`fluid_flux.comp` `params.pass == 5`) only called `mark_dirty()` on an actual successful swap (gated behind the `buoyancy_rate` random roll, default 0.15). `FluidSimulation`'s dispatch range (`flux_list`) is built from `_active_chunks`, and a chunk's idle counter only resets when something in it was marked dirty that tick. Once ordinary fluid transport settles to zero further deltas (a flat, otherwise-correctly-sorted body produces no more flux), a chunk with one lone remaining density inversion has *nothing else* keeping it active — and at a 15% per-tick swap chance, a single pair has ~52% odds of missing 4 consecutive ticks (`0.85^4`). Once that happens, the chunk is evicted from `_active_chunks`, drops out of `flux_list`, and Buoyancy never dispatches there again: the stray voxel is stuck permanently, not probabilistically slow.

**Why the Python bench didn't catch this:** `DensityFluidSim._pass_buoyancy` (`tools/fluid_prototypes/python/density_stack.py`) iterates every loaded chunk in the world directly (`world.chunk_to_slot.items()`), with no dispatch-range restriction at all — unlike the real GPU shader, which (correctly, for performance, matching Accelerate/Transport's existing sparse-dispatch architecture) only runs over `_active_chunks` + neighbours. The bench's simplified model has no equivalent of "this chunk fell out of the active dispatch list," so this entire bug class was structurally invisible to it — the exact same reason phi-flood's own wake-scheduler bug (`docs/PHI_FLOOD_PORT_PLAN.md`) was also only found via in-editor testing, not the bench: a bench that doesn't model the dispatch-range/active-chunk lifecycle can't reproduce a bug that lives entirely in that lifecycle.

**Fix:** mark both chunks dirty as soon as a pair is confirmed genuinely eligible (density-inverted, sufficient fill on both sides), *before* the random roll — not only when the roll succeeds. This keeps the chunk in `_active_chunks` every tick for as long as a real, unresolved inversion sits there, guaranteeing eventual resolution instead of a coin-flip chance of permanent starvation. Same fix shape as `PhiFloodStepFinal`'s own pressure-wave wake check (`PHI_WAKE_MARGIN`) — a cell that still needs attention must keep its chunk awake even on a tick where nothing has changed yet.

**Rule to remember:** any GPU pass that writes conditionally (behind a random roll, a contention loss, or similar) must mark its target dirty based on *eligibility*, not on whether this specific tick's attempt succeeded — otherwise the scheduler can starve out genuinely pending work the moment coincidence lines up against it for a few ticks in a row. And: a Python bench that doesn't model a mechanism's dispatch-range/active-chunk restrictions cannot validate correctness *of* those restrictions — only of the underlying per-cell logic.

### FIXED (2026-07-10): two different liquids near the same air cell could silently convert one material into the other (`fluid_flux.comp` Transport, `fill_mat` inference)

**Symptom:** found while bench-validating liquid↔liquid density stacking (Python bench, not yet ported to GLSL). An air cell adjacent to two *different* liquids (e.g. water resting on a ragged oil surface, with air pockets at the boundary) could have its entire inbound fill misattributed to the wrong material. Confirmed with a minimal 2-column repro (`tools/fluid_prototypes/python`, ragged oil mound + water poured on top, buoyancy pass fully disabled): total combined liquid mass stayed conserved (~3060→3068, normal rounding noise) while oil grew 1530→2930 and water collapsed 1530→138 over 20 ticks — water was being relabeled as oil as it spread past the boundary, not lost.

**Root cause:** Transport (`fluid_flux.comp` pass==1) computes an air cell's `delta_f` as a single unlabeled scalar sum of inbound flux across all 6 faces. Accelerate can drive flux into that same air cell from *multiple different liquid materials at once* (each face's `active_mat` is whichever liquid is on that face, independently) — but by the time Transport sums them, the per-material origin is gone. A *separate*, much cruder heuristic then decided what material the whole delta becomes: scan neighbors in a fixed axis/sign order, take the first liquid found. If water was the actual dominant contributor to that tick's inflow but oil happened to be scanned first, the entire delta got written as oil — silently converting real water volume into oil.

**Why it mattered:** not triggered by any single-material pile settling on its own (oil alone settling, ragged or not, loses nothing — isolated confirmation), and not triggered by (or specific to) the new density-stacking buoyancy pass (reproduced identically with that pass fully disabled). It was specific to "two different liquids both adjacent to a shared air cell," which is exactly the common case liquid↔liquid density stacking exists to handle — any splash, uneven pour, or partially-settled boundary between two liquids would trigger it.

**Fix (bench-validated, `tools/fluid_prototypes/python`):** an air cell may belong to at most one liquid material per tick. A new deterministic, snapshot-only helper (`FluidSim._designated_liquid`, mirrors the existing fixed axis/sign scan order) picks that owner; every Accelerate face between the air cell and a *non-owning* liquid neighbour is gated to zero flux (same shape as the existing "two different liquids never exchange pressure" gate, just extended to air↔liquid pairs). Transport's `fill_mat` inference now calls the *same* helper instead of its own separate copy of the scan, so gating and labeling can never disagree about which material owns a given cell's inflow. Because the losing liquid's face is zeroed at the source, its own donor-side `compute_s_out` sees zero outflow through that face too — conservation stays symmetric by construction, not by a Transport-side patch.

This is a scan-order tie-break (fixed priority), not a flux-magnitude contest — in a genuine multi-liquid race for the same air cell it can pick the smaller contributor as that tick's owner. That's a one-tick cosmetic ambiguity, not a conservation bug: once the cell holds real fill, it's an ordinary liquid voxel and the existing liquid-liquid gate takes over.

**Three call sites needed the identical gate** — `FluidSim._pass_accelerate`/`_pass_transport` (`fluid_engine.py`), `PhiFloodFluidSim.extra_correction_pass` (`phi_flood.py`, which independently redoes Pass A's update using `phi` instead of `head` and has its own full copy of the face-gating logic), and `ViscousFluidSim`'s per-material-knob overrides of both (`viscosity.py`, same reason). Missing any one of them would silently re-introduce the bug for that code path. **Rule to remember: any subclass that overrides `_pass_accelerate` or `extra_correction_pass` with its own copy of the face-gating logic (rather than calling `super()`) must carry every gate the base version has, kept in sync by hand** — there is no single source of truth enforcing this today.

Also caught in the same pass: `DensityFluidSim` (`density_stack.py`) was subclassing the pre-phi-flood base `FluidSim` instead of `PhiFloodFluidSim` — meaning all density-stacking bench validation up to this point wasn't actually running against the real shipped hydrostatics mechanism. Fixed by rebasing it onto `PhiFloodFluidSim`; full regression suite (`run_tests.py phi`, `test_viscosity.py`, `test_phi_demand.py`, `test_phi_demand_parallel.py`, `test_staircase_recovery.py`) re-run clean afterward, including `test_viscosity.py`'s bit-exact IDENTITY check confirming the new gate is a true no-op for every single-material scenario.

### FIXED (2026-07-10): three bugs caught while porting `phi_demand` sand↔water displacement to GLSL

Found while writing `shaders/demand_resolve.comp` and wiring it up in `simulations/granular_simulation.gd`, before any in-editor run — all caught by re-reading the code against known invariants, not by observed failures.

1. **GLSL int/uint mix.** `int remaining = (mat_amt >> 8) & 0xFFu;` mixes an `int` with a `uint` literal, which GLSL rejects. Fixed to `& 0xFF`. ### DIAGNOSED (2026-07-09): water "encapsulates" a falling sand mass — root-caused in the Python bench (bench-validated fix `block_combo` chosen, not yet ported to GLSL)

**Symptom (SAND_LIQUID_DENSITY_HANDOFF §2):** dropping a sand cluster into water makes water appear to wrap/climb the falling mass for ~8–10 ticks before settling normally.

**Root cause — NOT a logic bug and NOT primarily contention.** Reproduced on a faithful port of `granular_sim.comp` (`tools/fluid_prototypes/python/granular.py`, coupled granular→fluid per the engine ordering). Three measured components, in order of size: (1) *structural* — `try_displace_priority` levels 1/2 require an **air** cell adjacent to the impacted water voxel; submerged under a cluster footprint those cells are water (level 1) or the cluster's own sand (level 2), so level 3 fires almost every displacement (195 level-3 vs 35 level-2 in the 5x5x3 cluster scene) and teleports water up into the mass; (2) *swap-sinking interleave* — inherent to whole-voxel swaps: every sinking grain swaps one water voxel up behind itself, so a multi-layer mass pumps water up through its own interior one layer per tick; (3) *contention* — snapshot-A air cells lost to neighbouring grains' CAS, falling through to level 3 anyway (~3–4 events per impact; the handoff's headline hypothesis, real but minor). The handoff's stage-2 assumption ("pool wider than the footprint ⇒ level 3 never triggers") is wrong — "sideways" only sees the cells adjacent to the impacted voxel.

**Fix chosen in the bake-off (`block_combo`, see `tools/fluid_prototypes/python/SAND_DISPLACEMENT_NOTES.md` for the full matrix):** when the grain is buried (granular directly above) — (a) no air candidate in snapshot A → skip displacement unless `randf < 0.125` (percolation escape, prevents the sealed-plug deadlock that pure blocking causes); (b) air existed but every relocation CAS lost → `atomicExchange` the claimed water cell back to 0 (nothing logged yet — safe) and retry next tick. Halves interior pumping (peak 20→15 coupled, 18→9 granular-only), keeps single-grain/sealed-shaft/sealed-plug/conservation green. INVARIANT (level-3 fallback = `my_flat`) untouched.

**Failed approaches (don't retry):** wider lateral search (radius 2 + xz diagonals) — no help, distant cells are still water/sand; relocating water up the same-liquid column to the first air cell — no help, lifts water higher; hard blocking without the percolation escape — sealed 3x3 sand plug floats on water forever; "column hop" (water leapfrogs the sand stack to the air above it) — *worse*, hopped water lands on the still-falling mass and re-buries.

**Ceiling / rule to remember:** discrete air-targeted relocation cannot be artifact-free when submerged — there is no air to target, and any local answer either pumps water through the mass or piles it on top. The full fix is the handoff's §3 direction (hand displaced volume to the fluid solver as fill/flux, Phase 7e Step 8), where the pressure field can move volume *through* water.

**§3 explored same session, NOT adopted — see `tools/fluid_prototypes/python/SAND_DISPLACEMENT_NOTES.md` §5 for the full writeup.** Built the Step 8 impulse mechanism (`granular.py mode="impulse"` + `cavitation.py`'s `ImpulseFluidSim`) to check "if we're bench-validating anyway, does the real fix beat block_combo." Found and fixed a real mass-creation bug first: anchoring the impulse at the impact cell (now sand, but conventionally still stores `fill=255`) makes `compute_s_out` treat it as a full liquid donor with no material check, materializing water at neighbours from nothing (+928 fill/tick measured) — the impulse must anchor on the cell that actually holds the displaced water (`my_flat`/`gpos`), not the collision point. With that fixed, the mechanism does NOT beat `block_combo` on this symptom at any tested magnitude (0–220): a single unconfined water voxel already fully disperses in 1 tick via existing gravity/head flow with no impulse at all, and in the cluster scene the ~9-tick artifact duration is set by the avalanche's own landing cadence, not by dispersal speed — confirmed by a hybrid test (block_combo + impulse-on-fallback) that changed peak_interior by exactly 0. `block_combo` remains the recommendation for §2; the impulse mechanism is the right architecture for Step 8's actual motivating use case (splash/jet feel) but is a different fix for a different problem, not a substitute here.

### FIXED (2026-07-10): sand's diagonal fall into water skipped sideways-displacement priority — always teleported water straight up

**Symptom:** Sand displacing water via a diagonal fall (4 shuffled diagonal-down candidates in `granular_sim.comp`) always relocated the displaced water directly to the sand's old position (one level up, offset back toward where the sand came from) — never attempted to push the water sideways first, unlike the straight-down fall path a few lines above it, which already tried sideways at two levels before falling back to "up." `ARCHITECTURE.md`'s Phase 7b section claimed "same pattern applied to the 4 diagonal-down destinations," which was not true — a doc/code mismatch, not just a behavioral gap.

**Root cause:** the straight-down path had its 3-level priority logic written inline, specific to `below`/`gpos` as fixed reference points. The diagonal path called a separate, simpler helper, `try_displace` (no priority — CAS the destination, unconditionally write water to `my_flat`), because generalizing the inline logic to an arbitrary diagonal destination wasn't done at the time.

**Fix:** replaced both the inline straight-down logic and the raw `try_displace` helper with one function, `try_displace_priority(water_pos, my_voxel, their_voxel, my_flat, vpc, lat)`, parameterized by the liquid's actual position (`water_pos`) instead of assuming it's `below`. Both the straight-down and diagonal-down call sites now use it identically. Level 1 = sideways at `water_pos`'s height; level 2 = sideways one level above `water_pos`; level 3 (last resort) = `my_flat` unconditionally.

**Rule to remember (the safety invariant that made this fix non-trivial):** the level-3 fallback target must ALWAYS be `my_flat` (this thread's own exclusive, provably-free source slot), never a newly-CAS'd cell like "directly above `water_pos`" (which would differ from `my_flat` in the diagonal case). The original straight-down code's `my_flat`-fallback is only safe *because* `my_flat` is guaranteed free by construction (no CAS needed) — generalizing the fallback target to something that requires its own CAS would let that CAS lose a race, leaving the granular voxel's destination claimed with nowhere for the displaced liquid to go: a silent mass-conservation bug, not a cosmetic one. This is the same class of "guaranteed-free vs. must-be-CAS'd" reasoning that has repeatedly mattered in the fluid-flux work elsewhere in this file — don't relax a provably-safe unconditional write into a racy one without re-deriving why the original was safe.

### DESIGN (2026-07-08): connected-vessel hydrostatics — SOLVED IN THE FAITHFUL 3D PYTHON PORT via phi-flood (max-flood piezometric pressure + hydraulic slope + deficit suction + pressure-wave wake)

**Status: validated in `tools/fluid_prototypes/python/` (the 1:1 port of `fluid_flux.comp` + `fluid_simulation.gd`), not yet ported to GLSL.** `PhiFloodFluidSim` (`phi_flood.py`) passes all 5 acceptance criteria of `docs/CONNECTED_VESSEL_HANDOFF.md` §4, including the two that were never passed together before: first-fill equalization by per-arm MASS (gap 270 of 11475 poured, surface gap 0) **and** post-settling reactivity (second pour into arm A raises arm B, both settle to the same new level). Verified on the small rig (cs=8), a cs=16 tall-arm rig, and a cs=8 long-connector rig (gap=24, connector spanning 4+ chunks). Gross staircases (`51/255/19/255/7/255`) self-correct to monotone in ~50 ticks and the system then sleeps; residual inversions are bounded by `max(1, settle_threshold-1)` fill units, which is the substrate's own rest tolerance (1 unit = accel 0.45 rounds to zero; transfers < `settle_threshold` are invisible to the sleep scheduler by design — verified: with `settle_threshold=1` the residual is exactly 1). Conservation untouched (fix only rewrites Pass-A flux lanes; `compute_s_out`/`compute_s_in`/Transport unchanged).

**The field.** Per liquid voxel, per material, re-derived from current `voxels_a` every tick (no persisted state → reactivity is automatic): every free-surface cell (fill<255 or non-same-liquid above) seeds `P = fill`; then a bounded Jacobi **max**-flood over same-liquid neighbours with costs (all subtracting the RECEIVER's deficit `FILL_CAP − fill(p)`): down-step `+fill(p) − deficit(p)`, up-step `−FILL_CAP − deficit(p)`, horizontal `−EPS_H − deficit(p)` (`EPS_H = 4`). Pass A's `dh` then uses `P(p) − P(nb)` instead of `head(p) − head(nb)`; everything else identical. Deficit terms vanish on full cells, so own-column paths reproduce `head()` EXACTLY for settled bodies — feel preserved by construction. Two wake-loop bugs were fixed against the initial cost model (down-step missing the deficit; up-step costed `fill(q)` instead of `FILL_CAP`) — both let slightly-deficient submerged cells read as permanently over-pressured yet uncorrectable; see `phi_flood.py`'s inline comments.

**Why max-flood works here when Build B's max-relaxation was falsified:** two added terms do the physical work. (a) `EPS_H` per-hop horizontal cost keeps the field from being uniform-at-elevation — the tall arm's ramp invades the connector *decaying per step*, so adjacent connector cells always differ and flux forms along the whole pipe (the exact gradient max-propagation erased). (b) The fill-deficit "suction" term is the flood-form analogue of the Chorin bench's load-bearing density-correction source: a cell that just donated reads lower P than its full neighbours, so refill flux forms behind it and mass genuinely convects through the saturated pipe (bucket brigade) instead of the far arm's surface draining into a thin smear. Steady-state equalization error is bounded by `EPS_H·path_len/255` cells (sub-voxel for game-scale pipes) because the invading ramp UNDERSHOOTS at balance — the safe direction.

**Second structural bug found (would have bitten ANY correct field): the sleep scheduler is connector-blind too.** On the long-connector rig the discharge endpoint (far arm's surface) sits several chunks outside the dispatch frontier while every cell INSIDE the frontier is saturated — zero transfers occur, nothing marks dirty, and the idle-guard puts the rig to sleep 4 ticks after the pour with the imbalance intact (measured: arm A y=8 vs arm B y=2, asleep, forever). Fix: the flood runs over the whole loaded liquid set (it is read-only on `voxels_a`, so sleeping chunks are safe), and any REAL free-surface cell (air above or partial — sealed-full cells never qualify, so static pressure under rock can't churn) with `P − fill > WAKE_MARGIN (=64)` wakes its chunk. At equilibrium the signal is exactly zero (seeds win), so sleeping still works — verified `active=0` end states on every rig.

**Harness bugs fixed the same day (`run_tests.py`):** (1) the equalization threshold compared per-arm mass (fill units) against `water_poured` (a raw voxel count) — demanding equalization to 0.04 voxel, unsatisfiable by any solver; (2) the staircase metric's comparison was inverted, flagging every normal full-below/partial-top column and passing true staircases. Rule to remember: **sanity-check a metric against a known-good hand case before trusting its verdict on a fix** — the base system scored "0 staircases" only because it never transports anything in the U-tube at all.

**GLSL port sketch:** see the 2026-07-08 session report / `tools/fluid_prototypes/python/README.md`. Summary: one paged s32 phi buffer (ping-pong), a Seed pass + K Jacobi flood steps (barrier-separated in ONE submit — no extra CPU syncs; per-tick submit/sync count stays at 2), Accelerate reads phi instead of calling `head()`, flood dispatch range = liquid-bearing chunk component (chunk-granularity CPU BFS), wake rule via the existing dirty-bitmask machinery. Under-converged phi degrades gracefully toward `head()` behaviour (never overshoots), so K can be small and amortized.

### PORTED & VERIFIED IN-EDITOR (2026-07-08): phi-flood GLSL port — U-tube equalization/reactivity confirmed on the real KEY_U rig; one open bug found and reverted

**Status: ported to `shaders/fluid_flux.comp`/`simulations/fluid_simulation.gd` (passes 2/3/4 = PhiSeed/PhiFloodStep/PhiFloodStepFinal, two new paged phi buffers riding the existing flux page lifecycle, `phi_flood_iterations` export) and confirmed working in-editor on `KEY_U` — both first-fill equalization and post-settling reactivity, the two criteria no prior attempt ever passed together, hold on the real rig. One real bug (the "flat lake ripple," below) was found during broader in-editor testing; a fix was attempted and reverted the same session after it broke the core mechanism — left open.**

**K (flood iterations) needed raising from the Python bench's default.** The bench's own small test rigs converged with K=16 (avg 7/max ~30 hops measured there), but `world.gd`'s real `UTUBE_ARM_HEIGHT = 32` needs a per-tick reach budget covering roughly (down one arm) + (across the connector) + (up the other arm) — confirmed empirically: K=16 left the U-tube stably ~2x mass-imbalanced (not still converging — a genuine per-tick reach shortfall, since phi is re-seeded and re-flooded from scratch every tick with nothing persisted across ticks, so two seeds farther apart than K can never connect, full stop, no matter how many ticks pass); K=32 fully equalized it. Shipped default raised to `phi_flood_iterations = 40` for headroom. Under-convergence is still safe at any K — phi degrades toward `head()`, never overshoots, a too-small K just produces a stable but uneven rest, never an explosion.

**BUG (found 2026-07-08, in-editor, REVERTED same day): the "flat lake ripple."** Placing one full water voxel directly on top of an already-settled, full flat lake radiated a spurious pressure wave across the *entire* lake in a single tick — a wide "crater" ring (fill 1-5) draining a huge area, wildly out of proportion to one voxel's mass. A single voxel dropped from above (falls, materializes gradually via Transport) did not trigger it; only an instant full-fill (255) edit directly on an already-full surface did — and placing water on bare rock (no existing water body) didn't either.

*Root cause:* the seed rule ("`fill<255`, or the cell above isn't the same liquid") conflates two physically different situations. A cell exposed to AIR is the true local free surface — real excess there just raises the water level, never manifests as trapped pressure. A cell sealed under ROCK (the U-tube connector, exactly) is *not* a true surface — an interior point of the connected body that legitimately needs its phi inflated by a taller connected column; that's the entire point of the fix. The pile's genuinely higher head at the one true physical interface (its now-submerged former-top cell vs. a flat neighbour's still-open top — a real `head()`-matching 255-unit difference, confirmed by hand-tracing the numbers) was allowed to keep "leaking" sideways *through* the flat neighbour's own perfectly valid reading via `max()` — hop after hop, losing only `EPS_H=4` each time — radiating fake pressure dozens of cells wide in one tick, something stock `head()` (which never looks sideways at all) structurally cannot do.

*Fix attempted and reverted:* `phi_is_true_surface()` (a cell open to air/different-liquid/genuinely partial is protected — phi pinned to its own fill, never touched by flood candidates; a cell sealed under solid remains flood-eligible). This bench-verified the ripple was contained (`tools/fluid_prototypes/python/test_pile_ripple.py`, disturbed radius 0) — **but broke the U-tube's core mechanism outright** (equalization/reactivity both back to FAIL). Diagnosed via `diagnose_utube.py phi`: phi correctly propagated from arm A across the connector, then hard-stopped at the base of the still-*empty* target arm's shaft, flat at 255 — because that cell is *also* "exposed to air" (nothing has arrived there yet, so it reads as a protected true surface), capping its `dh` at exactly its own fill: precisely stock `head()`'s value, precisely what fails this test. **This is a structural conflict, not a tuning slip:** a single cell's local state (its own fill, what's directly above it) cannot distinguish "a coincidental neighbour that's already correctly at rest" (the lake bug — inflating it is wrong) from "a dry arm base that genuinely needs this exact inflation to know it should rise" (the U-tube fix — the entire mechanism *is* this inflation). Both are, structurally, "a cell exposed to air receiving an inflating horizontal candidate from a same-elevation neighbour." Only information about a genuine connected-body imbalance *further away* distinguishes them — exactly the non-local information the flood exists to carry, which by definition isn't visible to a single-cell local check.

**Rule to remember:** when a fix for one failure mode requires blocking non-local propagation into "cells that look locally like a rest state," check whether the target mechanism ALSO relies on inflating cells that look identical locally but aren't yet at rest (a not-yet-filled discharge endpoint, in this case) — the two can be indistinguishable without the very information the mechanism exists to provide, making a purely local fix structurally impossible.

**Left open for whoever picks this up:** `tools/fluid_prototypes/python/test_pile_ripple.py` reproduces the bug as a regression test (currently un-passable without breaking the U-tube tests, by design, until a real fix exists). Both `phi_flood.py`'s module docstring and `fluid_flux.comp`'s `phi_seed_floor()` comment carry the full analysis and a candidate direction: bound the *magnitude or propagation speed* of a disturbance (e.g. scale `EPS_H`'s effective reach to the size of the imbalance actually being carried, or cap how far a **single edit's** worth of excess can travel per tick) rather than blocking the mechanism by cell classification — so a small, local edit can't outrun what stock `head()`'s own one-hop-per-tick diffusion would do, while a genuine large connected-body imbalance (the U-tube's real use case) still gets through. Not attempted this session; a real design pass, not a quick patch.

### DESIGN (2026-07-04): connected-vessel hydrostatics — SOLVED IN A 2D BENCH via pressure projection; four cheaper approaches falsified first

**Status: validated design, not yet ported to GLSL.** After Build B (below) was reverted, the U-tube/connected-vessel problem was worked out from scratch in a standalone 2D Python emulator (a faithful bench: same owned-face flux model, same conservative `s_out`/`s_in` transport as `fluid_flux.comp`, plus a strict per-arm-mass + full-column + mass-conservation test suite). The bench falsified **four** successive approaches with concrete mechanisms before landing on one that passes every invariant. This entry records all of it so the next attempt doesn't re-walk the dead ends — **especially so nobody rebuilds a max-relaxation field like Build B again; the bench proves that whole family cannot work, and explains exactly why.**

**The core requirement the bench isolated:** the solver needs *a spatial pressure gradient generated by the current mass imbalance* — not a propagated maximum height. Any method that produces a pressure/head field which is uniform-at-each-elevation across a connected body has, by construction, deleted the lateral gradient that must drive water from the heavy arm to the light one.

**The falsification ladder (all ruled out, do not retry):**

1. **Narrow "static lift into air" correction (Y-only, gated on local equilibrium).** Fails two ways, both proven in-bench: (a) a *full horizontal pipe* has zero head gradient (every cell reads `head=255`, air above) so dynamic flux physically cannot route the tall arm's pressure across it; (b) the instant a lift starts, the donor goes partial and local `head()` sees an "unsupported" column and pulls it back down. Can't route, can't climb.
2. **Deficit toward a surface-elevation field (`L = y + fill/255`, fill cells below `L`).** Conserves mass but **smears**: a single scalar surface elevation can't tell "supported by a connected column" from "should pool lower," so water spreads as thin partial films up to the stale surface instead of pooling full. Also `L` (a no-decay max) never lowers when the source arm drains.
3. **`P` replaces `head()`, `P` = max-with-cost relaxation (`+FILL_CAP` per upward hop, propagate through liquid), rebuilt per tick from live seeds.** This is the **Build B family done more carefully** — and it is *equilibrium-correct but dynamically dead*. `max`-propagation computes a reachable upper envelope, so once it fills a connected region with the same maximum potential it makes `P` **uniform at each elevation** → the bottom-pipe horizontal gradient is exactly zero → the arms freeze lopsided (measured: bottom-row `P = [2040,2040,2040,2040]` at a 2:1 mass imbalance). **This is why Build B never worked, now isolated on a bench rather than guessed at.** No tuning rescues it; the defect is the `max` operator, which erases gradients. Rule: **never use a max/envelope-propagated field to *drive* equalization flow.**

**What finally worked — quasi-static pressure projection (Chorin) on the fill field.** Pressure is a *constraint correction to a provisional flux*, recomputed every tick, never stored as momentum; transport stays the only thing that moves fill. Per-tick pipeline:
- **Provisional gravity flux**, scaled by the water's actual **weight** (`fill`), on faces with liquid above (a flat constant gives a topology-only field that can't distinguish arms).
- **Divergence of that provisional flux** as the base RHS — this is what differs between a tall and a short arm and generates the lateral gradient.
- **Density-correction source** `STIFF·(FILL_CAP − fill)` on **submerged** cells (liquid directly above), **masked off at the free surface** (air above). Without this term: a thin column sits in false hydrostatic equilibrium and never fills (the "constant-at-elevation" trap). *Unmasked*, it force-fills legitimately-partial surface cells and breaks the rest state. **Both the term and the mask are load-bearing** — the bench fails specific invariants if either is dropped.
- **Iterative pressure solve** (`∇²P = RHS`) with BCs: `P = 0` at liquid→air (free surface, Dirichlet); solid **and** withheld/unavailable chunk pages are **sealed** (Neumann, face dropped — *never* treated as air/`P=0`, same rule as the dispatch-range fix below); air excluded from the domain.
- **Correct** `F = u* − ∇P`, feed the existing conservative `s_out`/`s_in` transport unchanged.

**Bench invariants it passes (the regression suite for any future port):** pressure-null at rest (corrected flux exactly 0 on a settled column); **bottom-pipe gradient exists** under unequal arms (the direct anti-test for the max-field failure); flat-lake no-op; **U-tube equalizes to level-matched FULL columns**, per-arm mass balanced, mass-exact; final level **independent of pipe length** (no horizontal decay); unsupported thin film drains instead of pinning; settled partial-surface column stays dead quiet (no churn). Conservation drift was `0.000` in every test, including the broken ones — the `s_out`/`s_in` transport is mass-exact by construction regardless of the driving field, which is what let the bench cleanly attribute every failure to the *field*, not the transport.

**⚠️ Metric pitfall — judge equalization by PER-ARM MASS, never `column_top` (this fooled a reviewer, and fooled the author three times):** a lopsided *thin smear* reaches the same column HEIGHT in both arms at very different DENSITIES, so `column_top` (or "median submerged fill over both arms") reports "equalized" while the arms hold very different amounts of water. The correct falsifier is per-arm mass (`sum(fill)/FILL_CAP` per arm column) plus a fill-profile dump. Approach #3 (max-relaxation) *looks* equalized by `column_top` on both the pre-filled-pipe and empty-pipe geometries (`column_top` ≈ equal in both arms) but has arm-mass imbalance ≈ 2–3 with a checkerboarded thin profile — that is the falsification, and it holds on the harder empty-pipe case too (water must migrate across an initially-empty connector; it still ends lopsided). Note: `tools/fluid_prototypes/utube_pressure.py` originally shipped with weak `column_top`-based tests that printed a **false** `ALL TESTS PASSED`; it has been rewritten to self-demonstrate the falsification via the strict metric (`demo_max_relax_falsified()` → `FALSIFIED AS DOCUMENTED`). Do not trust a green "pass" without a per-arm-mass check and a profile dump — build both into the in-engine acceptance scene.

**GPU-port plan (tiered; the cost lives entirely in the solver, so optimize the solver's DOMAIN, RESOLUTION, ITERATION SCHEDULE, and INITIALIZATION — never weaken the pressure model, the RHS, or the surface mask, which the bench proved are doing real physical work):**
- *Tier 1 (do first, fits the existing sparse+substep architecture):* **(a) active-region mask** — only solve pressure-active liquid (nonzero divergence, near a free surface, near a topology/fill edit, or in the halo of an active cell); this is a direct extension of the existing `_build_flux_chunk_list`/idle-guard sparsity, and the "inactive/withheld neighbour = sealed, never air" rule is *literally* the dispatch-range fix already in the code. **(b) temporal amortization** — run a few local solve iterations every tick (kills compression artifacts/thin-film-pinning immediately) and let long-range connected-vessel pressure crawl over *many* ticks via warm-started partial solves + residual-driven adaptive iteration counts (`priority ≈ max(|div|, |fill−FILL_CAP|, surface proximity)`, a "needs-more-solve" bit per page). A U-tube taking ~0.5s to equalize is invisible to a player; a one-frame explosion is not. This is also the only lever that reduces the **per-tick dispatch/sync count** (each solve iteration is a dispatch+sync; active-masking shrinks work-per-dispatch but not the number of syncs).
- *Tier 2 (later, gated on evidence):* coarse `2³` pressure grid for **bulk** bodies only (a `4³` block *erases* a 1-voxel pipe — dangerous for the exact plumbing case this whole effort targets; only safe if gameplay channels are reliably ≥2–3 voxels wide — an open design question); lightweight multigrid V-cycle for long pipes (principled, but real implementation risk on a sparse/irregular/free-surface domain — defer until temporal amortization is shown insufficient).
- *Tier 3 (optional, maybe never):* graph "pipe mode" — collapse degree-2 liquid chains into graph edges and solve a small graph Laplacian over junctions. Strong for long 1-wide plumbing, lots of edge cases; temporal amortization likely makes it unnecessary.

**Shader-specific caveat the roadmap must respect:** the bench used **serial SOR (Gauss-Seidel, `ω≈1.7`)**, which *does not exist on a GPU* (sequential dependency). The port must use **red-black Gauss-Seidel** (checkerboard coloring: update red reading black, then black reading red — parallel, keeps most of SOR's convergence rate) or plain **Jacobi** (ping-pong buffers like `voxels_a`/`voxels_b`, ~2× more iterations). **The iteration counts measured in the bench will not transfer** — re-measure convergence in a red-black/Jacobi bench before sizing the GPU iteration budget.

**Where the validated 2D emulator lives:** built in the session scratchpad (`utube_projection.py` plus the falsification-ladder files `utube_emulator.py`, `utube_pressure.py`). Scratchpad is ephemeral — the design above is complete enough to rebuild it, but the emulator is worth committing into the repo (e.g. `tools/fluid_prototypes/`) as a permanent regression rig before the GLSL port, since it's what will tell us whether the 3D/red-black version still passes the invariants.

### REVERTED (2026-07-04): "Build B" connected-vessel hydrostatics (persistent piezometric-head relaxation field) — handed off for a different approach

**Status: reverted in full, verified clean.** `fluid_flux.comp` and `fluid_simulation.gd` are back to the pre-Build-B state (matching commit `ac86f04`, "Compress fluid flux pipeline from 4 GPU passes to 2"), except that one independently-discovered bug fix (below) was kept. In-editor re-testing after the revert (sphere drops, pouring, settling) confirmed the baseline is stable again: no growth, no leaks, no cellular-automaton-style artifacts. This entry documents what was tried, what broke, and why it was abandoned rather than iterated on further — so the next attempt (handed to Fable) doesn't retread the same ground. **The underlying U-tube/connected-vessel hydrostatics goal is still unsolved.**

**Original goal:** the fluid pipeline settles flat lakes and falling water correctly but fails the classic U-tube test — pour water into one arm of a U-shaped pipe and it never climbs the other arm to find its level, because `head(p, mat)` is a strictly-local, straight-up-only column scan with zero visibility into pressure queued behind a horizontal connection (full derivation was in this entry before the revert; see git history of this file if needed).

**What was built:** `phead(p)` — a new, persistent, relaxation-maintained field standing in for `head()` in the accel formula's `dh` term only. Maintained by a new first pass, Relax-phead (`params.pass == 0`, shifting Accelerate to 1 and Transport to 2): `phead_new(p) = max(head(p), max(0, neighbour_max - PHEAD_DECAY))`, where `neighbour_max` is the elevation-adjusted max over same-liquid 6-connected neighbours' last-tick `phead`, `PHEAD_DECAY = 4` a flat (not multiplicative) per-hop decay. Validated first in a standalone Python prototype (vertical-column/flat-lake no-regression, U-tube propagation, drain-recovery, Jacobi/Gauss-Seidel parity all passed) before being ported to GLSL. New buffer `_phead_buf` rode the same page allocation as `_flux_buf`.

**What went wrong in real in-editor testing (not caught by the Python prototype or small-scale single/two-voxel GPU tests, which all matched predictions exactly):**

1. **Severe mass loss at scale.** Dropping a sphere into a multi-chunk-deep "test tube" dug through rock caused total fill (`debug_dump_fluid_stats`) to collapse across five `F6` snapshots: 972188 → 261744 → 27711 → 5155 → 1919 (>99% of the water). Root cause found and fixed (kept after the revert, see the entry below): `compute_s_out`/`compute_s_in` (from the 4→2 compression, not Build B itself) can read a cell 2 hops from the dispatching thread, but the per-tick dispatch range only guarantees 1-hop visibility — a cell outside that radius was treated as "unlimited capacity" instead of "unknown," a silent leak that `phead`'s much-wider, persistent pressure propagation triggered constantly (where `head()`'s narrow local-only reach rarely had before).
2. **The leak fix alone did not resolve the underlying behavior.** After applying it, further testing (sphere dropped into a dug test-tube shaft) still showed: water visibly "boiling" — voxels launched upward above the surface, falling, sticking, bubbling up again, repeating in a cycle; continued substantial mass loss even with the dispatch-range leak closed; and, per the most direct test (pour into one side of a narrow connected shaft), water spraying out the top of one arm rather than equalizing with the other — i.e. the core U-tube goal (level-matching between connected arms) still did not work correctly, and the system was actively unstable rather than merely imprecise.
3. **Assessment:** the max-relaxation `phead` design is likely fundamentally mismatched with the existing Accelerate/Transport tuning (`g_dt`, `gravity_bias`, `axis_cap`) — those were calibrated against `head()`'s narrow, single-column-bounded range, and `phead`'s legitimately much larger magnitude for real connected bodies (potentially many thousands of fill-units for a multi-chunk-deep body, vs. `head()`'s low hundreds) seems to overdrive them into oscillation rather than settling. This was a working hypothesis at the time of the revert, not confirmed — worth investigating directly if picked back up.

**Decision:** rather than continue iterating on `phead`/Relax-phead in place, the whole approach was reverted back to the known-working 4→2-compression baseline, and the connected-vessel hydrostatics problem is being handed to Fable for a fresh design pass. The glass material and its raymarch rendering (added the same session, for visually inspecting exactly this kind of test — see the Current To-Do entry) were kept; they're independent of the fluid physics and still useful for whatever hydrostatics approach comes next.

### BUG (FIXED, 2026-07-08, kept after the Build B revert above): `compute_s_out`/`compute_s_in` treated a dispatch-range boundary as "unlimited capacity" instead of "unknown" — real mass leak, not Build-B-specific

**Status: fixed and verified.** Reapplied on top of the reverted (pre-Build-B) `fluid_flux.comp`. This bug lives in the 4→2 pass compression itself (`ac86f04`), not in Build B — Build B just happened to trigger it far more often (see above), which is how it was found. In-editor testing with the reverted-to-baseline fluid pipeline (sphere drops, pouring, settling) confirmed the fix holds cleanly on its own, with no growth/leak/CA-artifact regressions.

**Root cause:** `compute_s_out(X, ...)`/`compute_s_in(X, ...)` each read `X`'s own page via `resolve_page_local`, and — per their own header comments — can be called on a cell up to **2 hops** from the Transport thread that invoked them (Transport calls `compute_s_in(receiver)`, which internally calls `compute_s_out(donor-of-receiver)`). But the per-tick dispatch range (`_build_flux_chunk_list`, `fluid_simulation.gd`) only ever includes **active chunks + their 1-hop face-neighbours** — chunks further out get their `flux_page_table` entry deliberately unmapped (`-1`) for the tick, even if they hold real, persistent flux/fill state from previous ticks (this per-tick unmap/restore is intentional and correct elsewhere — see the dispatch-range-leak fix referenced in `_build_flux_chunk_list`'s own comment). Both functions had `if (page < 0) return 1.0;` for this case — "assume full capacity" — which let a Transport thread credit or debit fill against a neighbour-of-a-neighbour that was invisible this tick and therefore *never dispatched to apply the matching half of the transfer*. Fill vanished (or, at a receiving boundary, appeared from nowhere) exactly at the edge of the 1-hop dispatch radius.

**Fix:** flip both early-outs from `return 1.0;` to `return 0.0;` — "cell outside this tick's visibility ⇒ assume no capacity ⇒ don't transport across this boundary this tick," instead of assuming unlimited capacity. This stalls flow at the dispatch-range edge for at most one tick and self-heals once the frontier chunk becomes active/mapped next tick (same self-healing philosophy as the pre-existing page-allocation-up-front fix documented in `_build_flux_chunk_list`). No dispatch-range widening needed, and no change to `compute_s_out`/`compute_s_in`'s existing legitimate `total_in <= 0.0 → return 1.0` case (that one means "no inflow at all," not "cell invisible this tick," and is unaffected).

**Rule to remember:** any function that can read state belonging to a cell *further away than the current pass's guaranteed dispatch radius* must treat "can't see it" as "assume the worst / no capacity," never "assume the best / unlimited" — the former fails safe (a one-tick stall), the latter fails as a silent, unbounded mass leak that only shows up once some driving force pushes real flux that far (in this case `phead`, but any sufficiently strong forcing term could trigger the same gap).

### BUG (FIXED, 2026-07-03): exported .exe renders black — shader `.comp` files not bundled into the PCK

**Symptom:** In-editor everything renders correctly. After exporting a standalone Windows `.exe` (Project → Export, "Water Simulation" preset), the running game is **completely black except for the player sphere and the UI** — the entire voxel world is missing. No crash, no visible error window.

**Root cause:** Every compute shader in this project is a plain-text `.comp` file loaded at runtime via `FileAccess.open("res://shaders/*.comp", FileAccess.READ)` and compiled from source through `ComputeHelper.compile_shader*` (see `RaymarchRenderer._shader_source()`, `WorldOrchestrator`, `edit_dispatcher`, `granular_simulation`, `fluid_simulation`). These files have **no `.import` sidecar** — Godot does not treat them as resources. The export preset used `export_filter="all_resources"` with an empty `include_filter`, and `all_resources` only bundles *imported resources* (`.tscn`, `.gd`, textures, …). Non-resource files like raw `.comp` are included **only** if they match `include_filter`. With it empty, `res://shaders/*.comp` was absent from the exported PCK. At runtime `FileAccess.open` returned `null`, so `RaymarchRenderer._shader_source()` returned `""`, SPIR-V compilation failed, and the raymarch pipeline never ran → black screen. The player sphere (a real mesh node) and UI (CanvasLayer) don't go through the raymarcher, so they still drew. This affected *all* shaders, not just the raymarcher — it's just the most visible one.

**Fix:** Set the export preset's non-resource include filter (`export_presets.cfg`, and equivalently the Export dialog → Resources tab → "Filters to export non-resource files/folders to include"):
```
include_filter="shaders/*.comp, shaders/*.glsl"
```
Re-export. Verify by running the exported build with the console wrapper (`debug/export_console_wrapper=2`, already on) — no `RaymarchRenderer: failed to load shader` push_error and a rendered world means the files are bundled.

**Rule:** Any file loaded via `FileAccess.open("res://…")` rather than `load()`/`preload()` is a *non-resource* file as far as export is concerned and will silently be missing from the exported PCK unless it matches the preset's `include_filter`. When adding a new raw asset (shader, JSON, CSV, etc.) loaded by path, extend `include_filter`. Alternative long-term fix (not taken): rename shaders to `.glsl` and load them as `RDShaderFile` resources so `all_resources` picks them up automatically and Godot's `#include` preprocessing becomes available.

**Loose end worth tightening (not required for the fix):** most shader loaders dereference the `FileAccess` handle with no null check (`edit_dispatcher`, `granular_simulation`, `fluid_simulation`), so in the broken export they would have thrown "Cannot call method 'get_as_text' on a null value" instead of failing gracefully like `RaymarchRenderer` does. Adding a null guard + `push_error` to each would make a future missing-file misconfiguration self-diagnosing.

### CHANGED (2026-07-06): fluid pipeline compressed from 4 GPU passes to 2 (Accelerate → Transport)

**Status: implemented and verified** (settled-lake zero-flux check, pour/spread/settle, and — after the dispatch-range leak fix a few entries above — stable at scale with no growth/leak/CA artifacts, confirmed 2026-07-04). Not a bug fix — a structural simplification of the passes described in the Scale-Inflow entry below. `Scale-Outflow` and `Scale-Inflow` used to each be their own fully-synced dispatch, rewriting `flux_buf` lanes (once scaled for the donor's outflow budget, once more for the receiver's inflow budget), which required a careful sign-based proof that no two invocations ever wrote the same lane in the same pass (see that proof in git history / the Scale-Inflow entry below).

**The change:** neither scale factor is written to a buffer by its own pass anymore. `fluid_flux.comp` now has `compute_s_out(gpos)`/`compute_s_in(gpos)` — pure, read-only functions of that tick's already-synced `flux_buf` + `voxels_a`, callable for *any* cell, not just "my own". Transport calls these inline for itself and for whichever neighbor is the true donor/receiver of each of its 6 relevant faces (`compute_s_out` only ever needs a 1-hop neighborhood; `compute_s_in` calls `compute_s_out` on up to 6 neighbors, so from Transport's thread it's a bounded 2-hop lookup, never deeper — no recursion risk). Because both endpoints of a shared face compute the identical deterministic function of the identical stable inputs, conservation holds exactly with zero shared writes and zero races — no proof needed, purity does the job instead of careful bookkeeping.

**Why this is safe re: the sub-threshold trap bug (see MIN_FLOW/eff_flux history further down):** `eff_flux()`'s read-side deadzone is unchanged and still applied identically everywhere `flux_buf` is read (Accelerate's decay, `compute_s_out`, `compute_s_in`, Transport's final delta) — the fix for that bug never depended on which pass did the reading, only on both sides reading through the same threshold function, which is still true here.

**Semantic change worth watching:** since nothing but Accelerate ever writes `flux_buf` now (no Scale pass clamps-and-rewrites it mid-tick), a persistently unservable lane no longer gets nudged toward zero by that rewrite. It's still bounded every tick by Accelerate's own `axis_cap` clamp, so it can't grow unboundedly, but it may sit at a stable nonzero raw value indefinitely if the underlying head difference driving it never resolves (e.g. a permanently pressurized face into an already-full receiver) — this is the physically correct behavior, not a regression, and it structurally deletes the "Scale-writeback oscillating trap" bug class described below (nothing rewrites `flux_buf` mid-tick anymore, so that race can't recur).

### FIXED (2026-07-04, root cause found 2026-07-03): fluid never fully settles — no hydrostatic equilibrium in Pass A's vertical forcing

**Status: fix applied 2026-07-04, verified in-editor same day — CLOSED.** `shaders/fluid_flux.comp`'s Pass A Y-axis accel now uses `(dh - FILL_CAP) * g_dt * gravity_bias` instead of `dh * g_dt * gravity_bias - gravity_force`. `gravity_force` is deleted entirely — the `@export` in `fluid_simulation.gd`, the `SimParams` field in the shader, and the corresponding byte in `_flux_params_buf`/`_upload_flux_params()` (struct/buffer shrunk 56→52 bytes, `settle_threshold`'s offset shifted 52→48 accordingly). No other pass changed — `axis_cap`, the truncated-decay logic, and the neighbour-page dispatch check were all confirmed unrelated to this bug.

**Verification (2026-07-04, in-editor, all 3 scenarios confirmed):**
1. Flat lake at rest: a watched voxel below the surface read `fill=255, flux=(0,0,0)` on load, with zero movement — no oscillation, exact fixed point, matching the emulator's prediction.
2. Pouring water onto the settled surface: spreads outward, forms a low-fill film on top of the stable sheet, and fully settles back to quiet within roughly a minute — no runaway, no standing oscillation.
3. Disturbing a settled surface near a watched voxel (sphere destruction/removal nearby): the watched voxel stayed rock-stable at `fill=255, flux=(0,0,0)` throughout the entire disturbance, completely undisturbed by the chaos a few voxels away. The large per-tick `[Conservation]` numbers during the disturbance are legitimate redistribution of displaced water re-settling (they taper off and stop as the region restabilizes), not a resurgence of the old leak.

Also added this session: a red wireframe indicator box (`world.gd`, tracks `FluidSimulation.watch_chunk`/`watch_local`, visible through geometry via `depth_draw_never`) so the watched voxel is visible in-game while testing, reusing the existing `_cursor_indicator` pattern from `player_controller.gd`.

**The actual mechanism:** Pass A's Y-axis accel is `dh * g_dt * gravity_bias - gravity_force`. `head()` is pressure head only (fill + column above). For two vertically stacked at-rest full cells (B below, A above), `head(B) - head(A)` is **always exactly 255** — not zero. So a column at perfect hydrostatic rest generates a constant, nonzero forcing on every interior vertical face, every tick, forever (with this session's defaults: `255*0.15*3.0 - 10 = +104.75`, upward). `gravity_force` is a flat constant bolted onto the force term instead of something that scales with and cancels against the pressure term the way real hydrostatic balance requires — so "rest" was never actually a fixed point of the system.

Mechanically, this produces exactly what `FluidWatch` showed: interior faces request the same residual every tick, Scale-Inflow clamps it back to 0 (receiver has zero capacity), Pass A re-integrates the same residual from 0 next tick — looks quiet but is permanently spring-loaded. At the *surface* (a full cell below a partial cell), a few units actually transfer up each tick, which drops the full cell below 255 — and `head()`'s walk treats a non-255 cell as "the surface," so `head()` collapses discontinuously (255+f → ~254), flipping the force's sign. Scale then clamps the reverse flow to exactly the deficit, restoring the full cell to exactly 255 — repeating the cycle forever. This is why `damp` was irrelevant to the whole session's tuning attempts: the oscillation isn't underdamped momentum, it's regenerated from scratch every half-cycle by a genuine equilibrium error, and Scale overwrites the stored flux with clamped values every tick regardless of `damp`. It also explains why lowering `damp`/`gravity_force` made it *worse*, not better — that changed the constant residual's magnitude/sign, not its existence.

**The "tearing" event (Symptom 2, see below) is very likely the same root cause discharging at scale:** the entire bulk of a settled body carries a standing, Scale-Inflow-suppressed upward request on every submerged face simultaneously. An edit opens up capacity somewhere in the connected region (air, a non-full cell), and every previously-suppressed request across the whole region stops being zeroed at once — the pent-up flux executes in a single tick. The `~10-20`-per-voxel losses seen during tearing are mostly legitimate redistribution; the small genuine loss component is `round(raw*s)` overshoot in the two Scale passes (clamped away by Transport), individually tiny but summing to thousands of units when thousands of voxels discharge in the same tick. (Worth double-checking separately: whether a widespread event like this can exceed `MAX_CHANGELOG` — dropped entries would apply a donor's debit without the receiver's credit, reading as spatially random tearing while the GPU conservation counter still shows ~0, a different bug wearing the same symptom.)

**The fix (applied 2026-07-04):** gravity for a vertical face now enters as *elevation head* (piezometric head, `h = z + p/ρg`), not a bolted-on constant force. In fill units, one cell of elevation = `FILL_CAP` (255):
```glsl
float accel = (axis == 1)
    ? (float(dh) - float(FILL_CAP)) * params.g_dt * params.gravity_bias
    : float(dh) * params.g_dt;
// delete the separate `accel -= params.gravity_force;` branch entirely
```
This also made `gravity_force` (the export, and its `SimParams` field) unnecessary — its intended purpose (give a floating, near-zero-`dh` mass a baseline pull) is served by the `-FILL_CAP` term itself: a floating blob's bottom face sees `dh_total = 0 - P - 255`, strongly negative, so it falls coherently with no constant force and no equilibrium violation. `gravity_bias` stays (now purely a response-to-imbalance amplifier; the Y-axis `axis_cap` asymmetry is harmless once the underlying equilibrium error is gone — confirmed by testing, not just reasoned). Removed alongside the fix: the `SimParams`/params-buffer size reduction (mirror image of the earlier 52→56 byte bump when `gravity_force` was added) and its `@export` in `fluid_simulation.gd`.

**Verification method (high confidence, not just code-reading):** an independent, exact integer-arithmetic Python emulation of all 4 passes (truncate-toward-zero decay, round-and-store Scale-Outflow/Scale-Inflow with their sign-based ownership rules, Transport's clamp) reproduced this session's actual watched trace bit-for-bit (surface fill cycling `241→237→238→237→236...`, incoming +Y lane alternating `+3 ↔ -3/-4`) under the current shader logic at every parameter set tried (session defaults, the lowered damp/gravity_force experiment, and `gravity_force=0`) — never settles, always a limit cycle. The same emulator with the elevation-head form above reaches an *exact* fixed point at t=0 for a settled column (bit-identical forever) at any `g_dt`/`gravity_bias`, and a mid-air droplet falls at full speed, lands, and fully settles (all lanes exactly 0) within 5 ticks, mass conserved throughout.

**Separate, pre-existing, lower-priority behavior to watch after the fix lands:** a 1-cell-thick surface film still spreads laterally into same-level air (`accel = fill*g_dt`, `MIN_FLOW=1` lets any nonzero through) — a lateral deadzone/threshold question, unrelated to this bug, not worth chasing preemptively.

### TOOLING (2026-07-03): voxel sleeping via settle_threshold, and debug print toggle

**Problem 1 — perf: a large, mostly-settled lake never fully slept.** `FluidSimulation`'s idle-guard evicts (and zeroes) a chunk's flux page after 4 ticks with a fully-quiet dirty bitmask, letting it drop out of `_active_chunks` and stop being dispatched. But `flux_buf` intentionally persists across ticks (so waves/slosh don't instantly damp), which means a large settled body can keep making tiny (1-3 unit) but genuinely nonzero transfers forever — every one of them reset the idle counter under the old "any nonzero change = still active" rule, so a big lake effectively never slept even once it looked completely flat.

**Fix:** added `settle_threshold` (new `SimParams` field, `FluidSimulation.settle_threshold` export, default 3) — a second, coarser floor purely for the *scheduling* decision, separate from `MIN_FLOW`/`eff_flux()` in the shader (which still own conservation correctness, untouched). Transport still writes every real transfer to `voxels_a` regardless of size — no new leak risk — but only calls `mark_dirty()` when `abs(applied) >= settle_threshold`. Sub-threshold sloshing no longer resets a chunk's idle counter, so it accumulates idle ticks and gets evicted through the existing path — which already zeroes the flux page on eviction. Sleep and zero-residual-momentum happen together by construction, so a chunk that wakes later (e.g. new water added nearby) starts from a clean zero instead of replaying stale, possibly many-tick-old flux values — deliberately chosen over freezing-in-place after user input, specifically to avoid a woken voxel appearing to "remember" expired momentum.

`settle_threshold = 1` reproduces the old behavior (any nonzero change keeps a chunk awake indefinitely) if it ever needs to be dialed back for comparison.

**Problem 2 — perf: unconditional per-substep GPU readback.** The automatic conservation checker (`_conservation_buf` download) ran every single sub-step regardless of whether anything was printed, forcing a GPU sync each time — worth it during the active leak investigation, a real cost once both leaks (dispatch-range, Scale-Inflow) were fixed and it was just running in the background.

**Fix:** gated the whole conservation-check block (download, print, gain-tracker download, buffer resets) behind `FluidSimulation.debug_conservation_check` (new export, default `false`). Re-enable from the remote Inspector only when actively chasing a new conservation issue.

### BUG (2026-07-02): fluid flux leak — Scale only capped outflow, never inflow

**Symptom:** After the dispatch-range leak below was fixed, a second, much smaller-magnitude leak remained: large, gravity-independent fill LOSSES (hundreds to low-thousands per tick) during active water pouring, always clustered around whatever cell happened to be the current flow-convergence point — never a single fixed cell, and never present on settled/resting water. A voxel-watch diagnostic (`FluidSimulation.watch_enabled`/`watch_chunk`/`watch_local`, plus an F9 crosshair-targeting keybind in `world.gd`) confirmed the watched cell itself stayed completely unremarkable throughout — the loss was landing on a shifting set of *different* voxels each tick, ruling out a single misbehaving cell. Confirmed independent of `gravity_bias`/`gravity_force` (magnitude unchanged with both at their minimum).

**Root cause:** `fluid_flux.comp`'s Scale pass only ever bounded what a voxel could *give away*: `s = min(1, fill(p) / total_outflow(p))`. Nothing bounded what a voxel could *receive*. At a flow-convergence point (e.g. under an active pour, or the bottom of a falling column), several different donor voxels can each independently stay within their own Scale-approved outflow budget while their *combined* delivery to one shared receiver still exceeds the 255 fill cap. Transport's `clamp(old_fill + delta, 0, 255)` then silently discards the excess, with no debit anywhere in the system to balance it — a real, uncorrected loss. This explains every observed property: losses (not gains, since convergence funnels many donors into few receivers) that shift tick to tick (whichever cell is the current convergence point), scale with how much simultaneous flow is happening (more active donors → more chances to overcommit a receiver), are silent on settled water (no convergence when nothing's flowing), and don't respond to gravity tuning (a geometric convergence problem, not a force-magnitude problem).

**Fix:** Added a second, symmetric cap — Scale-Inflow — mirroring the existing Scale-Outflow logic from the receiver's side: `s_in = min(1, (255 - fill(p)) / total_inflow(p))`, applied to every face representing inflow to `p`. This **must** run as its own GPU dispatch, fully synced after Scale-Outflow completes, not merged into the same pass — a single flux lane can simultaneously be "outflow" from its owner's perspective and "inflow" to its `+axis` neighbour's perspective, and two different invocations writing the same lane in the same pass would race. Running it sequentially after Scale-Outflow avoids that: Scale-Inflow reads the already-outflow-scaled values, and shrinking a lane further there can never re-violate Scale-Outflow's already-satisfied guarantee (shrinking only ever reduces a donor's total requested outflow). Within the Scale-Inflow pass itself, the same sign-based mutual-exclusion proof Scale-Outflow already relies on holds with inflow/outflow roles swapped, so it's race-free on its own too.

Pass numbering changed: `0=Pass A, 1=Scale-Outflow, 2=Scale-Inflow (new), 3=Transport` (was `0=Pass A, 1=Scale, 2=Transport`). `FluidSimulation.step()` now dispatches four passes per sub-step instead of three, each with its own submit/sync.

**Rule:** A conservation guard that only bounds one side of a transfer (donor-only, in this case) isn't sufficient — check whether the *other* side needs symmetric bounding too, especially at fan-in/fan-out points (multiple donors → one receiver, or the reverse). When two per-voxel caps must both apply to the same shared resource (a flux lane, here), and both directions could legitimately need to shrink it, don't try to enforce both in one pass — sequence them as separate, fully-synced dispatches so each pass keeps its own single-writer-per-lane guarantee.

### BUG (2026-07-02): fluid flux leak — Pass A computed flux against un-dispatched neighbour chunks

**Symptom:** Unbounded, one-sided fill GAIN reported by the automatic conservation checker, never balanced by a corresponding loss. Small and intermittent at first ("takes a minute to get the reaction started"), then explosive — totals climbing into the thousands per tick, eventually overflowing the changelog. A location-tracking diagnostic (`GainTracker`, binding 10 in `fluid_flux.comp`) showed every large gain clustered at local `y=30`/`y=31` — the topmost layer of a chunk, i.e. a Y-axis chunk boundary — across many different chunk positions. Setting `gravity_force` to 0 did **not** stop it (ruled out gravity as the cause; it only changed the cosmetic shape of the pour).

**Failed attempt (kept, but insufficient alone):** Zeroing a paged-but-excluded chunk's `flux_buf` data at the start of each `step()` (theory: stale flux surviving the idle-guard grace period was being read and credited by an active neighbour without ever being debited). This didn't fix the leak — confirmed by user testing with unchanged leak character afterward. It's still logically sound as a defense-in-depth measure and was kept, but it addressed the wrong layer: it cleaned up flux *data*, not the *page-table entry* that Pass A's neighbour check now depends on (see fix below).

**Root cause:** `fluid_flux.comp` Pass A gated its whole per-axis loop only on `my_page < 0` (the current voxel's *own* chunk). It never checked whether the *neighbour's* chunk was actually part of this tick's dispatch range (`flux_list`). `read_a(nb)` always succeeds regardless of paging — it's a plain world-position lookup into `voxels_a`. So a dispatched boundary voxel would happily compute a real, nonzero flux value using a neighbour's true fill data, and materialize/drain fill from itself accordingly — but if the neighbour's chunk wasn't in `flux_list` this tick (e.g. it's a stale page still in its idle-guard grace period, or simply 2 rings away from any active chunk), **no invocation ever runs for the neighbour's voxels this tick**, so the neighbour's side of the transfer (the debit or credit that should balance it) never happens. Net effect: mass created or destroyed from nothing, one-sided, every tick this condition holds.

This is self-reinforcing: each phantom materialization creates a newly-active voxel, which becomes part of `_active_chunks` next tick, which expands `flux_list`'s 1-ring neighbourhood one ring further out — so the same leak mechanism re-triggers at the new frontier, tick after tick, which is exactly why it "takes a minute to get started" (needs the active region to organically reach a boundary where a currently-undispatched neighbour holds real liquid) and then runs away once it does.

**Fix (two parts, must ship together):**
1. `shaders/fluid_flux.comp` Pass A: before computing accel for a face, look up the *neighbour's* chunk in `flux_page_table` (same pattern as `flux_lane()`) and treat `nb_page < 0` exactly like the existing solid-boundary case — zero the lane, skip. This requires `flux_page_table` to mean "in this tick's dispatch," not just "has ever had a page allocated."
2. `simulations/fluid_simulation.gd` `step()`: `flux_page_table` is now rebuilt every tick to match that meaning — every chunk in `flux_list` has its real page index re-written (`_write_flux_page_table_entry`) in case a previous tick unmapped it, and every paged chunk *not* in `flux_list` this tick gets its page table entry set to `-1` (in addition to the existing flux-data zeroing). The CPU-side `_flux_chunk_table` bookkeeping and the idle-guard eviction timing are untouched — this is a per-tick logical unmap/remap of the GPU-visible page table, not a change to actual page allocation lifetime.

**Rule:** Any shader that reads a neighbour's world-position data across a sparse/paged dispatch range must verify the neighbour is *also* within this tick's dispatch, not just that its own invocation is. Reading real data via a plain world-position lookup (`read_a`-style) will always "succeed" even for data that no corresponding GPU invocation will ever process this tick — that mismatch is invisible until you specifically check dispatch membership, not data validity.

### BUG: `Vector3i(0,0,0)` is falsy in GDScript — silently drops chunk (0,0,0)

**Symptom:** Sand in the exact center chunk (0,0,0) never simulated. Every other chunk worked. Placing sand there returned `[Edit] committed chunks: []`. The sand was visible (voxels_a was correct) but simulation never triggered and collision never rebuilt.

**Root cause:** `Dictionary.get(key)` returns the value if found, or `null` if missing. When the value IS `Vector3i(0,0,0)`, GDScript evaluates it as falsy — `not Vector3i.ZERO` is `true`. So `if not chunk_pos: continue` silently discarded the (0,0,0) result as if the key weren't in the dictionary. Two locations had this bug:
- `WorldOrchestrator._extract_changed_chunks` line: `if not chunk_pos: continue`
- `GranularSimulation._decode_dirty_bitmask` line: `if cp: out.append(cp)`

Both appear after `dict.get(slot)` where the slot maps to chunk (0,0,0).

**Fix:** Use `dict.get(key, null)` with an explicit sentinel default and compare `== null`:
```gdscript
var chunk_pos: Variant = slot_to_chunk.get(slot, null)
if chunk_pos == null:
    continue
```

**Rule:** Never use truthiness checks on values from a `Dictionary.get()` call when the value type can be zero or a zero vector. Always use `== null` or check `dict.has(key)` first.

### GOTCHA: GDScript integer division on negative values

`flat_idx / vpc` in GDScript uses truncating division (rounds toward zero), not floor division. For positive `flat_idx` values this is fine. If `flat_idx` ever becomes negative (e.g. from a corrupt changelog entry or a shader bug), the slot computation would be wrong. The GPU changelog should never produce negative `flat_idx` values — `world_to_flat` returns -1 for out-of-bounds which causes an early `return` in the shader before the changelog write — but worth knowing if debugging future slot mismatch issues.

### GOTCHA: GLSL reserved keywords as variable names

`flat` is a reserved GLSL interpolation qualifier and cannot be used as a variable name in compute shaders. Using it silently causes driver-dependent tokenization errors that are hard to trace. Always use ASCII-only characters in shader source — non-ASCII characters (em dashes, curly quotes) in comments can corrupt tokenization on some drivers.

The donor then couldn't spread further (below MIN_FLOW_FILL) but still fell vertically.

**Root cause (try_compress):** `try_compress` in fluid_sim.comp could leave the source with `new_my_fill = 1–31` after giving fill to the destination below. These trace-fill cells passed the `material_sim == LIQUID` check and fell via `try_move`.

**Root cause (total outflow):** With divisor=16 and 4 neighbors, a full cell (fill=255) sent `63×4=252` total, leaving itself at fill=3 — a trace cell at the original position.

**Fix (fluid_flux.comp pass 0):**
1. Changed divisor from 16 to 4 (4× faster equalization).
2. Rewrote pass 0 to compute all 4 neighbor fluxes, then cap total outflow at `my_fill - MIN_FILL (32)` to ensure the donor always retains at least fill=32.
3. For air targets only: skip the direction if computed flux < MIN_FILL (32) — prevents creating near-empty air cells.
4. Raised MIN_FILL from 16 to 32 (don't emit flux at all if below 32).

**Fix (fluid_sim.comp):**
1. Added `if (my_fill_v < 32u) return;` guard at top of main() — trace cells can't move at all.
2. In `try_compress`: if `new_my_fill > 0 && new_my_fill < 32`, snap to 0 (destroy the remainder). Tiny volume loss acceptable; prevents fill=1 ghost cells.

**Follow-up:** Pass 0 capping prevents the DONOR from going below MIN_FILL=32, but an existing liquid cell can still end up at fill=27 if it receives a small negative delta from pass 0 (gave away fill to 4 neighbors and the scaling rounded down). Fixed in pass 1: after `new_fill = clamp(old_fill + delta, 0, 255)`, snap `new_fill` to 0 if `0 < new_fill < 32`.

**Rule:** Any fill-transfer operation (flux, compress) must ensure the result is either ≥ MIN_FILL or exactly 0. Check at BOTH the source (pass 0 cap) and the result (pass 1 snap). The "middle ground" trace fills are inert, invisible, and hang permanently.

### BUG: Single water voxel explodes into a runaway fill=1 blob, changelog overflow

**Symptom:** Placing one water voxel produced a rapidly expanding blob that engulfed most of the visible terrain within seconds, converging to fill≈1 everywhere. `apply_changelog()` logged `changelog overflow (284752 entries); clamping to 131072` from what started as a single-voxel edit.

**Root cause — two compounding issues, both in Phase 7e's Transport pipeline (fluid_flux.comp):**

1. **`g_dt` default (6.0) was wildly oversized relative to the flux value scale.** Head ranges 0–255 for a single cell; `FILL_CAP` clamps a tick's flux to ±255. A freshly placed full droplet (`fill=255`) facing air computes `head(own)=255`, `head(air)=0` → `dh=255` → `f' = 255*6 = 1530`, instantly clamped to the maximum possible transfer (255) on the very first tick. Instead of building pressure gradually across many ticks (the entire point of persistent flux — see Phase 7d's root-cause writeup above), the donor could empty essentially its entire fill in a single tick.

2. **No floor on air-materialization.** Scale (Step 5) guarantees a donor voxel can never be asked to give more than it holds — but it does *not* guarantee the transferred amount is large enough to be worth spawning a new voxel for. A cell at `fill=1` can still legally give away that last unit (`s = min(1, 1/total_out)` permits it). With no floor, "give my last 1 unit, become 0, neighbour becomes 1" chains outward indefinitely — every newly materialized cell becomes an active candidate next tick and repeats the pattern, one air cell at a time, never settling. This is what produced the fill≈1 blob and the changelog explosion (hundreds of newly-materialized cells per tick, each triggering `chunks_committed` discovery, each activating more neighbouring chunks the tick after).

**Fix:**
- Lowered `FluidSimulation.g_dt` default from 6.0 to 0.15, tightened the export range from `(0, 50)` to `(0, 2)` — the useful range where flux builds up gradually instead of saturating instantly is well under 1.0.
- Added `MIN_MATERIALIZE = 16` in Transport's `is_air` branch: refuse to create a new liquid voxel if the transferred amount would leave it below this floor. The donor's outflow was already committed by Scale, so the discarded fill is a small, bounded, one-tick loss — not an unbounded leak, and not a case Scale's conservation guarantee was ever supposed to cover (it guarantees "can't overdraw," not "won't spread into monomolecular films").

**Rule — distinguish this from Phase 7d's MIN_FILL hacks.** Phase 7d's thresholds were emergency patches compensating for a system with *no* conservation guarantee. Phase 7e's `MIN_MATERIALIZE` is a deliberate design floor layered *on top of* a system that already conserves correctly — the same way real fluids don't spread into films a single molecule thick. Don't conflate "this system needs a threshold to not break" (7d) with "this system chooses a threshold for sane behavior" (7e) when reading old vs. new code.

tick 2: fill=220 (3 voxels)   — lost 35
tick 3: fill=220 (8 voxels)   — exact conservation

Y (vertical) flow is now handled entirely by `fluid_flux.comp`'s Y-axis flux — the same head-driven mechanism as X/Z, already proven conservation-safe by Scale.

**Rule:** when two systems can move the same conserved quantity, and only one of them is being actively verified, the other is a live suspect by default — "interim state, still dispatched for now" notes need to be treated as a todo with real urgency, not background noise, once the new system is far enough along to be measured.

### BUG (RESOLVED, 2026-07-02): Water fully vanishes to zero — stale flux survives voxel death

**Symptom:** After deleting `fluid_sim.comp` (previous entry), a single droplet no longer stopped at fill=1 — it went all the way to complete disappearance. Step-by-step data: `255 → 255(4vox) → 201(3vox) → 201(9vox) → 138(6vox) → 48(7vox) → 15(1vox) → 0 → 0`. A large sphere test (14,147 initial liquid voxels, `fill=3,607,485` total) showed the same shape at scale — a slow, steady, unrecoverable drain from 3.6M down to ~19K over roughly 90 stepped ticks, never stabilizing.

**Root cause.** Pass A's early-return for non-liquid cells — `if (mat_id == 0u || material_sim.data[mat_id] != SIM_LIQUID) return;` — meant that the instant a liquid voxel drained to `fill=0` and became air, **nothing ever touched its 3 owned flux lanes again**. But Scale and Transport keep reading a cell's owned-face storage regardless of whether the owner is still alive — a dead cell's last flux value is frozen permanently, and any live neighbor computing its own Transport delta keeps applying that stale, never-refreshed value *every single tick*, forever. This is the second half of Step 6b's flux-invalidation requirement: the existing Pass A code already handled "my neighbour became incompatible" (zeroes the face), but never handled "I myself just died" — the far more common case, since it fires every time flux successfully drains a cell to zero, which is the normal, correct, desired outcome of the whole system working.

**Why totals reached exactly zero and not some equilibrium:** once enough cells die and leave stale claims behind, live neighbors keep bleeding fill into frozen phantom obligations that are never revisited or corrected, compounding tick over tick with no counterbalancing mechanism — a one-way ratchet toward zero rather than a bounded loss.

**Fix:** Pass A now zeroes a cell's 3 owned lanes whenever it finds that cell is *not currently liquid* (covers death, displacement, and edits uniformly — anything that isn't `SIM_LIQUID` gets the same treatment), instead of silently skipping it:
```glsl
if (mat_id == 0u || material_sim.data[mat_id] != SIM_LIQUID) {
    for (int axis = 0; axis < 3; axis++) {
        flux_buf.data[my_page * vpc * 3 + my_local * 3 + axis] = 0;
    }
    return;
}
```
Since Pass A runs over the full active+neighbor dispatch range every tick regardless of current material, this invalidation now happens automatically the very next tick after any cell dies — no separate signal or edit-hook needed.

**Rule:** "early return for the cells I don't care about" is a dangerous default in a system with *persistent* per-cell state — a pass that skips a cell entirely also skips cleaning up after it. Any persistent buffer (this session: `_flux_buf`) needs an explicit answer to "what happens to this cell's stored state when it stops being a cell this system cares about," not just "what happens while it's alive."

### BUG (FIXED, 2026-07-02): `MIN_MATERIALIZE` was a one-sided conservation leak — replaced with a read-side deadzone

**Symptom:** Re-ran the single-droplet test after the stale-flux fix above. Result: **bit-for-bit identical** tick sequence to the pre-fix run — `255 → 255(4vox) → 201(3vox) → 201(9vox) → 138(6vox) → 48(7vox) → 15(1vox) → 0(0vox) → 0`. A large sphere test settled into a stable, uniform `fill≈1.7` plateau with `flux=0` everywhere (a genuine rest state, not still actively leaking — just reached after heavy loss along the way).

**Confirmed via the debug counter** (`DebugCounters`, binding 9 in `fluid_flux.comp`; `FluidSimulation.debug_dump_flux_stats()`, bound to `F6`), which measures exactly how much fill `MIN_MATERIALIZE` discards each tick. Re-running the droplet test with it active:

| Tick transition | Fill loss | Discard counter |
|---|---|---|
| 255→255 | 0 | 0 |
| 255→201 | 54 | 54 |
| 201→201 | 0 | 0 |
| 201→138 | 63 | 63 |
| 138→48 | 90 | 90 |
| 48→15 | 33 | 36 (float-rounding noise, negligible) |
| 15→0 | 15 | 15 |

Near-exact match every tick. The sphere test discarded 2,893,122 in a single accumulated read against a total loss of roughly 3.58M over the run — same story at scale. `MIN_MATERIALIZE` accounts for essentially all of the measured loss; the earlier stale-flux bug was real but not the dominant factor here.

**Why it's a leak, not just a bound that turned out bigger than expected — structural, not just numerical.** The floor (`if (is_air && new_fill < MIN_MATERIALIZE) return;`) only ever gates the *receiving* air cell. The *donor* voxel's own delta is computed and applied completely independently, the moment it's liquid — nothing gates a liquid cell losing fill to match. Concretely: `delta -= flux_buf.data[...]` for the donor's owned faces happens unconditionally in every liquid voxel's own Transport execution; whether the *neighbor* on the receiving end successfully materializes is irrelevant to the donor's own delta. So the donor always pays, and the receiver sometimes doesn't collect — asymmetric by construction. The original comment justifying this floor called it "a small, bounded, one-tick loss, not an unbounded leak" — the "bounded" half was never actually true, because nothing bounds the *donor's* side to match the receiver's refusal.

**My read, offered as a starting point, not a decision:** this floor should either (a) be removed outright, trusting Scale's conservation guarantee the way the rest of Phase 7e already does — the concern that motivated it (Phase 7d's "give my last 1 unit forever" chains) doesn't obviously reapply here since Scale + head-driven Pass A is a fundamentally different, physically-grounded mechanism, not the old biased CAS system; or (b) stay, but become symmetric — the donor's own outflow computation would need to respect the same floor Transport's receiver-side check applies, likely meaning the threshold has to move earlier, into Scale or Pass A, where both sides of a face are still being decided together rather than resolved independently per-cell in Transport. I don't have strong confidence between these without more testing (specifically: does removing the floor reintroduce visually-annoying trace droplets now that the underlying mechanism is physically damped, rather than a biased runaway?).

**Review verdict (Fable 5, 2026-07-02):** the floor is a real leak and must go. On the fix itself: replace `MIN_MATERIALIZE` (per-cell, receiver-side, lossy) with a per-face **read-side deadzone** applied wherever a flux lane is read, in both Scale and Transport — `eff_flux(f) = (abs(f) >= MIN_FLOW) ? f : 0`. Both sides of a face read the same stored value through the same pure function, so donor and receiver always agree — symmetric by construction, zero volume loss, no writes, no race, no extra pass. It also preserves the persistence property: sub-threshold flux keeps accumulating in the lane across ticks (equilibrium ≈ `dh·g_dt/(1−damp)`), so small pressure differences can still eventually seep, whereas a write-side snap would permanently block them. A per-face floor of `MIN_FLOW` also guarantees any single-donor materialized cell starts ≥ `MIN_FLOW`, so the old receiver-side check is deleted outright, not moved.

**Applied (2026-07-02).** `fluid_flux.comp`: added `const int MIN_FLOW = 16;` and `int eff_flux(int raw)` right after `head()`. Scale's `total_out` computation (both the owned-face loop and the neighbour-face loop) now reads through `eff_flux()`; its scaling-write loops only touch a lane when `eff_flux(raw)` is nonzero (a sub-threshold lane is never written at all, so it keeps accumulating under Pass A's normal integration rather than being nudged by a budget cap it was never part of). Transport's `delta` computation reads every term through `eff_flux()` too. The old `MIN_MATERIALIZE` block and its `debug_counters` atomic (which had done its job — it's what produced the table above) were both removed, along with the now-fully-unreferenced `DebugCounters` buffer (binding 9) in both `fluid_flux.comp` and `fluid_simulation.gd` — leaving it declared-but-unused would have reproduced the exact "SPIR-V strips it, GDScript still supplies a uniform for it, `uniform_set_create` fails" crash fixed earlier this session.

**Known narrow edge case, accepted as-is:** if an air cell receives from multiple donors simultaneously with opposing signs — e.g. `+17` from one neighbour and `−16` from another, each individually above `MIN_FLOW` — the *net* `delta` could be a small value like `+1`, producing a small materialized cell despite every individual contribution clearing the threshold. This requires simultaneous opposing flows from different neighbours and is self-limiting rather than runaway (nothing like the old unbounded "give my last unit forever" chain); not worth a second gate for.

Fable 5's verdict also referenced two upstream root-cause bug entries ("Pass A's non-liquid early-out," "Y-axis flux has no gravity offset") that didn't exist in this document at the time — see the entry immediately below, which writes both of them up. They turned out to be the same root cause, not two separate ones.

### BUG (FIXED, 2026-07-02): Pass A's liquid-only gating made flow one-directional — water could only expand +X/+Y/+Z, never fall

**Symptom:** reported directly by the user: placing a sphere of water produced a hard cutoff — it only ever expanded up, right, and forward (+Y, +X, +Z), never backward, left, or down (−Z, −X, −Y). Critically, the sphere never fell to the ground; it stayed floating exactly at its placement height indefinitely, expanding sideways in only three of six possible directions. This is the same root cause Fable 5's review verdict (previous entry) referenced as "Pass A's non-liquid early-out makes flow into air impossible in the −X/−Y/−Z directions (water literally cannot fall)" and "the Y-axis flux has no gravity offset" — investigation confirmed both symptoms trace to one bug, not two.

**Root cause.** Pass A computed acceleration for a voxel's 3 *owned* faces (+X, +Y, +Z), and only ran that computation when the *current* thread's own voxel was liquid — a non-liquid cell hit an early return that zeroed its lanes and skipped the loop entirely. But by the face-ownership convention (documented since Step 2), the face between a liquid cell `p` and its `-X` neighbour `q` is **owned by `q`**, not `p` — flow from `p` backward into `q` can only ever be expressed as a negative value on `q`'s own `+X` face, computed by `q`'s own Pass A execution. If `q` is air, that execution short-circuits before ever reaching the accel computation. Net effect: a liquid voxel can push into a `+axis` air neighbour (that computation happens from the liquid side, already worked), but nothing ever computes the symmetric case of an air neighbour on the `-axis` side accepting inflow — because that's a *different* thread's voxel, and that thread bailed out immediately for being air. This affected all three axes identically, but Y is where it's most visible: gravity is strictly a `-Y` phenomenon, so "flow only works in the positive direction" is indistinguishable from "there is no gravity" from the player's perspective.

**Fix.** Changed Pass A's gating from "am I liquid" to a symmetric per-axis check on both sides of the face: solid on either side → zero, always (no flow ever possible there); both sides air → zero (nothing to move); both sides liquid but different materials → zero (kept separate, unchanged from before); otherwise — liquid facing air, air facing liquid, or same liquid on both sides — compute `dh = head(gpos, active_mat) - head(nb, active_mat)` and integrate, exactly as before, just no longer gated on which side of the face the current thread happens to be looking from. `active_mat` resolves to whichever side actually holds the liquid, so `head()` reads the correct column regardless of orientation.

**Gravity falls out for free — no special case needed.** Because `head()` is used uniformly for all three axes (X, Y, Z) with no per-axis branching, downward flow isn't a separate mechanism or a constant force: a liquid cell always has `head > 0`, empty air below it always reads `head == 0` (see `head()`'s definition — non-matching material returns 0 immediately), so `dh` between a liquid cell and the air below it is always negative, driving flow downward, proportional to the liquid's actual head/depth rather than a fixed magnitude. This is why the "Y-axis flux has no gravity offset" framing and the "Pass A non-liquid early-out" framing turned out to be the same bug: once air cells can compute their own owned faces at all, gravity requires zero additional code — the existing head-difference formula already produces it correctly on the Y axis exactly like it does on X and Z.

**Self-invalidating by construction — the old Step 6b "I died" branch became unnecessary.** The previous code had an explicit early branch: if a cell isn't currently liquid, zero its 3 owned lanes and return, specifically to stop a dead cell's stale flux from being read forever (documented in an earlier bug entry, "stale flux survives voxel death"). That branch is gone now — and doesn't need replacing. Since every voxel (liquid or air) now recomputes its owned faces fresh every single tick based on current neighbour state, a cell that dies (or gets edited, or displaced) simply gets its faces recomputed correctly the very next tick, whatever its new state is. Invalidation was a workaround for a system that skipped updating dead cells; a system where every relevant cell is updated every tick doesn't need a separate invalidation mechanism.

**Follow-up (2026-07-02, same day): the "known residual limitation" above was worse than scoped and got its own fix.** Reported directly: water expanded correctly in all directions within a chunk, but hit a hard wall at chunk boundaries. Root cause: page allocation only ever covered `_active_chunks`. Positive-direction flow across a boundary stores on the *donor's* owned face — the donor's chunk is already active/paged, so it always worked and was never the problem. Negative-direction flow (including straight down) stores on the *receiver's* owned face, per face ownership — if that neighbouring chunk has never held water, it has no page, so Pass A's `if (my_page < 0) return;` fires for every voxel in it before the per-axis loop can even run. Critically, **this does not self-heal the way the original "1-tick lag" framing assumed**: self-healing requires a changelog entry to trigger discovery, and nothing is ever computed there in the first place, so no changelog entry is ever produced — it's a permanent wall for that direction, not a 1-tick delay.

**Fix:** `fluid_simulation.gd`'s `step()` now allocates pages for the full flux dispatch range (`_build_flux_chunk_list` output — active + all 6 face neighbours), not just `_active_chunks`. This closes the hole for all three negative axes uniformly (it's the same underlying mechanism, not a per-axis special case).

**This created a new problem, fixed in the same change:** proactively allocating pages for every neighbour means chunks that are adjacent to water but never actually receive any (e.g. a rock wall bordering a pond) would get a page and never have it freed — the existing eviction loop only walks `_active_chunks`, and a pure-neighbour chunk never enters that dict. Added a second, parallel idle-guard (`_flux_page_idle`, same `idle < 4` shape as the existing one) that tracks every paged chunk *not* currently active and frees its page after a few idle ticks — with enough grace period that a chunk materializing its first voxel this tick isn't yanked out from under itself before next tick's discovery recognizes it as active.

### BUG (FIXED, 2026-07-02): sphere expands as an octahedron instead of falling coherently — pressure difference alone isn't gravity

**Symptom:** with chunk-boundary flow working, a solid `fill=255` water sphere placed in mid-air didn't fall as a coherent mass — it immediately bulged outward in all six cardinal directions simultaneously, forming an octahedron ("a neat triangular bipyramid"). It never fell faster than it spread sideways.

**A separate coding agent's proposed fix** (`accel = -float(FILL_CAP) * g_dt` at a cited `fluid_flux.comp:201`) does not exist in the current file — traced to stale/different code predating today's Pass A rewrite. Its underlying instinct (Y needs *something* beyond pure pressure-difference) turned out to be partly right, but the specific mechanism (a `FILL_CAP`-scaled constant, unconditional regardless of neighbour fill) was correctly rejected — it would drain a `fill=10` cell exactly as hard as a `fill=255` one.

**Actual root cause:** `head(gpos, active_mat)` is a single scalar per cell — pressure due to the vertical column above it — and Pass A reused that *same* value identically for computing `dh` on all three axes (X, Y, Z). No directional bias existed anywhere in the accel formula. For a sphere, `head()` is largest at the bottom pole (the full vertical diameter of full cells sits above it) — but near a pole the horizontal cross-section is narrow, so that same maximum-pressure cell's horizontal neighbours are *also* air. The single large `head()` value pushed with equal, maximal strength into every exposed neighbour at once (down + several sideways), not preferentially downward — producing the octahedral bulge.

The deeper gap: real fluids have two distinct drivers — gravity (a constant body force, vertical only, independent of pressure) and the pressure gradient (arises from head differences, drives flow in all directions to equalize). These balance in hydrostatic equilibrium for a *supported* fluid, but for fluid in free-fall (nothing supporting it), gravity should dominate over lateral pressure-equalization. The system only ever had the pressure-gradient mechanism, with an identical constant (`g_dt`) on every axis — nothing made vertical respond faster than horizontal for a comparable `dh`, and nothing pulled a perfectly uniform mass down at all if its internal `dh` was near zero everywhere (amplifying zero is still zero).

**Fix — two complementary Y-axis-only terms, both layered on top of the existing `dh * g_dt` term, neither replacing it:**
```glsl
float axis_bias = (axis == 1) ? params.gravity_bias : 1.0;
float accel = float(dh) * params.g_dt * axis_bias;
if (axis == 1) {
    accel -= params.gravity_force;  // fy(p) positive = outflow upward, so downward push subtracts
}
```
- **`gravity_bias`** (multiplicative, default `3.0`, range `1.0–8.0`): once *any* pressure differential exists, vertical response wins the race against lateral spreading for the same `dh`.
- **`gravity_force`** (additive constant, default `10.0`, range `0.0–50.0`): a baseline downward nudge independent of `dh`, since `gravity_bias` alone only amplifies an *existing* differential — a perfectly uniform floating mass has ~zero internal `dh` everywhere and would never start falling from amplification alone. Both exported as `@export_range` on `FluidSimulation`, live-tunable via the Godot remote Inspector, matching the existing `damp`/`g_dt` pattern.

**Why this doesn't reintroduce the "drains disproportionately" flaw:** Scale (pass 1) still caps actual outflow at `my_fill` regardless of how large the raw computed accel is — a `fill=10` cell under a strong `gravity_force` still only ever loses up to 10 per tick in practice. The earlier rejected proposal's problem wasn't really about violating conservation (Scale already prevents that structurally); it was that a `FILL_CAP`-scaled constant, unconditionally applied, is a much cruder signal than a modest constant layered underneath the existing proportional term.

**`SimParams` grew from 44 to 52 bytes** (`fluid_flux.comp`: added `float gravity_bias;` and `float gravity_force;` after `g_dt`; `fluid_simulation.gd`: `_ready()`'s buffer allocation, `_upload_flux_params()`'s encoding, and the `_flux_params_buf` size comment all updated to match). Verified the 13-scalar/52-byte offsets line up exactly on both sides before testing — a struct/buffer size mismatch here would silently corrupt every param after `chunk_size` on the GPU side.

**No changes needed to Scale, Transport, or `head()`.** Scale/Transport are already axis-agnostic and read whatever ends up in `flux_buf` regardless of how it was computed. `head()`'s upward-only walk defines a correct, direction-independent physical quantity — the bug was in how that scalar was *applied* uniformly across axes in Pass A, not in how it was computed.

**Known secondary risk, not pre-emptively addressed:** does amplifying/adding-force-to Y suppress horizontal puddle-spreading once water lands and settles? Second-order: horizontal `dh*g_dt` is completely unchanged in absolute terms — a resting puddle has near-zero Y-axis `dh` against the floor already, so it spreads exactly as fast as before. In mixed scenarios (a mound still settling, both vertical and horizontal pressure present), more of the fluid's Scale-capped "response budget" goes vertical first — the intended fix, not a bug. If a real regression shows up, `debug_dump_flux_stats()` (`F6`) can compare per-axis lane magnitudes before/after to confirm, rather than pre-emptively adding a lateral counter-multiplier.

### BUG (FIXED, 2026-07-02): voxels with fill 1–14 permanently stuck in mid-air, never falling — `MIN_FLOW` deadzone traps low-fill cells

**Symptom:** reported while testing the gravity fix above, with a screenshot showing a tall thinning column of leftover water above a spread puddle — cursor on a voxel reading `Fill: 8`. User: voxels drop to fill 1–14 (even with more water directly adjacent/below) and then just stay stuck, never falling further, never handing off their remaining fill.

**Root cause — a real structural deadlock, not a slow drain.** `eff_flux(raw) = (abs(raw) >= MIN_FLOW) ? raw : 0` (`MIN_FLOW = 16`, added alongside the `MIN_MATERIALIZE` fix earlier today) is read symmetrically by both Scale and Transport. Scale caps a cell's total outflow at `my_fill` — so a cell with `fill=8` can never request more than 8 units of outflow, full stop, no matter how many ticks pass. Since `8 < MIN_FLOW`, that transfer is *always* invisible to `eff_flux()`, on every single tick, forever. The dispatch order makes this worse than a simple "small transfers never happen" limitation: Pass A integrates the raw stored value past 16 within 1–2 ticks (confirmed by hand-computing the geometric accumulation under `damp`/`gravity_force`), but **Scale runs before Transport in the same tick** and immediately re-scales that value back down to at most `my_fill` (< 16) before Transport ever gets a turn to read it. Next tick, Pass A grows it past 16 again from the shrunk base, Scale caps it back down again — an oscillating trap, not a threshold that eventually gets crossed. The comment justifying the original `MIN_FLOW=16` claimed sub-threshold flux "keeps accumulating... until it naturally crosses the threshold on its own" — that reasoning didn't account for Scale's same-tick, pre-Transport re-capping interacting with a cap that's itself below the threshold. Every fill value the user reported (1–14) was under 16 — not a coincidence, a direct prediction of this mechanism.

**Fix:** lower `MIN_FLOW` from 16 to 1 (`fluid_flux.comp`). This does **not** reintroduce the asymmetric `MIN_MATERIALIZE` leak fixed earlier — that leak came specifically from donor and receiver disagreeing about a value (one side saw it, the other didn't); `eff_flux()` applied identically on both sides is leak-free at any threshold, including a low one. The only thing a low threshold gives up is the original cosmetic goal (don't spawn dust-speck droplets in air) — and that concern is now substantially smaller given `gravity_bias`/`gravity_force` (previous entry) actively consolidate thin films instead of letting them spread indefinitely, which was the scenario `MIN_FLOW=16` was originally sized to prevent.

**No other changes needed.** Scale and Transport's logic is unchanged — only the threshold constant moved. Worth re-testing the earlier "trace droplet" concern now that both fixes are in (gravity fix + lowered deadzone) — if dust-speck droplets do turn out to be visually annoying in practice, the fix belongs in a *destination-aware* check (only gate genuinely new air→liquid materialization, never gate an already-existing liquid cell's continued movement) rather than raising `MIN_FLOW` back up, since raising it back up reproduces this exact bug.

### BUG (FIXED, 2026-07-02): raising `g_dt` freezes water into standing full-fill columns — `gravity_bias` amplification saturates away its own advantage

**Symptom:** while hand-tuning `gravity_bias`/`gravity_force`/`g_dt` live, raising `g_dt` produced tall, standing, full-`fill=255` columns/walls of water that simply stopped moving — screenshot showed pillar/arch-like frozen shapes with air gaps between them. Setting `g_dt` back to `0` let it "unstick" (briefly falling again), but placing more water and raising `g_dt` again reproduced the same frozen state.

**Root cause.** `gravity_bias` multiplies `g_dt` on the Y axis — at the *previous* export ranges (`g_dt` up to `2.0`, `gravity_bias` up to `8.0`), the effective Y-axis multiplier could reach `16`, meaning any `dh >= 16` (a very ordinary head difference, not an extreme one) instantly saturated flux to the `±FILL_CAP` clamp ceiling. Saturating isn't itself wrong — `FILL_CAP` clamping is a deliberate, correct per-tick limit. The actual bug: **once several competing directions all hit the exact same clamp ceiling simultaneously, they lose the relative distinction `gravity_bias` exists to create.** Scale divides a cell's outflow budget proportionally to each direction's *relative* magnitude — but if X, Y, and Z all read `255` because all three saturated, they're tied, and Scale splits the budget roughly evenly among them again, silently reintroducing the exact symmetric/octahedral-spreading problem `gravity_bias` was built to fix, just triggered by oversaturation instead of by the original missing-bias bug. Compounding this: `damp` carries a saturated value forward into the next tick, and a fresh, possibly differently-signed saturated `accel` gets added on top — the stored flux can oscillate between ticks without making net progress, which is exactly what "frozen in place" looks like from the outside. Resetting `g_dt` to `0` let the stored flux cleanly decay toward zero via `*damp` alone (no forcing to fight against), so raising it again started from a clean slate and worked — until enough ticks or new water pushed some region back into the saturating regime.

**Fix (initial attempt, insufficient):** narrowed the export ranges rather than changing the physics — `g_dt` from `[0, 2.0]` to `[0, 0.5]`, `gravity_bias` from `[1.0, 8.0]` to `[1.0, 5.0]`. Reasoning at the time: keep the combined `g_dt*gravity_bias` multiplier well under 1.0, mirroring the existing "keep g_dt well under 1.0" guideline.

**Follow-up (same day): still reproduced at `g_dt=0.2`, which is inside the narrowed range.** The range-narrowing missed the actual scale of the problem: `head()` adds 255 per full cell in a column, so even a **2-deep** column already produces `dh=510` on its bottom cell — at `g_dt=0.2, gravity_bias=3.0` (effective multiplier 0.6, saturation point `dh≈425`), that already saturates. Saturation isn't a rare edge case reachable only by cranking sliders too high — **it's the normal case for anything but a single shallow puddle voxel.** Narrowing the range made the corner harder to reach, not impossible, and any real body of water deeper than ~2 cells reaches it immediately regardless of how conservative the sliders are.

**Actual fix: give Y a taller clamp ceiling than X/Z, instead of sharing `FILL_CAP`.** The real bug was never "saturation happens" — `FILL_CAP` clamping every tick is correct and deliberate. The bug was that **X, Y, and Z all clamped to the exact same ceiling**, so the instant more than one axis saturated, they tied, and Scale's single proportional scale factor `s` (applied identically to every lane) had no way to tell them apart — collapsing straight back to symmetric/even distribution regardless of how large `gravity_bias` was set. Fix (`fluid_flux.comp`):
```glsl
float axis_cap = (axis == 1) ? float(FILL_CAP) * params.gravity_bias : float(FILL_CAP);
float new_f = old_f * params.damp + accel;
new_f = clamp(new_f, -axis_cap, axis_cap);
```
Y's raw stored value can now legitimately grow up to `FILL_CAP * gravity_bias` (up to 1275 at the new max `gravity_bias=5`) instead of being capped to the same 255 ceiling as X/Z. Scale doesn't need to know about this — it already operates on whatever raw magnitude is stored, with no assumption that any single lane is bounded to `FILL_CAP` specifically (verified: `FILL_CAP` doesn't appear anywhere in Scale's or Transport's logic). Because Scale's scale factor `s = my_fill / total_out` is applied uniformly, a larger raw Y value now receives a proportionally larger slice of the outflow budget even when every axis is fully saturated — preserving "down wins" all the way through saturation instead of losing it the moment multiple axes tie.

**Range narrowing from the initial attempt is kept, not reverted** — it's still a reasonable safety margin on top of the real fix, just not sufficient on its own.

### INVESTIGATION (OPEN, 2026-07-02): still freezes at `g_dt=0.2` after the per-axis clamp fix — changelog overflow found, cause not yet confirmed

**Symptom:** the per-axis clamp fix above (giving Y a taller ceiling) didn't resolve the freezing — same symptom reproduced at `g_dt=0.2`, well inside the narrowed range. User simultaneously noticed a console warning appearing every time it happens:
```
WorldOrchestrator: changelog overflow (259316 entries); clamping to 131072
```

**What this means, mechanically:** `apply_changelog()` silently *drops* any entries past `MAX_CHANGELOG_ENTRIES` — they're never applied to `voxels_a` at all, for any simulation sharing this buffer (granular, edits, fluid all write through the same one). If a large fraction of a falling sphere's legitimate fill updates get cut off this way every single tick, the visible result is indistinguishable from "frozen" even though the underlying flux math might be completely correct now.

**Two competing explanations, not yet distinguished:**
1. **The gravity fixes are working correctly** — more voxels are now legitimately active and moving every tick than in any scenario `MAX_CHANGELOG_ENTRIES=131072` (1 MB, sized for droplet-scale activity) was ever built for. The overflow is a capacity problem, not a physics problem — raising the cap should reveal correctly-falling water underneath.
2. **Still oscillating** — cells flip-flopping tick to tick without net convergence would *also* generate a large, sustained changelog count every tick (each flip is a fresh write), which would look identical to "legitimately lots of water moving" from the overflow warning alone. If this is what's happening, raising the cap just makes the oscillation more visible/expensive, not fixed.

**Applied so far (capacity side, safe regardless of which explanation is correct):** raised `MAX_CHANGELOG_ENTRIES` (`WorldOrchestrator.gd`) and every shader's matching `MAX_CHANGELOG` constant (`fluid_flux.comp`, `granular_sim.comp`, `edit_apply.comp` — all three write through the same shared buffer, so all three must match the GDScript-side allocation or a shader could write past what's actually allocated) from `131072` to `524288` (1 MB → 4 MB, trivial GPU memory cost, comfortably above the measured 259316-entry spike).

**Added a diagnostic to distinguish the two explanations, not yet interpreted:** `fluid_simulation.gd`'s Transport dispatch now prints the raw changelog entry count every sub-step (`[FluidTransport] changelog entries: N`), not just on overflow. Meant to be read via the existing `P` (pause) + `Right Arrow` (`step_once()`) workflow: a count that spikes once as a mass starts consolidating and then drops toward zero as it settles supports explanation 1 (capacity was the whole problem); a count that stays large and roughly constant tick after tick without decaying supports explanation 2 (still oscillating, cap increase just delays the symptom).

**Next step:** re-run the same `g_dt=0.2` repro with the raised cap and watch the printed counts. Not resolving this open item until that data comes back.

**Update — a third, distinct mechanism found, likely the dominant contributor:** while explanation 2 above ("still oscillating") was framed as a vague catch-all, the user's follow-up report ("water on the ground is always moving, never really settles... clogs the changelog with water that's just moving horizontally") pointed at something much more specific and provable — see the next entry. Both explanations 1 and 2 above may still be partially true, but this third mechanism is confirmed by direct calculation, not inference from a warning message, and is very likely what's actually filling the changelog on *settled* ground water specifically (as opposed to the still-actively-falling sphere, which is a separate, legitimate source of volume).

### BUG (FIXED, 2026-07-02): water on flat ground never settles — `round(old_f * damp)` has a fixed point, decay can get permanently stuck at 1–16

**Symptom:** reported directly: "water on the ground is always moving, it never really settles... it always clogs the changelog with water that's just moving horizontally." Got *worse*, not better, immediately after lowering `MIN_FLOW` from 16 to 1 (the low-fill-stuck-cell fix, two entries up) — a strong clue, since that fix specifically stopped filtering out the 1–16 magnitude range.

**Root cause — provable by direct calculation, not inference.** `flux_buf`'s persistence update was `flux_buf.data[lane] = int(round(old_f * params.damp + accel))`. For `damp = 0.97` and any integer magnitude `n` in `[1, 16]`, `round(n * 0.97) == n` — the decay term rounds right back up to its starting value. Concretely: `round(1 * 0.97) = round(0.97) = 1`; `round(16 * 0.97) = round(15.52) = 16`. **Decay alone can never reach exactly zero for any residual in this range** — it's a genuine fixed point of the update formula, not a slow asymptote. On a settled, flat puddle with no real pressure differential (`dh≈0`, `accel≈0`), any leftover residual flux in this range sits there forever, gets read by Scale/Transport every tick, and applied as a small (but real, nonzero) fill shift — perpetual, pointless shuffling that never converges, and a genuine changelog entry every tick for every affected voxel.

**Why lowering `MIN_FLOW` made it worse, not better:** `MIN_FLOW = 16` was, by coincidence, filtering out exactly this stuck range (`eff_flux()` treats anything with magnitude `< 16` as invisible) — so the rounding bug existed the whole time but had zero visible effect, because Scale and Transport never saw values in the range where it could get stuck. Lowering the threshold to 1 (needed to fix low-fill cells getting permanently trapped) simultaneously unmasked this completely different, previously-dormant bug across *every* settled body of water in the world at once — explaining both "why does ground water never settle" and "why did the changelog overflow get worse right after the last fix" in one mechanism.

**Fix:** truncate the decay term toward zero instead of rounding it, before adding the fresh `accel` contribution:
```glsl
int decayed = int(old_f * params.damp);   // truncation, not round — guarantees monotonic decay
float new_f = float(decayed) + accel;
new_f = clamp(new_f, -axis_cap, axis_cap);
flux_buf.data[lane] = int(round(new_f));
```
`int()` on a float truncates toward zero in GLSL (both directions — `int(-0.97) = 0`, not `-1`), so decay always shrinks in magnitude every tick with no fixed point: `int(1.0 * 0.97) = 0` (fully resolved in one step), `int(16.0 * 0.97) = 15` (still shrinking, not stuck). Only the carried-over persistence term needed this — `accel` (genuinely new forcing computed fresh this tick, not decay) still gets ordinary rounding on the final sum.

**Answers a design question that came up alongside this:** does a flux transfer have to go through the changelog? Yes — it's the only mechanism that updates `voxels_a` (the canonical GPU state the renderer reads), and skipping it for "merely cosmetic" transfers isn't actually possible without the render showing stale water. The fix belongs at the source (stop the spurious transfers from happening at all), not in routing around the changelog.

### BUG (FIXED, 2026-07-02): unbounded, one-sided fill creation at chunk-dispatch boundaries — stale flux pages read but never debited

**Symptom:** caught immediately by the new automatic conservation checker (previous tooling entry) — a sustained stream of `[Conservation] fill gained this tick: N` with **no corresponding losses ever printed**, growing without bound, from placing just a few droplets. Reported alongside a second, seemingly unrelated symptom: digging a deep hole and pouring water in, the water level rose barely at all, or extremely slowly.

**Root cause.** `flux_lane()` (the shader helper both Scale and Transport use to look up a neighbouring chunk's owned face) only checks whether that neighbour chunk **has a page allocated** — it does not check whether that chunk was **actually processed this tick**. The chunk-boundary fix from earlier today (giving every neighbour in the flux dispatch range a page, and separately, an idle-guard grace period before freeing pages that never became active) means a chunk can fall out of `flux_list` (active + 6 face neighbours, rebuilt fresh every tick) while still holding a page for a few more ticks. While it sits in that grace window, **Pass A never revisits it** (it isn't in the dispatch), so its last-computed flux values are frozen exactly where they were. But an *active* neighbouring chunk's Transport execution reads that frozen value via its own neighbour-owned-face lookup and credits itself — and since **Transport only ever reads `flux_buf`, it never writes to it**, nothing consumes or clears that value once read. The same active neighbour can read and credit itself from the identical stale number again the very next tick, and the tick after that, for the entire grace window — a real, repeatable, never-debited source of fill. With water constantly active near chunk boundaries, there's a continuous supply of newly-stale chunks feeding this, which is why the total kept climbing with no sign of stopping rather than settling at some fixed leaked amount.

**Why the hole-filling symptom is the same bug, not a separate one:** the water level in a deliberately dug hole is governed by real, correctly-computed downward flow (the gravity fixes earlier today) — comparatively modest and gradual, exactly as designed. The conservation total, however, was being inflated separately and much faster by phantom credits happening at essentially arbitrary chunk boundaries, unrelated to the pour location. Total fill skyrocketing while a deliberately-targeted hole barely rises is exactly what you'd see if most of the "new" fill was appearing somewhere other than where it was poured.

**Fix:** zero a paged chunk's flux data the instant it drops out of the current tick's dispatch range, rather than waiting for the idle-guard grace period to expire before freeing the page. This does not remove the grace period's own purpose (avoiding page alloc/free churn for chunks that briefly flicker in and out of the active set) — the page allocation itself still survives a few idle ticks for reuse efficiency. Only the *data* is invalidated the moment the chunk stops being actively recomputed, since stale-but-nonzero data is unsafe to leave readable by neighbours regardless of how briefly the chunk stays out of rotation. Implemented in `fluid_simulation.gd`'s `step()`, right after this tick's page allocation and before the Pass A/Scale/Transport sub-step loop: build the set of chunks in `flux_list`, then for every currently-paged chunk *not* in that set, zero its `vpc*3` flux lanes via `buffer_update`.

**Rule for the rest of this codebase's paging pattern:** "has a page" and "was processed this tick" are two different questions, and any shader logic that reads a neighbour's persistent per-chunk state through a page lookup needs to treat them as such — a page surviving for reuse efficiency does not mean the data behind it is still valid to read.

**Update (same day) — this fix did NOT resolve the leak.** Re-tested with the conservation checker running: same qualitative pattern (sustained one-sided gains, hundreds to low-thousands per tick, still climbing, never a single loss printed). The stale-page-during-grace-period mechanism above may still be real and worth keeping fixed, but it's evidently not the (only) dominant source. Rather than propose a fourth blind fix, added a location tracker instead of continuing to guess.

### TOOLING: gain-location tracker (added 2026-07-02) — pinpoints WHERE, not just how much

`fluid_flux.comp` binding 10 (`GainTracker`, 8 bytes: `flat_idx`, `amount`) — Transport does a plain (non-atomic, intentionally not synchronized against races — good enough for "which chunk to go look at," not meant to be a perfectly deterministic single winner) write whenever a voxel's applied gain exceeds the current tracked maximum for the tick. `FluidSimulation.step()` decodes `flat_idx` back into a chunk position + local `(x,y,z)` (same slot/local decomposition pattern as `_decode_dirty_bitmask`) and prints it alongside the conservation total, only when the conservation check has already found a nonzero delta:

[Conservation]   biggest single gain: 210 at chunk (3, -1, 2) local (17, 4, 9)
```

### GOTCHA: `SimulationRuntime._active` iterator invalidation

GPU simulations emit `chunks_committed` inside `step()`, which triggers `_on_chunks_committed`, which may `append` to `_active`. Iterating `_active` directly causes iterator invalidation. Fix: snapshot `_active` before the loop with `.duplicate()` and do a post-loop merge for any sims added mid-frame.

### DESIGN OUTCOME (2026-07-07): pressure projection — fully ported, bench-validated, and set aside after real in-engine testing under-delivered

**Status: parked, not deleted.** The Chorin quasi-static pressure-projection design (the DESIGN entry above, "SOLVED IN A 2D BENCH") was fully ported to `shaders/fluid_flux.comp` over a long session — `BuildRHS`/`solve_red`/`solve_black`/`Correct` plus a dedicated `LevelSurface` flat-puddle-leveling pass (`pass==6`, its own design gap documented in `FLAT_PUDDLE_HANDOFF.md`). Six real bugs were found and fixed in `LevelSurface` alone (LEVEL_DEGREE normalization, classify-symmetry, SUBMERGED_MIN threshold semantics, boolean-gate flicker, aggregate-vs-per-pair rounding, and finally a pressure-difference-based damping redesign), each validated in a Python bench mirroring the GLSL before porting — the process this project's discipline is built around worked exactly as intended, bug-for-bug.

**But real in-engine play kept finding real problems the bench suite didn't catch:**
- The U-tube acceptance test the whole design was built against was never actually a *complete* pass — it validated first-fill equalization, but pouring **more** water into an already-settled tube didn't make the far arm react at all. A connected-vessel system that only equalizes once, at first fill, hasn't actually modeled connected vessels.
- Settled columns could land in physically-uneven "staircase" configurations (e.g. `51/255/19/255/7/255/255` up a shaft) that then sit numerically stable — every face's corrective flux below `MIN_FLOW`'s deadzone — and never resolve, even though nothing about the configuration is actually at hydrostatic rest. This is the same `MIN_FLOW` churn-vs-precision tradeoff documented elsewhere in this file, just newly visible because pressure projection's own convergence behavior lands in this shape often.
- A separate investigation (with a fresh agent, Fable 5, given a full handoff) chased what looked like a `LevelSurface`-caused "one-sided mass drain" and root-caused it as a **bench geometry bug** (the repro's domain was accidentally fully sealed, giving the solver no free-surface anchor) rather than a real engine defect — a genuinely useful process win (confirms fix 6 and the bench-first discipline both held), but it also means a full investigation cycle was spent on a symptom that, once traced, wasn't actually about the fluid design at all.
- Performance and feel were both worse than the flux system being replaced — before/after, the previous system ran fast enough to iterate on interactively (drop things, watch waves propagate, tweak values, repeat) where the projection system did not, which matters as much for *being able to tell whether a fix is working* as it does for shipping.

**Decision (2026-07-07):** rather than keep iterating on a design that passes its own bench but keeps finding new failure modes in play, the whole effort was preserved and set aside. **Nothing was lost** — the complete implementation, all six `LevelSurface` fixes, the Fable 5 investigation and its handoff doc, and this session's rewind/snapshot debug tool all live on branch `pressure-projection-wip` (pushed to `origin`), untouched. `master` was reset to the last commit before any projection code existed (`598ceba`) — note that **none of the projection work was ever actually committed to git** before this; it had been uncommitted working-tree state the entire time, so "reset" here was really "first commit, then reset," not a loss of history.

**Open questions for whoever revisits this** (see `ARCHITECTURE.md` §5's current-to-do entry for the full framing):
1. Is per-tick global pressure projection the right tool for a voxel game's water at all, or does it fight the medium — worth exploring a hybrid where the existing flux model keeps doing what it's good at (cheap, local, wave-like horizontal movement) and something cheaper than a full Poisson solve injects just enough non-local awareness to handle connected vessels.
2. The flux system's own M2 (temporal amortization) was never reached — worth finding out whether pressure projection's performance complaint is inherent to the algorithm or just to not yet reaching the optimization tier that would have made it interactively testable.
3. **If a Python bench is built again for whatever's tried next, it must be a direct 1:1 port of the actual GLSL as it stands** (3D, red-black solver ordering, real chunk/dispatch-range discipline) — not a from-scratch model of the design. The 2D/serial-ordered benches used this round genuinely diverged from the shipped shader in ways that cost real debugging time; see `tools/fluid_prototypes/README.md` for the specifics.
